# 차분 테스트 하니스 (원작 에뮬 대 우리 엔진)

같은 시작 상태·같은 입력열로 원작(자작 68000 에뮬)과 우리 엔진(`Match.tick`)을 프레임별로 돌려 상태를 비트 단위로 비교한다.
엔진(`server/`)·클라이언트(`public/`) 파일은 건드리지 않는다. 3300 서버와도 무관하다(엔진을 node 로 직접 구동).

## 파일
| 파일 | 역할 |
|---|---|
| `scenarios.json` | 시나리오 정의(입력열·사전 조작·감시 대상·예상 판정) |
| `oracle_trace.py` | 원작 트레이서. 입력을 프레임마다 주입하고 선수 14명+공의 원시 값을 `traces/oracle/<이름>.json` 으로 덤프 |
| `ours_trace.mjs` | 상태 주입 어댑터 + 우리 트레이서 + 원작/우리 → 공통 형식 변환(단위·라벨 규칙은 파일 머리 주석) |
| `run.mjs` | 비교기. 콘솔 출력 + `analysis/22_diff_status.md` 생성, 우리 쪽 덤프는 `traces/ours/` |

## 실행 (프로젝트 루트에서)
```
python -I tools/diff/oracle_trace.py            # 원작 트레이스 생성(캐시: 입력열·setup 이 같으면 건너뜀). 프레임당 약 0.05~0.1초
python -I tools/diff/oracle_trace.py walk_R --force   # 특정 시나리오만 / 강제 재생성
node tools/diff/run.mjs                         # 전체 비교 + analysis/22_diff_status.md 갱신
node tools/diff/run.mjs walk_R -v               # 일부만(보고서는 안 씀), -v = 불일치 프레임 전부 출력
node tools/diff/run.mjs --no-pin                # 조작 선수 고정 끔(우리 자동 전환까지 비교)
python -I tools/diff/oracle_trace.py --verify walk_R  # 프레임 경계 방식 자체 검증(아래)
```
엔진을 고친 뒤에는 `node tools/diff/run.mjs` 만 다시 돌리면 된다(원작 트레이스는 캐시). 전체 약 1천 프레임, 수 초.

## 비교 규칙
- 프레임 i = i 번째 입력을 적용한 직후 상태. 프레임 0 = 주입 직후(여기서 다르면 "주입 불일치"로 표시, 어댑터 문제).
- 좌표·속도는 양쪽 모두 16.16 정수라 변환 없이 `===` 비교. 오프셋·허용 오차 없음.
- 감시 대상(`watch`): `p0`~`p13`(x,y,z,vx,vy,vz, 상태 라벨 act, 타이머 tmr), `ball`(x..vz, 모드, 보유자, 비행 중 위력), `rules`(전원 HP·남은 인원), `rng`(난수 시드 $E620).
- 상태 라벨: 원작 타입($0&0x7FFC)/서브($17) 와 우리 ST 를 `ours_trace.mjs` 의 표(HUMAN_SUB/TYPE_ACT/OURS_ACT)로 같은 이름으로 바꿔 비교. 엔진에 상태가 추가되면 OURS_ACT 에 한 줄 추가.
- 타이머는 원작 $18 RAM 값 그대로 비교(라벨이 catch/crouch/pickup/foul/down 일 때만). 원작이 상태 진입 프레임에 타이머를 아직 쓰지 않는 경우(웅크림 f1 = 0) 그 1프레임이 FAIL 로 잡힌다.
- 보고서의 "진단"(프레임을 밀면 일치, 원작 조작 전환, HP 변화)은 참고용이며 판정에 쓰지 않는다.
- 조작 선수 고정(기본 켬): 우리 엔진의 자동 조작 전환이 입력 대상을 바꾸지 않게 매 틱 좌팀 조작 선수를 원작 시작 값으로 되돌린다. 원작이 조작 선수를 바꾼 경우는 진단 칸에 표시된다(그 뒤 구간은 해당 영역 검증이 아님).

## 상태 주입 (`ours_trace.mjs` inject)
우리 엔진을 입장·점프볼이 끝날 때까지 틱한 뒤 Match 필드를 직접 덮어쓴다: 선수 x..vz·능력치(s0~s7)·HP·슬롯·조작 선수·남은 인원·공 x..vz/보유자·RNG 시드.
근사하는 것(보고서 "주입 근사·참고"에 출력): 공중 선수는 JUMP, 그 외는 IDLE 로 시작 / 공은 보유(HELD) 또는 LOOSE 만 / 방향(face)은 $3 bit0 추정값(비교 안 함).
주입하지 않는 것: CPU AI 내부 상태, 심판, 경기 시계, 포메이션. → 감시 대상이 아닌 선수는 양쪽이 다르게 움직인다.
엔진에 요청할 것(현재 없어도 1단계는 동작): 비행 중 공(FLY/필살기)·피격/쓰러짐 중 선수를 시작 상태로 넣을 공식 주입 API, AI 를 끄는 옵션(지금은 감시 대상 밖 선수의 AI 를 못 끈다).

## 시나리오 추가
`scenarios.json` 에 한 줄 추가 → `oracle_trace.py <이름>` → `run.mjs`.
```
{ "name": "air_throw", "area": "공중 투구", "setup": ["give_ball"], "pads": "C:1 -:8 BC:1 B:2 -:40", "watch": ["p0", "ball"], "known": "?" }
```
- `pads`: `키:프레임수` 나열. 키 = U D L R B C A S 조합, `-` = 무입력. `pads2` = 2P 패드.
- `setup`: `give_ball`(obj0 에게 공), `give_ball:k`, `pos:k,x,y`, `hp:k,값`, `poke:주소,값`(16진). 새 조작은 `oracle_trace.py` 의 `SETUP` 표에 함수 추가. 주입 어댑터는 조작 후의 원작 상태를 그대로 읽으므로 따로 손댈 필요 없다.
- 다른 시작 상태가 필요하면 `analysis/state/*.pkl` 을 만들고(`analysis/scripts/mk_state.py` 참고) `scenarios.json` 의 `state` 를 시나리오별로 쓰도록 `oracle_trace.py main` 을 확장.
- 확장 방향: 캐치·피격·아웃·교체 = `watch` 에 상대 선수(`p7` 등)·`rules` 추가 + 공을 상대에게 주는 setup / 점프볼 = 점프볼 직전 저장 상태 / CPU AI 입력 대조 = `watch` 에 CPU 선수와 `rng` 추가(난수 호출 순서까지 같아야 통과). 필요한 원작 필드는 `oracle_trace.py obj()` 에 추가하면 트레이스에 실린다.

## 오라클 신뢰도 (정답 의심 지점)
원작 값은 실기가 아니라 자작 에뮬 `analysis/scripts/m68k.py` 의 결과다. 실기·검증된 에뮬(BlastEm 등)과 대조한 적이 없다.
1. **CPU 명령 구현 오류 가능성**: 68000 명령·플래그를 직접 구현했다. 이 게임이 부팅·경기 진행되는 범위에서만 검증됐고, 드문 명령/플래그 오류는 수치(예: 나눗셈·시프트 결과)를 조용히 틀리게 만들 수 있다.
2. **타이밍은 사이클이 아니라 명령 수**: 프레임당 14000명령, VBlank 는 12500번째. 실기에서 처리 지연(랙)이 나는 프레임을 재현하지 못한다. 트레이서는 메인 루프 대기 지점(PC 0x14E2/0x14E6)을 프레임 경계로 쓰고, 14000명령 안에 못 돌아오면 `lagFrames` 로 기록한다(현재 전 시나리오 0).
3. **RNG 시드**($E620)는 VBlank 마다 +2 되고 호출 시 섞인다. 호출 횟수는 CPU AI 등 게임 진행에 좌우되므로 에뮬 오차가 있으면 여기서 먼저 갈린다. H/V 카운터·Z80·사운드 타이밍에 의존하는 로직이 있다면 재현되지 않는다.
4. **프레임 경계**: `MD.run_frame()` 끝에서 RAM 을 읽으면 선수 0~4 는 새 프레임, 5~13·공은 이전 프레임이 섞인다(측정으로 확인). 기존 `audit_*.py`/`t_*.py` 수치 중 공·상대 선수 타이밍은 1프레임 어긋나 있을 수 있다. 이 하니스는 대기 루프 경계에서 읽으며, `--verify` 로 표준 run_frame 진행과 RAM($C000~$E7FF)이 같음을 확인한다(setup 없는 시나리오만 가능).
5. **사전 조작(setup)은 RAM 직접 쓰기**: `give_ball` 은 실제 줍기/캐치 경로를 거치지 않으므로 원작이 함께 바꾸는 다른 변수를 빠뜨렸을 수 있다. 중요한 결론은 실제 입력만으로 만든 상태에서 다시 확인할 것.
6. **시작 상태**(`ctrl0.pkl`)는 점프볼 직후라 상대 선수 1명이 공중이고 공이 굴러다닌다. 긴 시나리오는 CPU 의 공·조작 전환에 오염될 수 있다(진단 칸으로 표시).
7. 라벨 표(타입/서브 의미)는 `analysis/05_match_rules.md` §7 기준이다. CPU 형 타입의 서브는 미해독이라 `cpuN` 으로만 표시한다.
