# 피구왕 통키(炎の闘球児 ドッジ弾平, MD 1992) 웹 온라인 재구현 - SPEC

상태: 초안 v0.1 / 작성: 문기획 / ROM 분석(analysis\) 진행 중이라 "미확정"은 분석 후 갱신
참고 구조: ..\tank (서버 권위 로비/방/재접속, docs\PROTOCOL.md), ..\liero

## 1. 목표·범위
목표: 메가드라이브 원작을 최대한 비슷하게(규칙·조작감·연출) 웹에서 온라인 멀티플레이로 재구현. 2D, 해상도 업 그래픽, 디자인된 한글 폰트 UI, 한국판(피구왕 통키) 이름 사용. 개인용(비공개 운영 가정).

이번 범위(In)
- 닉네임 로그인, 로비(방 목록), 대기실, 방 코드 대전, 재접속
- 1:1 대전 한 판(시작~종료~결과)
- 경기 결과 기록 구조(저장만, 화면 노출 없음)

제외(Out)
- 랭킹/레이팅/시즌(구조만 확보, 보류)
- 계정·비밀번호·소셜 로그인, 관전, 채팅 고도화, 친구, 결제
- 원작 싱글 스토리 모드, AI 상대(1차 제외, 이후 검토)
- ROM 에셋 원본 배포(§4 에셋 정책 참조)

## 2. 원작 규칙: 확정 / 미확정
확정 후보(일반 피구, ROM 확인 전까지는 "후보")
- 두 팀이 코트를 나눠 공을 던져 상대를 맞히는 경기
- 공에 맞으면 아웃/데미지, 받으면(캐치) 무효 및 공격권 이동
- 한국판 명칭은 "피구왕 통키" 계열 이름 사용

미확정(ROM 분석 결과로 채울 항목, 확인 방법 병기)
| 항목 | 확인 방법 |
|---|---|
| 팀 인원, 내야/외야 구조, 코트 크기 | 스프라이트·맵 카탈로그, 게임 시작 루틴 |
| 승패 판정(전멸/체력/시간/세트) | 승패 분기 코드, 결과 화면 |
| 피격 판정: 아웃제인지 체력제인지 | 데미지 처리 루틴 |
| 캐치 판정(타이밍, 방향, 실패 시 처리) | 충돌/입력 루틴 |
| 필살기(입력, 게이지/소비, 위력, 연출) | 입력 핸들러, 능력치 테이블 |
| 캐릭터/팀 목록, 능력치 | ROM 데이터 테이블 |
| 조작 체계(버튼 수, 선택 범위 입력) | 패드 입력 처리 |
| 게임 속도(프레임레이트, 60Hz/50Hz), 물리 | VBlank 주기, 속도 상수 |
| 한국판 이름 매핑표 | analysis\names_ko.md + 사용자 확정 |
| 랜덤 요소(시드, 판정 난수) | 난수 루틴 |

규칙 확정 시 이 표를 "확정 규칙" 절로 옮기고 근거(ROM 주소/분석 파일)를 기록한다.

## 3. 인수조건 (핵심)
세션/로그인
- AC-01 닉네임(길이·허용 문자는 §6 결정)만으로 입장한다. 중복 닉네임이 접속 중이면 거부하고 토스트로 안내한다.
- AC-02 서버는 세션 토큰을 발급하고, 새로고침 후 같은 토큰으로 같은 사용자로 복귀한다.

로비/방
- AC-10 로비에서 공개 방 목록(방 코드/방장/인원/상태)을 실시간으로 본다.
- AC-11 방을 만들면 고유 방 코드(예: 4~6자)가 발급되고, 코드 입력으로 입장한다. 없는 코드/가득 찬 방/진행 중 방은 사유와 함께 거부한다.
- AC-12 대기실에서 방장/참가자 표시, 준비 토글, 방장만 시작할 수 있다. 전원 준비 시에만 시작 가능하다.
- AC-13 방장이 나가면 방장이 위임되고, 방이 비면 삭제된다.

대전
- AC-20 시작하면 두 클라이언트가 같은 초기 상태에서 시작하고, 상태 판정은 서버만 한다. 클라이언트 입력 조작으로 판정을 바꿀 수 없다.
- AC-21 한 판이 승패 또는 무승부로 종료되고, 결과 화면 후 대기실로 복귀한다.
- AC-22 입력 후 상대 화면 반영 지연이 일반 광대역 기준 체감상 끊김이 없다(수치 목표는 §6 결정).

재접속
- AC-30 대전 중 연결이 끊기면 유예 시간(권고 30초) 동안 자리를 유지하고, 복귀 시 현재 상태로 이어진다.
- AC-31 유예 초과 시 기권패 처리하고 상대에게 알린다.
- AC-32 서버 재시작 시에는 진행 중 방이 소멸해도 되며, 클라이언트는 로비로 안전하게 복귀한다.

기록/확장
- AC-40 경기 종료 시 결과 레코드(경기ID, 시작/종료 시각, 참가자, 승패, 종료 사유, 규칙/빌드 버전)를 저장한다.
- AC-41 100명 이상 동시 접속(로비 포함)에서 방 단위로 상태가 격리되고 한 방의 오류가 다른 방에 영향을 주지 않는다.

공통
- AC-50 오류와 거부 사유는 토스트로 표시한다(인라인 에러 박스 금지, tank 프로토콜과 동일 방침).
- AC-51 모든 UI 텍스트는 한글 디자인 폰트로 표시하고, 에셋은 경로 교체만으로 바뀐다.

## 4. 권장 기술 구조
- 서버: Node.js 서버 권위. 방 하나 = 독립 게임 루프(고정 틱, 원작 프레임레이트에 맞춤, 확정 전 60Hz 가정). 클라이언트는 입력만 보내고 서버가 상태를 확정해 스냅샷/이벤트를 전송한다.
- 전송: WebSocket(JSON으로 시작, 이후 바이너리 전환 여지). 메시지 구조는 tank PROTOCOL.md(세션/재접속/방/오류) 패턴을 따르되 dodge-danpei 전용 docs\PROTOCOL.md를 별도로 둔다.
- 클라이언트: HTML5 Canvas, 고정 해상도 논리 좌표 + 정수배 확대, 입력은 키보드 우선(패드 후순위). 예측/보간은 2단계에서 검토하고 1차는 서버 상태 렌더 + 단순 보간.
- 규칙 엔진: 렌더·네트워크와 분리된 순수 모듈(서버에서 실행, 단위 테스트 가능). ROM 확정 규칙은 데이터(JSON)로 외부화한다.
- 에셋 분리: assets/ 경로와 manifest(키 → 경로)를 두고 코드는 키로만 참조한다. 임시 에셋 → 업스케일/리디자인 에셋으로 교체 가능해야 한다.
- 에셋 정책: ROM 추출 원본(analysis\)은 분석용이며 배포 산출물에 포함하지 않는다. 개인용 단계에서는 업스케일본을 사용하되 공개 전에는 새 에셋으로 교체한다.
- 확장성(100명+): 단일 프로세스 Node 이벤트 루프로 1차 충족 가능(방당 2명, 틱 부하 작음). 방/세션 상태는 저장소 인터페이스 뒤에 두어 이후 프로세스 분리나 Redis 전환이 가능하게 한다. 로비 갱신은 변경분 브로드캐스트로 제한한다.
- 저장: 경기 결과는 저장소 인터페이스로 추상화한다. 1차 SQLite 또는 JSON Lines(권고: SQLite), 랭킹 도입 시 같은 레코드를 재사용한다.
- 세션: 닉네임 + 서버 발급 토큰(로컬 저장). 비밀번호 없음.

## 5. 단계
1차 프로토타입(1:1 한 판 플레이 가능)
- 닉네임 입장 → 로비 → 방 생성/코드 입장 → 대기실 준비/시작 → 1:1 한 판(이동, 던지기, 캐치, 피격, 승패) → 결과 → 대기실
- 재접속(유예 30초), 결과 레코드 저장
- 그래픽은 임시, 캐릭터 1~2종, 필살기는 ROM 확정 후 1종만
- 규칙은 "확정 후보 + 분석된 범위"만 구현, 나머지는 데이터화해 후속 반영

이후 단계
- 2단계: ROM 규칙 정합 강화(전 캐릭터, 필살기 전체, 팀전), 지연 보정, 사운드
- 3단계: 해상도 업 에셋·한글 UI 완성, 방 옵션, 연습/AI 상대
- 4단계: 랭킹/전적 화면, 관전, 운영 도구

작업 분해(제안 담당)
- 규칙 명세 확정(ROM 분석 연동): 문기획 + 분석 담당
- PROTOCOL.md 작성, 서버 방/세션/재접속, 규칙 엔진·게임 루프: 박백엔
- Canvas 클라이언트·로비 UI: 윤프론
- 실화면 검증: 강화면 / 2인 실플레이: 하플레이
- 에셋/한글 폰트·UI 스타일: 안아트
- 독립 리뷰(입력 검증, 토큰, 방 코드 추측): 정검수

## 6. 열린 질문 (권고안 병기)
1. 에셋 방침: 개발 중 ROM 추출/업스케일 에셋 임시 사용. 권고: 그대로 진행, 공개 전 교체(법무는 비차단 메모).
2. 1차 인원 구성: 권고 1:1, 원작 구조 확인 후 팀전 확장.
3. 한국판 이름: analysis\names_ko.md 사용, 불명 항목은 음역 후보 + 확인 필요 표시.
4. 닉네임 규칙: 2~10자, 한글/영문/숫자, 접속 중 중복 불가.
5. 조작: 키보드 1차, 패드 후순위.
6. 지연 목표: RTT 100ms 이내 쾌적, 보정은 2단계.
7. 배포: 로컬 개발 후 단일 VPS.
8. 랭킹: 결과 저장만, 화면 없음.
