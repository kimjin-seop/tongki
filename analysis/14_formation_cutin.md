## 0. 요약
- **포메이션은 원작에 있다** [확인]. 원작 이름은 "フォーメーション アタック"(작전 타임). 공을 든 지상 선수 쪽 사람이 **Start** 를 누르면 YES/NO 창이 뜨고(게임 정지), YES 면 같은 편 7명이 팀별 고정 위치로 모인 뒤 **팀별 고정 순서로 자동 패스를 돌리다가 "엔드 어택"(위력 = 던지는 선수 s4×4)** 을 던진다. 한 경기 사이드당 **3회**. CPU 도 확률로 쓴다.
- **팀별 작전 이름은 ROM 그래픽으로 확정** [확인]: 15종(五芒星, V字, エンドアタック 등). 팀1 セントアローズ = **五芒星**(패스 경로가 실제로 별 모양), 팀3 ブラックアーマーズ = **V字**. 08 문서의 "배너 8=エンドアタック, 9=오망성"은 오해였고, **배너 8/9 는 사이드1/사이드2 팀의 작전 이름 슬롯**이다(§1.6).
- **필살기 컷인·이름 표시는 원작에 없다** [확인]. 필살기 발동 시 배너/일시정지/암전/번쩍임/카메라 연출 없음, 변화는 공 그래픽·팔레트 4색·잔상·효과음뿐(06 §4 + 이번 화면 캡처). ROM 전체를 자체 문자코드로 디코드해도 **필살기 이름 문자열은 없다**(일반 명사 "ひっさつシュート" 만). → 06 §5 의 ID→이름 대응은 **ROM 으로 확정 불가**(추정 그대로).
- (2026-11-18: 웹 컷인은 사용자 지시로 제거, §3.3 머리말) 웹 컷인은 **새로 추가하는 연출**이며, 서버의 기존 `special` 이벤트(`{p, id}`)와 스냅샷 `b[6]`(kind=ID+1)만으로 **클라이언트 전용 구현 가능, 서버 변경 불필요** [확인: 서버 코드 읽기].

## 1. 포메이션 (작전 타임)
### 1.1 발동 조건 — 사람 [확인]
매치 서브 0x00(플레이) 0x5C04 에서 P1/P2 Start(edge) → 0x5CBE/0x5CCC:
```
조건(모두 만족) -> 서브 0x08(작전 창), 효과음 0xA1, $E24E=사이드, $E24C=그 팀 선수 배열
  사이드.$17 != 0           (사람 사이드)
  $E250 == 0                (진행 중인 포메이션 없음)
  공.$3 bit4 (보유 중)  and  보유자.$3 bit2 == 0 (보유자가 지상)
  보유자 사이드 == Start 누른 사이드
  보유자 사이드.$57 (남은 인원) >= 4
  보유자 사이드.$59 (남은 작전 횟수) != 0
  그 팀 7명 모두 $1E == 0   (0x5D3E, $1E 의미 미해독 [코드])
아니면 -> 서브 0x4C(일시정지)
```
- 즉 **공을 들고 지상에 있을 때 Start = 작전 창, 그 외 Start = 일시정지**. P2 패드도 동일(사이드2) [코드].
- 횟수 `$59`: 일반 매치 준비(0x5880, 상태 0x10/0x28/0x2C 경로)에서 사이드당 **3** [확인: 실측 3→2]. 1:1·특수 구성(0x3550/0x3780/0x5B30)은 0 → 사용 불가 [코드].
### 1.2 YES/NO 창 (서브 0x08, 0x5E40) [확인]
- 생성: `$D900` 타입 0xBC(남은 횟수 공 아이콘, 화면 (160,68) 부근, `$59` 개 표시), `$D980` 타입 0x58(커서), `$DA00` 배너 타입 1(창, 기준점 (160,80), 104x64). 팔레트 0x3A1AC → CRAM 라인2(0x58C6).
- 문구(그래픽): `フォーメーション アタック?` / `YES  NO` / `のこり ●●●`. 스크린샷 `formation_00_yesno_window_x3.png`.
- **기본 커서 = NO**($E238=1). ←=YES($E238=0), →=NO(0x51CA). A/B/C/Start 중 아무거나(edge, `$E20D & 0xF0`) 결정 → 효과음 0xA1.
- **창이 떠 있는 동안 게임 정지**: 서브 0x08 은 오브젝트 갱신(0x1E28)·시계(0x5378)를 호출하지 않음(배너 4개만 갱신 0x4F06) [확인: 선수·시계 정지].
- NO → 0x5E24: 서브 0x00 복귀(횟수 차감 없음) [확인]. YES → 서브 0x1C.

### 1.4 엔드 어택 발동 조건 (0x9D32, 매 수신 순간 1회 판정) [확인]
- **사람**: 받는 순간 **B 를 누르고 있으면**(현재 입력 `$E20C` bit4) 또는 **패스 수 ≥ 32** 이면 엔드 어택. [확인: B 를 f200~229 홀드, f212 수신 → f213 엔드 어택. B 를 비행 중에만 잠깐 누르면 무시]
- **CPU**: 수신마다 `rand&0xFF < 0x40`(25%) 이면 `$E221`+1, `$E221 > 4`(5회 성공) 이면 엔드 어택 후 `$E221=0`. 기대 약 20패스 [코드; 실측 31패스(force 1회)].
- 대상: `선수.$56 → $18` = 상대 사이드의 현재 활성 선수 [코드; 실측 조준 방향 일치].

### 1.6 연출 [확인]
- **배너**: 배너 오브젝트 2개 동시. 타입 7 = `フォーメーション`(기준점 (192,96)), 타입 8(사이드1) 또는 9(사이드2) = 작전 이름(기준점 (128,96)). 두 배너 모두 프레임 표상 64x16 이고 이름 그래픽은 경기 준비 때 팀별로 VRAM 타일 0xE0(사이드1)/0xF0(사이드2)에 압축 해제(0x579E). 수명 0(상태 전환까지) → 실측 집합+대기 동안 약 82f 표시. 화면 고정(카메라 무관).
  - 그래서 08 §5 의 "8 エンドアタック, 9 오망성(작전 이름)" 은 ctrl0 대진(팀0 대 팀1)에서만 맞는 표기다. 정정: **8/9 = 사이드별 작전 이름 슬롯**.
- 이름 그래픽은 흰 글자 + 검은 테두리 + **50% 체커 디더 검정 배경**(색 인덱스 2)이다. 1배 화면에서는 반투명 그림자처럼 보인다 [확인: 화면 픽셀 대조].
- **카메라**: 대기 단계에서 포메이션 팀이 공격하는 쪽 끝으로 이동(사이드1 → x=191, 사이드2 → 0), 패스 중 `$E251=1` 로 공 추적 정지, 엔드 어택 시작 시 해제 [확인: cam 191 고정 실측].
- **효과음/음악**: 창 열기·결정 0xA1, 패스 0xC3, 수신 0xA5(관측), 엔드 어택 점프 0xA6·투구 0xA2(일반 투구와 같음). BGM 변경 없음 [코드]. 실제 소리는 청취 불가 → **UNVERIFIED**.
- 엔드 어택 전용 배너·컷인·화면 효과 **없음** [확인: 몽타주].
### 1.7 엔드 어택 (0x9A86~0x9B2A) [확인]
```
점프(0x8802) -> 애니 이벤트 프레임에 투구:
  위력  $1A(공) = 0x89AA(선수) << 2      # 실측: s4=25 -> 100, s4=20 -> 80  (= s4 x 4)
  속도  $74(공) = 0x7D0C(선수) + 0x400   # 실측 0x940(s6=84), 0x800(s6=64) = s6/16 + 4 px/f
  타입 0x14(일반 투구 공), 위험 플래그 bit6 set  # 0x8BEE(필살기 판정)를 거치지 않음 -> 절대 필살기 아님
```
- 던지는 선수는 외야여도 된다(실측 1P: 외야 아래 슬롯7, CPU: 외야 뒤 슬롯10).
- 피격 판정·캐치 규칙은 일반 투구와 같은 코드 경로 [코드]. 실측: CPU 엔드 어택(위력 80)이 가만히 있던 1P 슬롯0 에 명중, HP 85→15(-70 = 80 - 방어 10) [확인]. 1P 엔드 어택(위력 100)은 CPU 대상이 피해 빗나감 [관측]. **1P 가 캐치/웅크림으로 막는 실험 결과는 §1.10**.
### 1.8 CPU 사용 로직 (0xBCC2 → 0xD948) [코드 + force 실측]
CPU 활성 선수가 지상에서 공을 들고 행동을 정할 때(리그 `$E697` 이면 생략):
```
if $E681 or $E266 or $E250: 안 함
사이드.$62 += 1 ; if $62 < 문턱[팀](0x186FA: 2~4) : 안 함
$62 = 0
if 남은 인원 >= 4 and 남은 횟수 > 0 and (rand & 0xFF) <= 0x80 (약 50%) and 7명 $1E==0:
    $E266=1, $E24E=사이드, $E24C=팀 배열   -> 다음 프레임 서브 0x1C 로 바로(YES/NO 창 없음)
```
- 문턱: 팀0~24 = 3,2,2,2,3,3,3,3,3,3,3,3,3,3,3,4,4,2,2,3,3,4,2,2,2. 팀1(五芒星)·팀3(V字)는 2 → 공을 잡을 때마다 2번에 1번 꼴로 50% 시도.
- 자연 발생은 이번 2500f 관찰에서 카운터가 1회만 올라 재현 못 함 → `$E266` poke(force)로 실측 [미확인: 자연 빈도].
### 1.9 소모 자원·시간

## 2. 필살기 컷인
### 2.1 원작에 컷인이 있는가 → 없음 [확인]
- 필살기 공 전이(0x8BEE/0xB7D8)·공 핸들러(0xADB8~) 어디에도 배너(타입 0x54 @$D900) 생성·서브상태 전환·일시정지 코드가 없다. 배너 생성 지점 전수(0x360E, 0x3AC2~, 0x3DE2~, 0x5772, 0x5E4C, 0x5F30, 0x6134, 0x6192, 0x631E, 0x6430, 0x6470, 0xDB7A, 0xDBCA)는 메뉴·결과·작전·시작·종료용뿐 [코드].
- 화면 캡처 `special_id22_no_cutin_montage.png`(ID22, 발동 −1~+20f): 배너 슬롯 4개 모두 비어 있고 서브상태 0x00 유지, 게임 정지·암전·번쩍임 없음. 차지 중 공이 하얗게 변하는 것(ROM 대사 "ボールのいろが まっしろに なったときに Bボタンを はなすと なげられる" 0x76B41)과 발동 후 불꽃 공 그래픽만 보인다 [확인]. 06 §4 의 VSRAM/CRAM 검사(ID 22,25,31,48)와 일치.
- 선수 얼굴 확대·초상 연출 없음. HUD 얼굴은 피격 시 표정만 바뀜(07_hud).
### 2.2 필살기 이름 ROM 문자열 → 없음 [확인]
- 팀·선수 이름의 자체 1바이트 문자코드(0x21C0, 09 문서)를 ROM 전체에 적용해 가나 4자 이상 구간 17,310개를 추출(`romtext.py`): `ショット` 0건, `ほのお` 0건, 기술명 후보(スカイ/トマホーク/アックス/スピン/ドライブ/カミソリ 등) 0건. `シュート` 는 AI 파라미터 이름(0xEA96~, 디버그용 "シュートりょく" 등)과 특훈 대사 "ひっさつシュート"(0x769DE, 0x76B16)에만 나온다.
- 그래픽 이름표도 없다: 배너 프레임 19종(0xE130), 팀별 이름 그래픽(0x38660)은 작전 이름 15종뿐.
- 결론: **06 §5 의 ID→한국판 이름 대응은 ROM 으로 확정 불가(전부 추정 유지)**. 확인 가능한 출처는 원작 연출 자료/한국판 자료뿐 [미확인]. 스토리 화면 그래픽(대화 장면 일러스트)은 이번에 전수 확인하지 않음 [미확인: 잔여 위험 낮음].
### 2.3 확인된 관련 규칙(대사 근거)
- 0x76AAA "あいてのなげた シュートを キャッチしたら すばやく Bボタンで なげかえすと キャッチしたシュートを そのままかえせるぞ!" = 06 §3.3 반격 규칙(글로우 60f 안에 되던지면 같은 필살기)의 게임 내 설명과 일치 [확인: 텍스트].
- 0x76B6A "ダッシュジャンプすると ジャンプちゅうの じかんが ながくなって なげやすくなるぞ!" (대시 점프 = 체공 증가) [확인: 텍스트].

## 3. 웹 구현 사양
### 3.1 포메이션 — 서버 상태 머신 추가안 (박백엔)
원작 구조를 그대로 옮기되 **온라인 대전에서 한 사람이 게임을 멈추는 창은 두지 않는 안**을 기본으로 제안(결정 필요 §5-1).
```
match.fm = null | { seat, team, nameIdx, st, t, passes, holder, endReq }
match.sides[s].fmLeft = 3        # rules.formation.uses (모드별 0 가능)
입력: BIT.S = 128 (작전) 신설 — 서버 consts.BIT 에 추가, 클라 net 입력 바이트 bit7
발동(사람): 플레이 중 && edge(BIT.S) && 공 보유자가 내 편·지상 && remaining>=4 && fmLeft>0 && fm==null
발동(CPU): 공 잡을 때마다 cnt++; cnt>=THRESH[team] 이면 cnt=0, rng.int(256)<=128 이면 발동 (원작 그대로, 시드 결정성 유지)
st GATHER: 팀 7명 목표 위치(formations.json pos, 미러는 512-x)로 3+s2/16 px/f 이동, 전원 도착 -> HOLD
st HOLD  : 60틱, 시계 정지(원작) — 시계 정지 여부는 결정 §5-3
st PASS  : 보유자 자동 패스(속도 8px/f, 상대 충돌 없음, 위력 3) -> 수신 10틱 후 다음 패스
           수신 순간: 사람 = B 홀드 or passes>=32 -> END / CPU = rng<64 이면 cnt2++, cnt2>4 -> END
st END   : 수신자 점프 투구, 위력 s4*4, 속도 s6/16+4, 일반 투구 공(필살기 판정 안 함), fm=null
중단: 패스 공이 바닥/벽(LOOSE) -> fm=null
```
- 이 동안 포메이션 팀 선수 입력은 무시(사람 B 판정 제외), 상대 팀은 정상 진행.
- 데이터: `analysis/data/formations.json` 을 `server/data/formations.json` 으로 옮겨 사용(pos_by_group, pos_by_group_mirror, pass_next_slot_by_group, cpu_threshold, name_idx). 슬롯 번호는 서버 `court.json` 슬롯 0~12(같은 번호·같은 기본 좌표, 예: 슬롯4 a=(352,24) b=(160,24))와 동일 [확인: 파일 대조].
- **메시지 프로토콜 변경안**:
  - 입력: 기존 입력 바이트 bit7 = 작전(Start). 구버전 클라는 0 이라 호환.
  - 스냅샷: `fm: [seat, st, t, passes, nameIdx] | null`, `fmLeft: [n0, n1]`, `cam` 은 기존 필드로 고정값 전달(HOLD/PASS 중 원작처럼 고정할 경우).
  - 이벤트: `fm_start {seat, team, name}`, `fm_ready {seat}`(HOLD 끝), `fm_pass {p, tgt}`(기존 `pass` 재사용 가능), `fm_end {p, pw}`(엔드 어택 투구, 이어서 기존 `throw` 도 발생), `fm_cancel {seat}`.
  - game_start `info().rules` 에 `formation: { uses, names: [nameIdx per seat] }`.
- 테스트(핵심 2개만): ① 사람 발동 → 32패스 자동 엔드 어택 → 위력 = s4*4, ② CPU force 발동 시드 고정 결정성(같은 시드 같은 해시).

## 5. 사용자 결정 필요
1. **YES/NO 창(게임 정지) 재현 여부**: 원작은 창이 뜨면 전체 정지. 온라인 대전에서는 상대를 멈추게 하므로 권고안 = 창 없이 Start 한 번으로 즉시 발동(남은 횟수는 HUD 표시), 오조작 방지가 필요하면 클라에서 "Start 두 번" 확인.
2. **포메이션 도입 범위**: 전 모드 vs 캠페인/CPU 전만. 원작은 일반 매치 전부 사이드당 3회.
3. **집합·대기 동안 시계 정지**: 원작은 정지(약 1.4초+). 권고안 = 원작대로 정지.
4. **V字 한글 이름**: 'V자 패스'(names_ko 불확실) vs 'V자 포메이션'(직역). 권고안 = 직역.
5. **엔드 어택 위력 s4x4**: 원작 값(80~100+)은 대부분의 선수를 한 번에 크게 깎는다. 원작 그대로 둘지 밸런스 조정할지(임밸런 측정 권장).
6. **컷인 고유 필살기 이름**: ROM 근거가 없어 `필살 슛!` 고정이 기본. 통키(팀0 선수0, ID22)만 '불꽃슛'을 예외로 허용할지(06 §5 추정 중간 수준, 원작 상식).

## 6. 못 한 것 / 불확실
- CPU 자연 발동 빈도(force 로만 실측), `$1E`(발동 조건의 7명 플래그) 의미, 엔드 어택 공의 `$76`(반격 필살 플래그) 잔존 여부.
- 2P(사람 대 사람) 사이드2 발동, 미러 카메라 값(0)의 실제 화면은 CPU 쪽 캡처로만 확인.
- 효과음 실제 소리(청취 불가, UNVERIFIED), 0xA5 가 수신음인지(큐 관측만).
- 스토리 대화 그래픽 안의 기술 이름 존재 여부(전수 미확인).
