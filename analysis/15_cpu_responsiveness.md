# 15. CPU 반응 지연·외야 조작 전환 지연 분석 (분석 전용, 소스 미수정)

작성 2026-11-17. 사용자 불만: "CPU 동작이 굼뜨고, 공이 외야로 가도 조작 선수 전환이 즉각적이지 않다."
표기: [실측]=이 문서 작성 중 직접 측정, [코드]=소스 판독, [추정]. 줄 번호는 작성 시점 기준이며 다른 작업자가 match.js 를 동시에 수정 중이라 어긋날 수 있다.
측정 스크립트(임시, 프로젝트 밖): 웹=Node 로 Match 직접 구동, 원작=analysis/state/ctrl0.pkl 에서 공(0xC700)을 정지 공(타입 0x1C, 서브4, 타이머 30)으로 배치 후 프레임 실행(analysis/11 와 같은 방식).

## 1. 결론 요약
1. **외야 전환 지연 자체는 원작과 동일**(정지 후 29f). 불만의 실체는 "정지까지 걸리는 시간 + 30f" 이다. 웹은 공 정지까지 중앙값 173f(최대 317f)(tools/ball_sim.mjs, stage0, 20시드) → 전환은 굴러가는 동안 일어나지 않고 약 3.0~5.0초 뒤에 일어난다. 원작의 정지 시간 분포는 미측정(확인 필요).
2. **CPU 굼뜸의 최대 원인은 이동 속도.** 웹 CPU 는 걷기만 한다(0.50~0.75px/f, spd 8/12 기준 spd/16). 대시(더블탭)는 사람 조작 선수만 가능(match.js 더블탭 분기 `this.humans[p.seat] && p.pid === ctrl`). 원작 CPU 는 대시 서브상태(sub 8)로 달린다(에뮬레이터 실측 최대 3.5px/f, 외야 타입 0x74 도 sub 8 사용).
3. CPU 투구 지연(레벨2: 최소 50f), 방어 반응 시점 후행(trigShift), 방어 실수 확률(blunder)이 "굼뜸" 체감에 더해진다. 이는 난이도 파라미터라 데이터만으로 조정 가능.
4. 파라미터만으로 해결 가능한 것: 전환 주기(ctrlSwitch.tickFrames), 줍기 대기, CPU 난이도 값. 코드 변경이 필요한 것: CPU 대시, 굴러가는 공 선제 전환, 외야 CPU 추격.

## 3. 사람 쪽 외야 타게팅 전환 지연
코드(match.js autoSwitch, 846행~): 외야 구역 전환 조건 = `LOOSE && z==0 && vx==vy==0 && ballZone>0 && still>=tickFrames(30) && (still-30)%30==0`.
- 공이 외야 존에 **정지한 시점부터 정확히 30f** 후 전환(원작 f29 와 동일). 실측 [웹]: 상단 (350,25) 정지 배치 → 29f 에 ctrl 슬롯4. 원작 [실측]: f29.
- 그 전까지(굴러가거나 바운스 중, 또는 정지 후 29f 이내): 4번째 분기(`!valid(cur) || LOOSE && z==0`)가 **내야 최근접 선수**로 전환시킨다(현 조작 선수보다 16px 이상 가까울 때). 즉 외야로 간 공에 대해 조작권이 먼저 엉뚱한 내야 선수로 갔다가 30f 뒤 외야로 점프하는 구간이 생긴다.
- 지연 구성(공이 외야 존에 들어간 시점 → 전환):
  - 존 진입 후 정지까지: 바운스·마찰 시간. 마찰 0.125px/f², 속도 2.5px/f 공은 약 20f(25px), 3px/f 는 24f 구름. 전체 LOOSE 정지까지는 중앙값 173f(ball_sim; 바운스 포함, 외야가 아닌 경우 포함한 통계).
  - 정지 후 30f(0.5초).
  - 합계 대략 0.5초(정지 직전 진입) ~ 5초. 사용자가 "즉각적이지 않다"고 느끼는 것은 타당.
- 참고: 투구가 사람 사이드 선수를 향할 때는 이미 비행 시작 시 대상 선수로 즉시 전환(b.tgt, 같은 파일 857행 부근)되어 별도 지연 없음.
- 웹 캠페인 시뮬(tools/campaign_sim.mjs)은 humans=[false,false] 이므로 autoSwitch 의 사람 분기를 거치지 않는다 → **전환 관련 수정은 시뮬 승률에 반영되지 않는다**(실플레이 승률에는 사람에게 유리하게 작용).

## 4. 수정안
### A. 파라미터(코드 불변, server/data/rules.json)
| 항목 | 현재 | 제안 | 효과·부작용 |
|------|------|------|-------------|
| ctrlSwitch.tickFrames | 30 | 10~12 | 정지 후 전환 지연 0.5초→약 0.17~0.2초. 원작 이탈(원작 충실도↓)이지만 편의 목적. 주기 판정이 `still>=tick && (still-tick)%tick==0` 이라 값이 작으면 정지 후 매 tick 마다 재평가(근접 선수가 바뀌면 조작 전환 흔들림 가능) |
| autoPickup.stillFrames | 15 | 8~10 | CPU 줍기 5~7f 단축. 효과 작음 |

| cpu.levels.N.holdDelayAdd | 45/30/20 | 레벨2 30→20, 레벨1 45→35 등 | CPU 투구 템포 상승 = 난이도 상승(§4-C) |
| cpu.levels.N.trigShift | −6/−4/−2 | −3/−2/0 | 방어 반응 빨라짐 = 난이도 상승 |
| ai.holdDelayBase | 20 | 15 | 전 레벨 템포 상승 |
- 하지 말 것: move.baseShift/accelShift 변경(사람 조작 속도도 바뀜), 사람 쪽 전환에 영향을 주는 값을 CPU 밸런스와 혼동.

### B. 코드 변경 필요
1. **CPU 대시**(효과 최대): ai.js 에서 공 추격/복귀 시 거리가 임계(예: >60px)면 대시 진입. 현재 대시 진입이 match.js 더블탭 분기(사람만)에만 있으므로 AI 용 경로(예: `bits` 에 가상 더블탭 또는 `p.aiDash` 플래그로 `p.st = ST.DASH`)가 필요. 영향: 줍기 이동 시간 약 1/3~1/4(0.75→3.0px/f, 가속 `spd<<9`/f). 결정론·리플레이 영향 없음(엔진 내부).
2. **굴러가는 공 선제 전환(사람 쪽)**: LOOSE 이고 이동 중이라도 공의 최종 정지 예상 지점(마찰 0.125px/f²로 계산, 속도·방향 기준)이 내 외야 구역이면 즉시 외야 선수로 전환. 또는 최소한 공 중심이 외야 구역에 들어가고 속도가 임계 이하(예: <1.0px/f)일 때 전환. 정지 대기 30f 와 4번째 분기(내야 선수로 엉뚱한 전환)를 같이 정리해야 깜빡임이 없다. 원작 이탈.
3. **외야 CPU 추격**: 공이 자기 구역에 정지 시 외야 CPU 가 공까지 걸어가 줍기(현재 한 축 정렬만, 12px 이내여야 습득).
4. CPU 추격 시작 조건 완화: `slow(<1.5px/f)` 대신 예상 정지 지점으로 선행 이동.

### C. 밸런스 영향 예상
- 전환 개선(A tickFrames, B-2): 사람에게 유리, 캠페인 시뮬(봇 vs CPU)에는 무반영. 실플레이 승률은 소폭 상승 가능(줍기 빠름) — 초반 목표 ~80% 쪽은 유리, 보스 25~29% 쪽은 약간 쉬워질 수 있어 모니터링.
- CPU 대시/외야 추격(B-1, B-3), holdDelay·trigShift 상향: CPU 소유권 회복이 빨라져 **사람(및 봇) 승률 하락**. 방향 확실, 크기 미측정. 완화: 초반 레벨1(k0~2)은 holdDelayAdd/blunder 유지, 대시는 레벨2 이상만(레벨별 플래그 `dashDist` 추가) 처럼 레벨 의존으로 도입.
- 참고용 기준선(현 코드, campaign_sim seeds=20 botLevel=2, 95%CI 매우 넓음 ±20%p): 승률 k0~14 = 45,45,25,30,30,30,10,35,30,55,35,10,30,20,5 %. 봇은 필살기를 안 쓰고 사람과 다르므로 절대값이 아니라 **수정 전후 차이**로만 해석(HANDOFF 의 "초반 ~80%, 보스 25~29%"는 실플레이 기준 목표이며 이 시뮬 값과 직접 비교 불가).

## 5. 재측정 방법
1. 기준선: `node tools/campaign_sim.mjs 60 2 - 0 14`(seeds 60 이상, 약 6분) — 수정 전 결과 저장. (이번 20시드 값은 CI 가 넓어 판정용 부적합)
2. CPU 파라미터/대시 변경 후 동일 명령 재실행, k 별 승률 차이를 Wilson CI 로 비교. 초반(k0~2)·보스(k14) 변화 우선 확인. `BOT` 값은 스크립트에 고정이라 CPU 레벨 변경의 영향만 분리된다.
3. 전환·줍기 지연: 이 문서의 정지 배치 측정을 tools 스크립트로 만들어(사람 좌석 humans=[true,false], 공 정지 배치 후 ctrl 변경 f 기록) 전/후 비교. 목표 예: 외야 진입→전환 <= 15f(정지 직후 기준).
4. 최종은 하플레이(실브라우저) 15경기 체감 + 사람 대 CPU 승률 확인(시뮬로 사람 전환 경로는 검증 불가).
5. 한계: 원작 CPU 대시 조건·추격 시작 규칙(0x70/0x74 두뇌)은 이번에 미해독. 필요하면 analysis/scripts 로 0x70 두뇌 분기 추가 해독 후 대시 임계 확정(확인 필요).
6. 이번 측정 중 match.js 가 다른 작업자에 의해 수정 중이었다 → 위 수치는 작성 시점 코드 기준, 수정 반영 후 재확인 권장.

## 6. 구현 요약
- 사람 외야 선행 전환: `match.predictRest()`(마찰·바운스·벽·정지 보정 `settledPos` 복제, 난수 없음, 프레임 캐시)로 예상 정지 구역을 구해 `autoSwitch` 가 정지 전에 전환. 그 구역 외야 선수가 이미 조작 중이면 내야 최근접 재전환 안 함(깜빡임 제거). 예측 검증: 40 시나리오(바운스·벽 포함) 예상 정지점 = 실제 정지점 오차 0.5px 이내 40/40. `ctrlSwitch.tickFrames` 30 -> 12(원작 30 은 rules.json _note 보존).
- CPU 대시: `ai.js chaseMove` 가 `p.aiDash` 요청, `match.updatePlayer` 가 레벨 플래그(`cpu.levels.N.dash`)가 켜진 사이드만 DASH 진입. 제동거리 안에서는 입력을 떼어 오버슛 방지. 레벨1은 꺼짐(캠페인 k0~2 유지). 속도 상한 = min(레벨 dashMaxPx, `cpu.dashCapPx` 3.5).
- 외야 CPU: 예상 정지 지점이 자기 구역이거나 자기 띠에서 직각 거리 `outReach`(L2 24 / L3 28px) 이내(코트 안쪽 포함)면 띠 안에서 접근, 줍기 반경도 `outReach`. L1 은 기존.
- 포메이션 `no_receiver` 수정: 4명 남아 전원 내야 슬롯이면 순환표(0->4->10->7->0)가 생존자에 닿지 못해 취소되던 문제 -> 표로 못 찾으면 슬롯 번호 순 다음 생존자 폴백. 재현: 25팀 x 6조합 중 9건 취소(패스 0~1회 후) -> 수정 후 150건 0건.
- CPU 방어 캐치 보정: `catch256`(캐치 행동 확률 보정), `catchShift`(캐치 버튼 시점, trigShift 와 분리).
- 변경 파일: server/engine/match.js, ai.js, server/data/rules.json, test/engine.test.js(+4, tickFrames 단언 30->12), docs/PROTOCOL.md.
