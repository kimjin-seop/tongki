## 2. 새로 확정한 원작 규칙 (공·충돌)

### 2-1. 캐치 방향 판정의 실제 입력
- 공의 방향 비트(공 $3 bit0/bit1)는 **던진 선수의 방향이 아니라 공 속도의 부호**다: 0xA85C 가 공이 움직이는 모든 핸들러(투구·패스·필살기 0xA728, 바운스 0xA5C8)에서 매 프레임 `vx<0 → bit0`, `vy<0 → bit1` 로 갱신(0 인 축은 유지). [판독] (문서 24 의 "던진 선수의 0x78A0 방향 비트"는 오독. 엔진 필드 b.dl/b.db → b.d0/b.d1)
- 주축은 공 $72(마지막 **투구** 발사 각도 플래그) bit2. 패스(0x72AE~)는 $70/$72 를 쓰지 않으므로 패스 공의 주축·넉백 각도는 마지막 투구 값이 남는다. [판독]
- 0x847C 피격 조건은 `공 $3 & 0xC0 != 0`: 투구(bit6)뿐 아니라 **패스(bit7)도 상대에게 닿으면 피격**(위력 $1A=3 → 데미지 max(0, 3−방어), 넉백 0x851C). [판독]
- 캐치 자세(0x7350)에서 패스 공을 잡으면 밀림 없음(0x7408 이 bit6 을 본다), 받아치기 창 0(0x8CE2). [판독]
- 피격·캐치 판정은 공이 아니라 **각 선수 핸들러가 선수 번호 순으로** 한다 → 뒤 번호 선수는 같은 프레임에 바뀐 상태(새 활성 선수 등)를 본다. 엔진: stepPlayers 가 선수 갱신 직후 hitOne 호출. [확인 cpu_def_throw: p7 피격 프레임에 p9 가 활성 타입으로 정지]

### 2-2. 패스 [판독, rules.pass.rom]
- 발사(0x72A0~0x7300): 공 위치는 보유 위치 그대로, 수평 속도 = 속력(s7×16, 8.8) × 대상 방향, `vz = floor((거리/2 × 16) / (속력>>4)) × (중력>>12) << 12`(0x7E02). 타입 0x18, bit7, 위력 3. 대상을 따라가지 않는 포물선(0xA516: 중력 → 이동 → 벽·천장·바닥이면 바운스 공).
- 대상은 수신 대기(타입 0x30, 0x935C): 속도 0, 공 쪽을 한 번 봄. 패스 공이 히트박스 12(64×64, 높이 무시)에 들어오면 지상 패스는 캐치 자세, 공중 패스는 점프(vz = 1.0 + s3<<12, 대시 플래그마다 +1.0). 현재 히트박스가 공과 겹치면 획득(0x945C → 0x744E, 상대 전환 없음).
- 미이식: 패스 대상 선택($E214), 포메이션 패스(종전 유도 패스 유지).

### 2-3. 조작(활성) 선수 전환이 일어나는 곳 [확인/판독]

| **반발 0.5 이상인 바운스마다** | 0xA7B6~0xA7C6 → 0x85CC | 바닥 반발 뒤 새 vz ≥ 0x8000 이면 같은 전환 루틴 | 확인(bound_L f63 전환 시점·대상 일치) |

### 2-4. 그 밖
- 점프볼 점프(타입 0x88)의 히트박스 9 는 착지 뒤 타입 초기화 프레임까지 남는다. 착지 다음 프레임(타입 0x70 초기화 + plan 0)에는 행동이 없고 피격 판정도 없다 → 그 다음 프레임에 히트박스 9 로 맞는다. [확인 ball_launch_tap/hold, cpu_def_throw PASS]
- 착지 시 수평 속도 0 은 컴퓨터형도 같다(0x8D92/0xC7A0 → 0x83DA). [확인 rng_stop_45 p7]
- 캐치 자세로 공을 잡은 프레임의 보유 공 위치는 캐치 애니 손 위치(다음 프레임부터 서기 애니). [확인 rng_roll_180 f72]
- 외야 120프레임 타이머(0x9212)는 공의 마지막 보유자($C71C)의 사이드가 다를 때 센다. 아직 아무도 든 적이 없으면 포인터 0 → ROM 0x52 의 값(0x0200)을 사이드로 읽어 양 팀 외야 모두 센다. [확인 rng_stop_45 f30: 난수 6회]

## 3. 컴퓨터형 두뇌 직역 (rules.cpu.rom, server/engine/ai.js)

### 3-1. 수동 내야 = 타입 0x20, 0x8D02 (사람 편 동료 + 컴퓨터 편 비활성 내야) [확인 ctrl_stop_in, rng_stop_45, cpu_def_throw]
| 서브 | ROM | 내용 |
|---|---|---|
| 0 | 0x8D28 | 초기화: 속도 0, 타이머 60. 매 프레임 공 쪽을 봄(0x8E50), 피격 판정, 대기점 판단(0x8EDE), 투구 공(bit6, **편 구분 없음**)이 히트박스 12 에 들어오면 웅크림(0x8E82), 상대 패스 공(높이 ≤48)이 히트박스 12 에 들어오면 캐치 자세(0x90A6, 타이머는 남은 값 그대로) |
| 8 | 0x8D98 | 대기점으로 빠른 이동((s2×16+0x300)/256 px/f). 영역 클램프·피격 판정 없음. ±32 안이면 서브 0x10 |
| 0x10 | 0x8DD6 | 초기화: 타이머 60. 걷기 속력으로 이동, 클램프·피격 판정 없음, 0x8EDE, ±4 안이면 서브0 |
| 0x14 | 0x8E0C | 패스 공이 사라지면 서브 0x10, 아니면 공용 캐치 자세(0x730A) |
| 0x18 | 0x8E24 | 웅크림 30프레임(피격 판정 있음) |
- 대기점 판단 0x8EDE: 양 사이드의 공 구역이 직전 값과 같으면 타이머−1, 0 이면 60 으로 되돌리고 난수 1회(결과 bit3 = 0 이면 그대로). 구역이 바뀌었거나 bit3 = 1 이면: 상대 사이드가 공을 가졌으면 0x8F52(상대 기준 공 구역의 8점 표), 아니면 공의 마지막 보유자가 내야(슬롯 ≤3)일 때만 0x8FBE(구역 0 표)로 새 대기점 → 서브8.
- 대기점 선택: 난수 1회, 새 시드 하위 3비트 번호부터 "지금 내 목표와 같은 점"·"같은 편 내야 다른 선수의 목표와 같은 점"(0x9012)을 건너뛰며 번호를 1씩 내린다. 표 0x9E92~0x9F91: **좌석1 표는 좌석0 의 좌우 반전이 아니다**(구역 0 의 순서가 다름) → 종전 `512-x` 반전 표를 실제 표로 교체.
- 그래서 원작의 사람 편 동료는 공이 멈춘 직후 30프레임 동안 서 있고, 상대가 공을 잡거나 구역이 바뀔 때만 대기점으로 달린다.

### 3-2. 컴퓨터 활성 내야 = 타입 0x70, 0xBBE8 의 공 없는 plan [확인: plan 0/0x28/0x2C(rng_stop_45, rng_roll_180 f1~f72, cpu_def_throw), 나머지 판독]
| plan | ROM | 내용 |
|---|---|---|
| 0 | 0xBC42 | 공이 내 구역(0xD52C)이면 바운스·정지 공일 때 0x28, 아니면 0x2C. 내 구역이 아니면 상대 활성 선수가 공을 들고 투구 동작 중일 때 방어 결정, 아니면 0x2C. 이 프레임은 이동·피격 판정 없음 |
| 0x28 | 0xC15C | 공으로 **걷기 속력** 이동(0x9E32; 대시 아님). 공이 높이 ≥24 이고 내 히트박스와 겹치면 선다. 이동 뒤 공에 닿으면 캐치 자세/줍기(0x77D4) |
| 0x2C | 0xC22C | 대기점 선택(0x8F52) → 빠른 이동(±32) → 걷기(±4) → 0x30. 매 프레임 상대 투구 동작이면 방어 결정 |
| 0x30 | 0xC2D4 | 제자리, 공 쪽을 봄. 타이머 60 마다 난수 bit3 이면 0x2C, 구역이 바뀌어도 0x2C, 내 구역 바운스·정지 공이면 0x28 |
| 0x34~0x44 | 0xC3B0~0xC5DC | 방어(서기/캐치/웅크림/점프/옆걸음). 결정 = 상대 활성 선수의 투구 동작(서브 0x0C) 중(0xD7CC), 8비트 난수 1회 vs 파라미터 b9..b12(0xD5F0). 서기·캐치 대기는 매 프레임 공 쪽을 보고 피격 판정을 받는다. 웅크림·점프·옆걸음 대기는 초기화 때만 공 쪽을 보고 **피격 판정이 없다**. 투구 공이 히트박스 12(점프는 13)에 들어오면 실행. 옆걸음 = 난수 bit2 로 위/아래 64px(y 48~216) 빠른 이동 |
| 0x48 | 0xC732 | 파라미터 b13+1 프레임 대기 뒤 plan 0(점프 착지·웅크림 끝) |
- 컴퓨터 캐치 자세(0xC86C)는 사람과 같은 판정(0x7392 → 0x8416). 자세 중에는 방향을 바꾸지 않는다.

### 3-3. 강제 회수 = 타입 0x44, 0x9590 [판독 + 단위 테스트]
- 공으로 빠른 이동(영역 클램프·피격 판정 없음), 공이 높이 ≥24 이고 겹치면 대기, 닿으면 캐치 자세/줍기. 공이 담당 구역이 아니게 되거나 누가 들면 끝.
- 획득 뒤 선 밖이면 슬롯 기본 위치로 빠른 이동(±4 → 정수부 맞춤) 뒤 끝. 그동안 사람 입력을 받지 않는다(타입이 사람형이 아님).

## 4. 정지 공 방치 규칙 (rules.stall.rom) [판독 + 단위 테스트]
- 정지(서브4) 첫 프레임에 방치 카운터 $E25E=0. 매 프레임 타이머−1, 0 이면 전환(카운터 증가 없음), 아니면 카운터+1 이고 300(0x12C) 초과 시 서브8 → 서브4 의 311번째 프레임에 서브8, 312번째 프레임에 구역 갱신 + 0x86A6: 사이드마다 공 구역(0 → 내야 4명, 4/7/10 → 그 구역 3명, 13 → 후방 외야 3명)의 최근접 선수를 활성 + 타입 0x44. 구역이 없는 사이드는 내야 최근접으로 보통 전환만. 서브8 이후에는 30프레임 전환이 없다.
- 자작 `settleBall`(정지 위치 보정)·`autoPickup` 은 쓰지 않는다. `stallGuard`(360/720프레임)는 **원작 규칙으로 회수할 선수가 없을 때만** 도는 휴면 안전망으로 남아 있다 [자작]. 1차 구현에서는 그 구역 외야가 아웃된 선수뿐일 때마다 발동했다(CPU 대 CPU 16경기 nudge 67회, 공 정지 비율 11.1%). §8 의 아웃 선수 외야 활동 직역 뒤 실제 발동은 **24경기에서 nudge 0회·give 0회**, 공 정지 비율 2.6%(변경 전 엔진 6.6%), 최장 정지 345프레임.

## 11. 컴퓨터 외야 대기 선수의 정지 — 원작 대조 (2026-11-18, 강화면 round29 지적)

결론: **원작 동작이다.** 원작의 컴퓨터 외야도 경기 시간의 5~7% 만 움직이고 한 자리에 최장 60초(3,589프레임) 서 있다. 외야 대기 핸들러 직역(ai.js outfieldRom)은 고치지 않았다. 대조 중에 난수 시드의 홀짝 차이 1건을 찾아 고쳤다(11-3). 백업 `_backup/engine_before_outfield/`. 3300 서버는 재시작하지 않았다.

### 11-1. ROM 판독 (타입 0x24 = 0x9128 상·하단 띠, 타입 0x28 = 0x92A8 후방. 서브 표가 같고 자리 맞춤만 0x8306 / 0x831E)
| 서브 | ROM | 내용 |
|---|---|---|
| 0 | 0x914E / 0x92CE | 초기화: 속도 0, 타이머 120. 매 프레임 캐치 검사(0x9D8A: 보유 중이 아닌 공이 히트박스 14 에 들어오면 0x77D4 캐치 자세/줍기) → 공 쪽 보기(0x8E50) → 자리 맞춤 → **0x9212** → 패스 대상 지정 대기 검사(0x8EA8). 공을 쫓는 이동·방황 코드는 없다 |
| 0x0C | 0x91C6 / 0x9346 | 지정 대기: 우리 편이 공을 들었고 내가 패스 대상($E214)인 동안 제자리(0x8EC2) |
| 0x10 | 0x91EE (두 타입 공용) | 대기점($60/$62)으로 걷기 속력(0x9E2A) 이동, ±4 안이면(0x6FEE) 서브 0. 캐치 검사 없음 |
| 0x14 | 0x730A | 공용 캐치 자세 |
- **0x9212 (움직이는 유일한 계기)**: 공의 마지막 보유자($C71C)의 사이드가 내 사이드와 **다를 때만** 타이머−1. 0 이 되면 120 으로 되돌리고 난수 1회, 결과 bit3 = 1 이면 0x9248 로 슬롯별 3점 표(0x9FFA / 0xA066)에서 새 자리 → 서브 0x10. 우리 편이 공을 들었거나 마지막으로 만진 동안은 타이머가 멈춘다 = 그동안 외야 대기 선수는 절대 걷지 않는다.
- 그 밖에 외야가 움직이는 경우는 대기 핸들러가 아니다: 활성 외야(타입 0x74 plan 0x1C 등, §9-3), 강제 회수(0x44), 포메이션 집합(0x7C), 아웃 교체 이동(0x4C).
- **bit3 은 사실상 난수가 아니다 [판독 + 확인]**: 난수 루틴 0x14EA 는 시드×41 을 만들고 d1 하위 워드 = 그 곱의 하위 워드다. 시드를 쓰는 곳은 VBlank 의 `addq.l #2`(0x928)와 이 루틴 둘뿐이라 시드는 언제나 짝수이고(원작 트레이스 67개 8,160프레임에서 홀수 0), 짝수 n 에서는 41n ≡ 9n ≡ n (mod 16) 이라 **난수를 몇 번 불러도 하위 4비트가 그대로**다. 즉 bit3 은 프레임마다 +2 되는 카운터의 비트(8프레임 주기 중 4프레임 = 1)이고, 외야 타이머 120 은 8 의 배수라 **타이머가 연속으로 도는 동안에는 만료 때마다 같은 결과**가 나온다(계속 안 움직이거나, 만료 때마다 움직이거나). 위상은 타이머가 멈추는 구간(우리 편 보유)·걷는 시간·지정 대기로만 바뀐다. 수동 내야 대기점 판단(0x8EDE, 타이머 60)·plan 0x30 의 bit3 도 같은 구조.
  - 확인: `out_wait_400`·`out_wait_seed`(사람이 공을 든 채 400프레임) — 원작 외야 3명이 f30/f150/f270/f390 에 난수를 부르고도 400프레임 동안 한 번도 움직이지 않는다(호출 주소 0x922E, 3명 x 4회 = 12회 모두 bit3 = 0. `oracle_rngwho.py out_wait_400 1 400`). `out_wait_move`(시드 하위 바이트만 0xA8 → 0xA0 으로 위상 반전) — 같은 프레임에 3명 모두 걷기 시작(p11 f31~65, p12 f31~70·f191~228·f349~386, p13 f31~73). 세 시나리오 모두 우리 엔진과 난수·외야 3명 좌표·속도·라벨이 400프레임 전부 일치(PASS).

### 11-3. 수정 1건: 난수 시드 짝수 고정 (match.js 생성자)
- 원인: 서버는 32비트 무작위 시드로 경기를 만든다(roomGame.js) → 절반이 홀수. 홀수 시드에서는 난수를 부를 때마다 하위 4비트의 bit3 이 뒤집혀(9n ≡ n+8) bit3 판정이 '부른 횟수의 홀짝'이 된다. 원작에 없는 상태.
- 수정: `new Rng(seed & 0xFFFFFFFE)`. `m.seed`(기록·스냅샷)는 받은 값 그대로. 짝수 시드 경기는 결과가 전과 같고, 홀수 시드 경기는 (시드−1) 경기와 같아진다.
- **동작이 달라진 점(보고 필요)**: 홀수 시드로 저장된 과거 경기를 같은 시드로 다시 돌리면 전과 다른 경기가 나온다. 홀수 시드 경기에서 외야 대기 선수·수동 내야의 자리 이동 빈도가 원작 구조(위상 고정)로 바뀐다.
- 검증: npm test 44개 통과(1개 추가: 홀수 시드로 시작해도 1,500프레임 내내 시드 짝수), 차분 하네스 **67개 중 66 PASS**(추가 3개 PASS, 남은 FAIL 은 rng_roll_180 그대로), 컴퓨터 대 컴퓨터 48경기 미종료 0(전멸 24·시간 종료 18·서든데스 6, 평균 16,944프레임), 100경기 미종료 0·NaN 0·장외 0(x 16.0~496.0, y 16.0~248.0)·공 최장 정지 340프레임·발사 없는 최장 구간 832프레임·안전망(stall_nudge/give/t44) 0회.

### 11-4. 미해결
1. 원작 실측은 play0 한 팀 조합·시드 3개뿐이다. 사람 대 컴퓨터 경기의 원작 장시간 트레이스는 재지 않았다(사람 입력열이 필요). 외야 대기 핸들러는 사람 편·컴퓨터 편이 같은 코드(타입 0x24/0x28)이고 `out_wait_*` 는 사람이 공을 든 상황이다.
2. 원작의 초기 시드(전원 켠 직후 $E620)가 0 이라는 것은 쓰는 코드가 둘뿐이라는 판독과 트레이스의 짝수 관측에 기댄다. RAM 초기화 코드를 직접 확인하지는 않았다.
3. 화면에서 외야가 "멈춰 보이는" 인상을 줄이려면(제자리 애니 등) 원작 애니 프레임 카운터($10/$11, §9-7 1번) 이식이 먼저다. 자작 방황은 넣지 않았다.
