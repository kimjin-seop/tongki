## 1. 결론 요약과 권고

### 1.1 한 줄 결론
**권고 = 옵션 A(지연 기반 락스텝 + 서버 재생 판정)를 「P2P 우선 + 서버 그림자 입력 수신」 하이브리드로.** 엔진은 브라우저에서 수정 없이 돌고 Node 와 지문이 완전히 같았다(§2.1, Edge 157 / Node 25, 4경기 모두 일치). 서버 재생 비용은 경기당 CPU 약 0.3~0.6초라 판정 비용은 문제가 아니다.

### 1.2 왜 하이브리드인가
- 상대 입력 → 내 시뮬레이션의 **임계 경로만 P2P**(WebRTC DataChannel)로 보낸다.
- 각 클라이언트는 **자기 입력을 서버에도 묶어서 올린다**(기존 WebSocket, 250ms 단위, 지연에 민감하지 않음). 서버는 이 기록과 상대가 보증한 입력 블록(§5.3 MAC)으로 경기를 **worker 에서 재생해 결과를 확정**한다.
- 이 그림자 기록 덕분에 (1) 열혈의 약점(서버가 거짓 보고자를 못 가림, nekketsu `analysis/22` 109행)이 풀리고, (2) P2P 가 끊겨도 **같은 경기 안에서 서버 중계로 경로를 바꿀 수 있고**(§4.5), (3) 재접속은 「시드 + 입력 기록 빨리 감기」로 끝난다(§2.4).
- 현행 서버 권위 방식(옵션 D)은 컴퓨터 대전·스토리·특훈·리그·불꽃 도전에 그대로 남긴다. P2P 대상은 `isHumanVsHuman` 계열(사람 두 좌석) 경기만.

### 1.3 기대 효과와 냉정한 한계
- **서버 대역폭이 가장 큰 이득.** 현행은 60Hz 스냅샷(평균 708바이트 [실측]) × 2좌석 = 경기당 송신 약 85KB/s(약 0.68Mbps). 동시 100판이면 약 68Mbps. P2P 후 서버 송신은 경기당 1KB/s 미만(지문·확인 응답) [추정].
- **체감 지연 이득은 서버 위치에 따라 다르다.** 현행 체감 = 서버 왕복(RTT) + 보간 1틱(`snaps.js DELAY_TICKS=1`) + 틱 대기 ≈ RTT + 약 25ms. 락스텝 체감 = 입력 지연 D 프레임(양쪽 같음). 같은 도시 P2P 로 D=2(33ms)면, 서버가 국내에 있을 때 이득은 10~30ms 수준 [추정]. 서버가 멀면 이득이 커진다. 1단계 실측(§7)으로 확인한다.
- **새로 생기는 위험**: 상대 IP 노출(§5.4), 락스텝 「미리 보기」 부정(§5.6), 엔진 코드가 클라이언트로 나가 봇 제작이 쉬워짐(§5.7), 브라우저 엔진 간 부동소수 차(§2.2).

### 2.2 부동소수·난수 점검 [코드 + 실측]
- 난수: 원작 RNG(`rng.js`) 정수 연산(`Math.imul`, `>>>`)만. `Math.random`·`Date` 는 엔진에 없다(서버가 정한 시드만 사용, `roomGame.js:30`). → 엔진 간 차이 없음.
- 위치·속도: 16.16 고정소수 정수가 기본. 다만 부동소수가 남아 있는 곳이 있다:
  - `Math.hypot`: `match.js` 271·418·483·1073·1132·1389·1391·1639·1643·1686·1854·2133·2143·2210행, `ai.js` 25·26·999행. 대부분 거리 비교·`Math.ceil`·나눗셈 입력.
  - `Math.sqrt`: `match.js:1981`(캐치 밀림 속도, `Math.round` 로 정수화).
  - `Math.cos/sin`: `special.js:49`(루프 필살, ×256 후 `Math.round` 정수화).
  - 내부 상태에 비정수로 남는 필드는 입장 행진의 `p.en.spd/ex/ey` 3개뿐이었다 [실측, 11,000프레임 표본].
- 위험 판단: `+ - * /`·`Math.sqrt` 는 IEEE 754 상 정확 반올림이라 엔진 간 같다. `Math.hypot`·`sin`·`cos` 는 ECMAScript 가 「구현 근사」를 허용한다 [사양, ECMA-262 Math 함수 절] → V8 과 SpiderMonkey·JavaScriptCore 가 마지막 비트에서 다를 수 있다. 정수화·비교 경계에 정확히 걸릴 때만 결과가 갈라지므로 드물지만, 갈라지면 그 뒤 전체가 어긋난다(디싱크).
- 대응(1단계): (1) Firefox·iOS Safari 실기기에서 §2.1 스크립트를 돌린다(강화면). (2) 불일치가 나오거나 예방 차원이라면 위 `hypot/sin/cos` 를 정수 표·정수 제곱근(`isqrt`)·제곱 거리 비교로 바꾼다 — 단 원작 직역 차분 하네스(`analysis/22_diff_status.md`, 64개 중 63 PASS)를 다시 통과해야 한다(입장 행진·필살 추적은 [자작] 구간이라 영향 범위가 작다). (3) 엔진에 `Math.hypot` 등 사용을 막는 정적 검사 시험을 추가한다.

### 2.3 같은 엔진을 양쪽이 돌릴 때: 입력 지연·60Hz 동기
- 입력 의미 보존: 현행 서버는 틱 사이 짧은 탭을 래치한다(`roomGame.js:89`, 새로 눌린 비트 1틱 보장). 락스텝에서는 **클라이언트가 자기 틱마다 `cur | latch` 를 샘플링해 프레임 f 의 입력으로 확정**하면 같은 의미가 된다. 엣지·더블탭 대시 판정은 엔진 안이라 그대로.
- 입력 지연 D: 로컬 프레임 f 에서 샘플한 입력을 프레임 f+D 에 적용. `D = ceil((단방향 지연 + 지터 여유) / 16.67ms)`, 최소 2, 최대 6 권고. 시작 전에 P2P 핑 3~5회로 정하고(열혈 방식, `server_online.js` 「핑 3회 → 지연 프레임 결정」) 경기 중엔 고정(바꾸면 체감이 흔들린다).
- 60Hz 고정 틱: 브라우저 `requestAnimationFrame` 은 60/120/144Hz 로 들쭉날쭉하므로 렌더와 분리된 누산기(accumulator) 루프로 1/60초마다 틱. 따라잡기 상한 4틱(현행 `MAX_CATCHUP`).
- 시계 드리프트: 양쪽 시계 속도가 조금 달라도 락스텝은 「상대 입력이 없으면 기다린다」로 스스로 맞춰진다. 앞서 가는 쪽이 자주 멈추지 않게, 상대 입력 도착 여유(frame advantage)를 패킷에 실어 앞선 쪽이 수 프레임에 걸쳐 1프레임씩 늦추는 보정을 넣는다 [GGPO 류 일반 기법].
- 패킷 손실: 순서 없음·재전송 없음 채널에 **최근 미확인 프레임 최대 8개를 매 패킷에 중복 실어** 보낸다. 1프레임 1바이트라 중복 비용이 거의 없다.
- 멈춤: 상대 입력이 D 프레임 안에 안 오면 화면을 멈춘다(`SnapBuffer.frozen` 재사용). 200ms 이상이면 서버 중계로 경로 전환 시도(§4.5), 현행 `game_pause` UI·유예(`GRACE_MS`, `maxPauseMs` 90초, `maxDisconnects` 5)를 그대로 쓴다.

### 2.4 현재 스냅샷·보간 렌더를 락스텝에서 쓰는 법
- 클라이언트 러너가 매 틱 `m.tick(bits)` 후 `m.snapshot(true)` 를 만들어 기존 `SnapBuffer.push()` 에 넣는다. **렌더·HUD·효과음·컷인 코드는 스냅샷·이벤트 형식이 같으므로 수정 없이 동작**한다(스냅샷은 엔진이 만들기 때문). 직렬화 비용 13µs/스냅 [실측].
- `game_start` 페이로드도 로컬 `m.info()` 로 만들 수 있지만, **경기 설정(시드·팀·스테이지·규칙·evade·flame 옵션)은 서버만 정하고 내려준다**(클라이언트가 바꾸면 지문이 어긋나 적발, 서버 재생은 서버 값으로 돈다).
- 보간: 로컬에서 60Hz 로 스냅이 생기므로 `DELAY_TICKS` 는 0~1 로 충분. 멈춤 중엔 마지막 스냅 유지.
- 재접속: 서버가 `{시드, 설정, 지금까지의 확정 입력}` 를 보내면 클라이언트가 화면 없이 빨리 감는다. 18,000프레임(5분) 빨리 감기 = 약 0.3~0.5초 [실측 µs/틱 × 프레임]. 엔진 상태 직렬화 API 없이도 된다.

## 3. 서버 판정(결과 확정)

### 3.1 흐름
1. 매칭·방 시작: 서버가 `matchId`, 시드, 경기 설정, 엔진/데이터 해시, 좌석별 비밀키 `K_s`(32바이트 난수, 그 좌석에게만), 짝 키 `K_pair`(두 좌석 공통)를 WSS 로 내려준다.
2. 경기 중: 각 좌석은 (a) 자기 입력을 250ms 묶음으로 서버에 올리고(`p2p_in{f0, bits}`, RLE+base64, 열혈 `encodePads` 형식 재사용 가능), (b) 30프레임마다 상태 지문을 서버와 상대에게 보내고(`p2p_hash{f,h}`), (c) 상대에게서 받은 **서명된 입력 블록(§5.3)을 증거로 함께 올린다**.
3. 종료: 각 좌석이 `p2p_result{f, winner, reason, h}` 를 보낸다. 서버는 좌석별 정본 입력(§3.2)으로 worker 재생(열혈 `replay_save.js runInWorker` 패턴: 별도 스레드, `resourceLimits`, 시간 제한) → 엔진 `result`·`endF`·`phase` 로 결과를 만든 뒤, **기존 `RoomGame.finish()` 와 같은 경로**(결과 레코드·`onRanked`·`onPvp`)로 반영한다. `wentGo` 는 재생 엔진의 `phase` 로 판정.
4. 클라이언트 보고(`p2p_result`)는 화면 전환용 참고값일 뿐 **반영 근거가 아니다**.

### 3.2 정본 입력 규칙
- 좌석 s 의 프레임 f 입력 = 서버가 s 에게서 직접 받은 값(WSS 세션 인증). 빠진 구간은 상대가 제출한 「s 의 `K_s` 서명 블록」으로 채운다.
- 같은 (s, f) 에 서로 다른 값이 `K_s` 인증으로 둘 이상 나오면 = **s 가 상대와 서버에 다른 입력을 보낸 것(이중 입력)** → s 기권패(래더) / 무효 + 기록(일반 방). 대칭 키지만 `K_s` 는 s 와 서버만 알므로 상대가 위조할 수 없다.
- 어느 경로로도 입력이 없는 프레임 = 그 좌석이 입력을 끊은 것 → §5.5 끊김·지연 규칙.

### 3.3 DISPUTE(불일치) 처리
| 상황 | 판정 |
|---|---|
| 두 좌석 지문 = 서버 재생 지문 | 정상. 재생 결과 반영 |
| 한 좌석 지문만 재생과 다름 | 재생 결과 반영. 다른 쪽에 `desync` 기록(변조 클라이언트·버그 신호). 반복 시 관리 확인 대상 |
| 두 좌석 지문이 서로 같은데 재생과 다름 | 서버/엔진 버전 문제 가능성 → **무효(VOID)** + 경보 로그(정직한 두 사람을 벌하지 않는다) |
| 이중 입력 증거 | 증거 낸 쪽 승(래더 기권 처리), 기록 |
| 한쪽이 결과·입력을 안 냄 | 서버 기록이 있는 데까지 재생. 끝까지 있으면 그 결과, 아니면 §5.5 |
| 재생 시간 초과·엔진 예외 | 무효 + 경보(벌점 없음) |
- 경기 중에도 30프레임 지문을 비교해 **불일치 즉시** 양쪽에 알리고(열혈 `desync{f,h}` 와 같음) 서버가 그 지점까지 재생해 정본 상태를 확인할 수 있다. 일반 방은 경고 후 서버 중계 권위(옵션 D)로 넘기는 복구도 가능(§4.5).

### 3.4 재생 비용 [실측 기반 추정]
- 순수 틱 비용 16~42µs/프레임(Node, 4경기). 5분 경기 + 서든데스 ≈ 11k~19k 프레임 → **경기당 0.3~0.6초**. 최악 상한: 시간제 `hardCapFrames` 54,000(15분), 무제한 `unlimitedCapFrames` 108,000(30분) [코드 rules.json] → 2.3~4.5초.
- 동시 판 수 기준: 평균 경기 약 4~5분, CPU 0.5초라 하면 코어 1개가 5분에 약 600판 재생 → **동시 진행 약 600판까지 코어 1개**. worker 생성 비용(모듈·JSON 로드 수십 ms [추정])을 피하려고 worker 풀(2~4개) + 대기열 상한 권고.
- 비교: 현행 서버 권위는 판마다 60Hz 틱 + 스냅샷 직렬화(13µs×60) ≈ 판당 코어 0.3% 수준이라 CPU 차이는 작다. 비용 이득은 대역폭(§1.3).

### 3.5 적용 범위
- **래더(랭크) 경기: 서버 재생 결과만 반영(필수).** 실시간 경과 하한(열혈 `TOO_FAST`: 프레임 × 16.7ms × 0.9 미만이면 미반영)도 함께 — 공모한 두 계정이 경기를 빨리 감아 만들어 내는 것을 막는다. 시각은 서버의 입력 수신 시각으로 잰다.
- 일반 방: 「선택」이지만 **재생 기본 켬 권고**. 재생이 싸고, 일반 방도 사람끼리 전적(`pvp_records`, PROTOCOL §11.1)에 오르기 때문. 재생을 끄는 설정은 두지 않는 것을 권고(분기 줄임).

## 4. P2P 연결

### 4.1 전송: WebRTC DataChannel [사양 RFC 8831·8832, W3C WebRTC 1.0]
- 채널 2개:
  - `in`: `ordered:false, maxRetransmits:0`(순서 없음·재전송 없음). 입력·확인 응답·여유값. 중복 실어 손실 보완(§2.3). 순서 있는 채널은 손실 한 번에 뒤 패킷이 줄줄이 막힌다(SCTP 순서 보장).
  - `ctl`: `ordered:true`(기본 신뢰 채널). 인사(hello)·지문·서명 블록·일시정지·결과.
- 바이너리(ArrayBuffer) 권고. 입력 패킷 예: `[u8 종류][u16 seq][u32 첫 프레임][u8 개수][개수 × u8 비트][u32 받은 마지막 프레임][i8 여유]` ≈ 12~20바이트.
- 경기마다 새 `RTCPeerConnection`(DTLS 세션도 경기마다 새로) → 다른 경기 패킷 재사용 불가.

### 4.2 시그널링: 기존 WebSocket 로비 재사용
- 새 메시지(서버는 내용 검사 후 같은 방 상대에게만 전달): `rtc_offer{sdp}`, `rtc_answer{sdp}`, `rtc_ice{cand}`, `rtc_state{path:'p2p'|'turn'|'relay'}`. 방 좌석 두 사람 사이에서만, 경기 시작 직전 한정, 크기·빈도 상한(현행 4KB·초당 240개 안, SDP 가 4KB 를 넘을 수 있어 `maxPayload` 조정 또는 분할 필요 [추정]).
- 서버는 SDP 의 `a=fingerprint` 를 뽑아 좌석별로 기록한다(§5.2).
- 운영은 반드시 `wss://`(TLS). 클라이언트는 이미 https 면 wss 로 붙는다(`public/js/net.js:13`). 평문 ws 위에서는 시그널링 변조로 중간자 공격이 가능하므로 **P2P 기능은 https/wss 에서만 켠다**.

### 4.3 STUN/TURN 필요성·NAT 실패율·비용
- STUN 만으로 직접 연결이 안 되는 경우(대칭 NAT, 기업망 UDP 차단, 이동통신 CGNAT 일부) 가 있다. 공개 자료에서 흔히 인용되는 「TURN 이 필요한 비율」은 대략 10~20% 범위 [추정, 원문 미확인]. 이동통신 비중이 높으면 더 높을 수 있다.
- TURN [사양 RFC 8656, STUN RFC 8489, ICE RFC 8445]: coturn 자체 운영 권고. 자격 증명은 서버가 경기마다 발급하는 **시간 제한 HMAC 자격 증명**(coturn `use-auth-secret`, 「TURN REST API」 초안 방식) — 고정 비밀번호를 클라이언트에 넣지 않는다.
- TURN 중계 비용 [추정]: 입력 패킷 60개/초 × (페이로드 20 + DTLS/SCTP/UDP/IP 머리 약 80) ≈ 6KB/s 한 방향. 중계는 받고 보내므로 경기당 약 24KB/s, 5분 ≈ 7MB. 클라우드 송신 단가를 GB 당 0.1달러로 잡아도 판당 0.1센트 미만. 패킷을 30Hz(2프레임 묶음)로 줄이면 절반. **현행 스냅샷 송신(5분 ≈ 25MB)보다 작다.**
- 실패 시 폴백: TURN 도 실패하면 **서버 WebSocket 중계 락스텝**(열혈과 같은 구조: 서버가 엔진을 돌리지 않고 입력만 전달). 클라이언트 코드 경로가 같아서 별도 모드가 아니다. 최후 폴백은 현행 서버 권위(옵션 D) — 서버가 그림자 입력으로 지금까지를 빨리 감아 넘겨받을 수 있다(§4.5).

### 4.4 시도 순서
`host/srflx 직접` → `TURN(UDP→TCP/TLS 443)` → `WS 중계`. ICE 연결 제한 시간 약 5초 [추정] 안에 안 되면 WS 중계로 시작하고, 경기 중 백그라운드로 직접 경로가 잡히면 옮긴다.

### 4.5 한 경기 중 경로 전환
- 입력은 프레임 번호로 식별되고 중복 제거되므로 **어느 경로로 오든 먼저 온 것을 쓴다.** 그래서 P2P ↔ TURN ↔ WS 중계 전환은 경기 상태와 무관하게 언제든 가능하다.
- 서버는 그림자 입력을 이미 갖고 있으므로, P2P 가 200ms 이상 조용하면 클라이언트가 `rtc_state{path:'relay'}` 를 보내고 서버가 상대의 그림자 입력을 **묶지 않고 프레임마다** 전달하기 시작한다(평소 250ms 묶음은 중계 모드에서만 1프레임 단위로).
- ICE restart 로 P2P 재수립 후 다시 `p2p` 로.
- 지연 D 는 경로가 바뀌어도 그대로(중계가 느리면 멈칫이 잦아진다 → 일반 방 한정으로 경기 중 D 재협상은 후속 검토).

## 5. 보안·암호화

### 5.1 전송 암호화 [사양 RFC 8827·8826, SCTP over DTLS RFC 8261]
- DataChannel 은 DTLS 로 암호화·무결성 보호된다(평문 모드 없음). TURN 을 거쳐도 TURN 서버는 암호문만 본다(종단 간).
- DTLS 상대 인증은 「SDP 의 `a=fingerprint` 와 상대 인증서 해시 비교」로 이뤄진다. 즉 **신뢰의 뿌리 = 시그널링 경로(우리 서버 + WSS)** 다.

### 5.2 상대 신원 확인·중간자 방지
- 서버 발급 일회용 매칭 토큰: `matchId` + 좌석별 `K_s` + 공통 `K_pair`(경기 시작 때 생성, 경기 끝나면 폐기, 로그에 남기지 않음).
- 연결 직후 `ctl` 채널 인사: `HMAC(K_pair, "tk-hello" ‖ matchId ‖ seat ‖ 내 인증서 지문 ‖ 상대 인증서 지문 ‖ 엔진 해시)`. 상대 지문은 `RTCPeerConnection.getStats()` 의 `certificate` 통계(로컬·원격 인증서 지문)로 읽는다 [사양 W3C webrtc-stats, 브라우저별 지원 1단계 확인]. 맞지 않으면 즉시 끊고 WS 중계로.
- 서버는 두 좌석이 낸 SDP 지문을 기록하고, 각 좌석이 실제로 본 상대 지문(인사 때 보고)을 대조한다 → 시그널링 중 바꿔치기 적발.
- 시그널링 메시지는 같은 방 두 좌석 사이에서만 전달(다른 사람 주입 불가), 경기 시작 단계에서만 받는다.

### 5.3 입력 위조·재전송·순서 바꿈 방지
- 전송 구간: DTLS 가 위조·재전송을 막는다. 애플리케이션 층에서 `seq`·프레임 번호로 중복·순서를 처리하고, 이미 확정된 프레임의 다른 값은 버린 뒤 이중 입력 증거로 보관한다.
- 증거 블록(서버 판정용): 30프레임마다 `{seat, f0, f1, MAC = HMAC-SHA256(K_s, matchId ‖ seat ‖ f0 ‖ f1 ‖ bits[f0..f1])}` 를 상대에게 보낸다(16바이트로 잘라도 충분). 상대는 검증할 수 없지만(키 없음) 서버에 그대로 제출 → 서버가 검증. Web Crypto `crypto.subtle` HMAC 는 비동기라 블록 단위(초당 2회)면 비용 무시 가능.
- 서버로 올리는 그림자 입력은 WSS 세션 인증으로 충분(별도 MAC 불필요).

### 5.4 IP 노출(직접 P2P 의 고유 위험)
- 직접 연결이면 상대가 내 공인 IP 를 안다(ICE srflx 후보, `getStats`). 위험: 표적 DDoS, 대략적 위치 노출. 내부 IP 는 브라우저가 mDNS 이름으로 가린다(권한 없는 페이지 기준) [사양 RFC 8828 + mDNS ICE 초안, 원문 미확인].
- 대책:
  - **「IP 숨기기」 개인 설정**: 켜면 그 사람 쪽은 `iceTransportPolicy:'relay'`(TURN 후보만) → 상대에게는 TURN 서버 주소만 보인다. 서버도 그 사람이 보내는 후보 중 relay 가 아닌 것을 시그널링에서 걸러 낸다(방어 겹치기).
  - **래더(모르는 상대와 무작위 매칭)는 TURN 강제 기본**(§8 결정 1). 일반 방은 직접 P2P 기본 + 설정으로 숨김.
  - 직접 연결 상대 정보는 화면에 IP 를 표시하지 않는다(개발자 도구로는 보일 수 있음 — 막을 수 없다).
- 개인정보 처리 [법무 비차단 메모, 공개 전 정리]: (1) 서버가 이미 접속 IP 를 처리(`server/index.js clientIp`, 연결 수 제한)하고 있으며 P2P 는 「상대방 이용자에게 IP 가 전달될 수 있음」을 처리방침에 추가해야 한다. (2) TURN 서버 로그(접속 IP·시각)의 보관 기간을 정한다(예: 7일) [추정 권고]. (3) 그림자 입력 기록은 경기 판정·분쟁 목적, 보관 기간 명시.

### 5.5 기권·고의 지연·끊김
- 입력 공급 책임: 상대가 멈춰 있을 때 「누구 입력이 없어서 멈췄는가」를 서버가 그림자 입력 도착 상태로 판정(열혈 `blame` 방식). WS 와 P2P 둘 다 끊긴 좌석이 책임.
- 규칙(현행 값 재사용): 끊김 1회당 유예 `GRACE_MS`, 경기당 누적 일시정지 `maxPauseMs`(90초), 끊김 `maxDisconnects`(5회) 초과 = `forfeit_disconnect`. 기권 메시지 = `forfeit_leave`. GO 이전 종료 = 무효(현행 §11.1 그대로).
- 느린 진행(고의 지연): 확정 진행이 실시간의 25% 미만이 10초 이어지면 원인 좌석 멈춤 1회(열혈 `STALL_RATE` 0.25·`STALL_MS` 10초 참고), 3회면 기권.
- 모바일 백그라운드 전환(타이머 정지) = 끊김과 같이 처리(`visibilitychange` 로 상대에게 즉시 알림).

### 5.6 치팅
- **정보 공개 여부 [코드 확인]: 통키는 완전 공개 정보 게임이다.** 현행 스냅샷이 이미 양 팀 전원의 위치·상태·HP·공을 매 틱 보내고(§5.3), 시드도 `game_start.seed` 로 내려간다(`match.js info()`). 맵핵에 해당하는 숨은 정보가 없으므로 락스텝으로 바꿔도 새 정보 유출은 없다(시드로 난수 미래를 아는 것도 현행과 같다).
- 상태 조작(체력·위치 변경): 내 화면만 바뀌고 서버 재생이 진실이라 결과에 영향 없음. 지문 불일치로 기록.
- **락스텝 미리 보기 부정(새 위험, 중간)**: 프레임 f 는 두 입력이 모여야 진행하므로, 부정 클라이언트가 상대의 f 입력을 받은 뒤 자기 f 입력을 정해 보내도 D 가 왕복 지연보다 길면 멈춤 없이 통한다. 이득 = 상대 행동(투구 등)을 화면보다 최대 D 프레임 먼저 알고 캐치·웅크림을 맞추는 것. 대책: (1) D 를 「단방향 + 지터」로 작게 잡아(왕복보다 짧게) 기다리면 자기 입력이 늦어 멈춤이 생기게 하고, 멈춤 책임 좌석을 집계(§5.5), (2) 서버가 그림자 입력 도착 시각으로 좌석별 「입력 선행량」을 기록해 계속 늦게 오는 좌석을 표시, (3) 래더 통계(투구 대비 캐치 반응 프레임 분포) 사후 분석. 완전 차단은 커밋-공개 방식(왕복 1회 추가 지연)뿐이라 비권고.
- 속도 조작·되감기: 락스텝은 느린 쪽에 맞춰 돌고, 서버 재생 + 실시간 하한(§3.5)으로 빨리 감은 가짜 경기를 막는다.
- 공모(승 몰아주기): 아키텍처와 무관, 현행 같은 상대 제한(24시간 3판, §11.1)이 그대로 적용된다.

### 5.7 매크로·입력 조작의 한계
- 키 매크로·자동 입력은 현행과 마찬가지로 막을 수 없다(입력은 결국 클라이언트가 만든다).
- **엔진이 클라이언트로 나가면 봇 제작이 쉬워진다**: 클라이언트가 같은 엔진으로 몇 프레임 앞을 시뮬레이션해 「완벽한 캐치 타이밍」을 찾는 보조 도구가 가능해진다(현행은 엔진 소스를 서빙하지 않는다). 대책은 사후 통계(사람이 낼 수 없는 반응 분포) 정도. 남은 위험으로 공개.
- ROM 유래 표(`romtables.json`·`teams.json` 등)가 공개 경로로 나간다 → 저작권 메모(법무 비차단, 공개 전 정리). 지금도 `public/assets/rom/` 이 서빙되고 있어 성격은 같다.

## 6. 래더·채팅·공지와의 상호작용

### 6.1 래더·랭크(analysis/46, PROTOCOL §11)
- Elo·티어·배치·마스터·시즌·같은 상대 제한·기권 잠금 값은 **바꾸지 않는다**. 바뀌는 것은 「승패 입력의 출처」뿐: 현행 `RoomGame.finish()` 의 `winner/reason/wentGo` → 서버 재생 결과의 같은 값. `lobby.rankedResult`·`pvpResult` 호출 형태 그대로.
- 추가 무효 사유: `REPLAY_FAIL`(재생 실패·시간 초과), `DESYNC_BOTH`(두 좌석 일치·서버만 다름), `TOO_FAST`. 이중 입력 적발은 기권패(`forfeit_cheat` 또는 기존 `forfeit_leave` 재사용 — 1단계 결정, 권고는 새 사유로 구분 기록).
- 결과 확정이 재생만큼(0.3~0.6초 + 대기열) 늦어진다 → `game_end` 뒤 `ranking_result` 가 조금 늦게 온다(화면은 이미 「집계 중」을 표시하면 됨).
- 래더 경로: TURN 강제 권고(§5.4)라 래더의 지연 이득은 「TURN 이 서버와 같은 곳에 있으면 현행과 비슷」하다. 래더의 주 이득은 서버 대역폭과 공정성(양쪽 같은 D).

### 6.2 채팅·공지(analysis/49, PROTOCOL §14)
- **채팅은 P2P 로 옮기지 않는다.** 서버의 정리·욕설 가림·도배 제한·관리자 표시(`admin:true`)가 서버 경유를 전제로 하므로 WebSocket 그대로. 경기 중에도 WS 는 계속 열려 있다(그림자 입력 때문에 어차피 필요).
- 공지(`notice`)도 WS 그대로. 경기 중 화면 표시 동작 변화 없음.
- 주의: 경기 중 WS 가 끊기고 P2P 만 살아 있으면 채팅·공지는 안 오지만 경기는 계속된다. 그림자 입력은 재접속 후 클라이언트가 보관분을 다시 올린다(유예 안에 못 올리면 래더 판정은 상대 증거 블록으로 채움).

## 7. 단계별 구현 계획·인수조건·분배

범위 원칙(전역 규칙): 각 단계 시험은 핵심 동작 1~2개 + 오류 없음 확인. 운영 DB 쓰기 없음. TURN 서버 설치·포트 개방은 운영 인프라 변경이라 사용자 승인 후.

### 1단계: 엔진 브라우저 구동 + 결정론 지문 검증 (PoC 정식화)
- 작업(박백엔, 약 2~3일): `data.js` 를 순수 조립 + Node 로더로 분리, 정적 서버에 엔진·필요 JSON 9개 화이트리스트 마운트(빌드 해시 경로 `/engine/<hash>/`), `Match.digest()`(정본 필드만 정수로 해싱 — PoC 의 `JSON.stringify` 전체 해싱은 필드 순서·상호 참조에 민감해 정식 API 로 대체), 엔진 정적 검사(`Math.hypot/sin/cos/random/Date` 사용 목록 고정), Node 지문 시험 1개(`npm test`), PoC 스크립트를 `tools/` 로 옮김.
- 강화면(약 1일): Edge·Chrome·Firefox·iOS Safari·Android Chrome 실기기에서 지문 페이지 실행, 모바일 µs/틱 측정.
- 인수조건: (1) 4개 시나리오 지문이 Node 와 위 5개 브라우저에서 모두 같다, (2) 모바일 최저 기기에서 틱 평균 1ms 미만, (3) 차분 하네스 결과가 바뀌지 않는다(엔진 수정이 있었다면 63/64 유지).
- 불일치가 나오면: 해당 부동소수 지점을 정수화(박백엔) 후 재측정. 2회 실패 시 「V8 계열만 P2P 허용, 나머지 브라우저는 WS 중계 락스텝」으로 축소 보고.

### 2단계: 일반 방 P2P(락스텝)
- 박백엔(약 4~5일): 시그널링 메시지(`rtc_*`), 경기 설정·키 발급, 그림자 입력 수신·보관, WS 중계 모드, `P2pGame`(RoomGame 과 같은 인터페이스: `setConnected`·`step`·`finish`), 재접속(입력 기록 전송), PROTOCOL §15 신설, 시험 2개(두 가짜 클라이언트 락스텝 결과 = 서버 재생 결과, P2P 끊김 → 중계 전환 후 같은 결과).
- 윤프론(약 6~8일): 고정 틱 러너(`cur|latch` 샘플링, D 지연, 멈춤), WebRTC 연결·채널 2개·바이너리 패킷·중복 전송·경로 전환, `SnapBuffer` 연결(렌더 무수정 확인), 「IP 숨기기」 설정, 연결 경로 작은 표시(설명 문구 최소).
- 강화면(약 2일): 서로 다른 두 기기(PC + 모바일, 다른 망 1회 포함)로 일반 방 경기 끝까지, 끊김·재접속·경로 전환, 스크린샷.
- 정검수(약 1~2일): 시그널링 경로 보안(방 밖 주입·크기·빈도), 키 수명, IP 숨김 우회 여부.
- 인수조건: (1) 일반 방 사람 대 사람 경기가 P2P 로 끝까지 진행되고 두 화면의 결과·지문이 같다, (2) P2P 를 강제로 끊어도 경기가 WS 중계로 이어진다, (3) 「IP 숨기기」 켠 쪽의 비-relay 후보가 상대에게 전달되지 않는다(서버 로그 확인), (4) 컴퓨터 대전·스토리 등은 현행 그대로.

### 3단계: 서버 재생 판정 + 래더 연동 + TURN·폴백
- 박백엔(약 4~5일): worker 풀 재생(시간 제한·메모리 상한), 정본 입력 규칙·증거 블록 검증·DISPUTE 표(§3.3), 실시간 하한, 래더 반영 출처 교체, 새 무효 사유, TURN 시간 제한 자격 증명 발급, 결과 레코드에 경로·지문·재생 시간 추가, 시험 2개(거짓 결과 보고 → 재생 결과 반영, 이중 입력 → 기권패).
- 윤프론(약 2일): 증거 블록 송신·제출, 「집계 중」 표시, 래더 TURN 강제.
- 인프라(승인 필요): coturn 설치·포트(3478/UDP·TCP, 443/TLS) 개방, 로그 보관 기간.
- 강화면·정검수: 래더 한 판 끝까지 + 결과 반영 확인, 위조 시나리오 리뷰.
- 인수조건: (1) 래더 결과는 서버 재생 결과와만 같다(클라이언트가 거짓 `p2p_result` 를 보내도 반영 불변), (2) 이중 입력 증거가 있으면 위반 좌석 패배, (3) 재생 실패는 무효·벌점 없음, (4) 동시 50판 재생 부하 시험에서 로비 응답 지연 없음.

### 4단계(선택): 소규모 롤백(1~2프레임) — 1~3단계 실측 지연이 아쉬울 때만. 엔진 상태 저장/복원 API 필요(박백엔 상 난이도).

예상 총 규모: 1~3단계 약 3~4주(병렬 시 약 2~3주) [추정].

## 8. 사용자 결정 필요 항목(권고안으로 진행, 승인만 필요한 것 위주)

1. **경로 기본값(권고안으로 진행 가능)**: 일반 방 = 직접 P2P 기본, 「IP 숨기기」 설정 제공(기본 꺼짐). 래더 = TURN 강제(모르는 상대에게 IP 비노출). → 다른 의견이 없으면 이대로.
2. **TURN 서버 운영 승인(승인 필요)**: coturn 설치·포트 개방은 운영 인프라 변경. 승인 전에는 TURN 없이 「직접 P2P → 실패 시 WS 중계」로 2단계까지 진행 가능(래더는 그때까지 WS 중계 락스텝).
3. **1단계 결과에 따른 계속 여부(권고 기준 미리 합의)**: 실측에서 P2P 체감 지연이 현행보다 20ms 이상 좋지 않거나, 비 V8 브라우저 지문 불일치를 2회 수정으로 못 고치면 → 대역폭 이득만 취해 「WS 중계 락스텝 + 서버 재생」(P2P 없이)으로 축소하는 것을 권고.
