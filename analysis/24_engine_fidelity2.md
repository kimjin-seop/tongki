## 3. 미해결 (추정으로 채우지 않음)
[2026-11-18] 1·2·4 와 3 의 일부(공 없는 plan·방어)는 analysis/25_cpu_brain.md 에서 처리했다. 아래는 당시 기록.
1. **ball_launch_tap/hold f15 이후**: 발사(f1~f14)는 일치. 이후는 대상 CPU(타입 0x70, 점프볼 착지 직후)의 피격 시점이 CPU 두뇌(plan 0)와 히트박스 유지 규칙에 좌우된다.
2. **bound_L, ctrl_stop_in**: 전환 시점은 맞지만 사람 편 수동 내야(0x8D02)의 대기점 이동(0x8EDE/0x8F52: 구역 변경 또는 60f 마다 1/2 확률 재선택)이 직역이 아니라 후보 선수 위치가 다르다. 난수 호출 순서까지 맞아야 해서 CPU 전체 이식이 선행 조건.
3. 컴퓨터 활성 선수(타입 0x70/0x74) plan 전체, 투구 대상 = 상대 조작 선수($E21E) 규칙, 패스 대상, 필살기 사용률. 컴퓨터 캐치의 방향은 "공 쪽을 본다"(0x8E50)로 처리했으나 plan 핸들러별 확인은 안 됨.
4. 정지 공 300f 방치 시 강제 회수(0xA64E→0x86A6, 타입 0x44), 양쪽 구역 밖 공의 후방 외야 회수(0x8622). 그동안은 자작 안전망 stallGuard(360f/720f)가 남아 있다.
5. 보유 공 위치의 애니 프레임 카운터($10/$11, 0x19EC): 걷기·대시 중 손 위치(높이 ±1, 대시 x ±4)는 0번 프레임 값.
6. 아웃된 선수가 외야에서 계속 뛰는지(현재 엔진은 DEAD 로 정지), 필살기 공의 수동 내야 웅크림 여부(공 $3 bit6/bit7). -> [2026-11-18 해결] 필살기 공 웅크림은 **웅크린다**로 확인·이식: 원작 `ctr_special` 트레이스의 두 장면(f64, f112 모두 p10 서브 0 -> 0x18, 필살 공 $3 bit6)이 근거. analysis/25_cpu_brain.md, docs/HANDOFF.md §4-15 참조. 아웃된 선수의 외야 활동은 여전히 미해결.
7. 클라이언트가 서버 방향(face, 플래그 bit7)을 그리도록 바꾸는 일(윤프론): 지금은 클라이언트가 방향을 추정해 그려서, 캐치 실패 원인(등을 돌림)이 화면에 안 보일 수 있다.
8. BGM: manifest 에 bgm.* 키 없음(종전 키는 자작 합성음이라 제거됨). ROM 렌더(rom/bgm) 24곡의 루프 지점은 analysis/data/rom_audio.json 기준 `loop_confident` true 6곡 / false 18곡(이 중 `loop:false` 6곡). 키 연결·청취 확인 전이라 BGM_ENABLED 는 켜지 않는다.
