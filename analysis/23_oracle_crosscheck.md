# 23. 오라클 교차 확인 (자작 68000 에뮬 대 공개 에뮬)

작성 2026-11-17. 목적: 차분 하니스(`tools/diff/`)가 정답으로 쓰는 자작 에뮬 `analysis/scripts/m68k.py` 가 공개·검증된 에뮬과 같은 값을 내는지 확인.
도구·출처·해시·재실행법: `tools/ext_emu/README.md`. 이 문서의 수치는 전부 실제 실행 결과다(실행하지 않은 것은 "미확인"으로 표시).

## 결론
- **하니스 1단계 28개 시나리오 1,337프레임 + 추가 장시간 구간 3개 1,403프레임 = 2740프레임 전부에서, 감시 필드(선수 14명·공의 x,y,z,vx,vy,vz, 타입·서브·타이머, 능력치/HP, RNG $E620, 남은 인원, 조작 선수, 패드 값)가 공개 에뮬과 비트 단위로 같다. 필드 불일치 0건.**
- 필드뿐 아니라 68k RAM 64KB 전체가 같다. 예외는 두 가지뿐이고 둘 다 게임 로직과 무관하다.
  1. `$E632` 1바이트(매 프레임, 자작 00 / 공개 FF): VBlank 핸들러가 Z80 버스 요청 레지스터 `$A11100` bit0 을 읽어 저장하는 플래그. 자작 에뮬은 이 레지스터를 항상 0 으로 돌려준다(하드웨어 스텁 차이, CPU 명령 오류 아님).
  2. 스택 아래 죽은 영역(`$FF2A~$FF65`) 6~8바이트, 각 시나리오 **첫 프레임에만**: 주입 시점에 공개 에뮬이 갖고 있던 레지스터(D0~A6)가 VBlank 핸들러의 `movem` 으로 스택에 저장된 흔적. 2프레임째부터는 이 영역까지 같다 = 한 프레임 뒤에는 CPU 레지스터까지 양쪽이 같다.
- 공개 에뮬에서 처리 지연(랙) 프레임 0 (대기 진입 사이 VBlank 수가 전 프레임 1). 자작 쪽 `lagFrames` 0 과 일치.
- **판정: 이 범위에서 자작 오라클은 공개 에뮬(Genesis Plus GX)과 동등하다. m68k.py 의 명령/플래그 오류는 발견되지 않았고, 수정한 것도 없다. `analysis/22_diff_status.md` 의 FAIL 10건은 오라클 오류가 아니라 우리 엔진 쪽 차이로 봐야 한다.**
- 오라클 교체 권고: **교체하지 않는다.** 자작 오라클 유지 + 이 교차 확인을 보조 검증으로 둔다(근거·조건은 아래 "권고").

## 방법
| 항목 | 내용 |
|---|---|
| 공개 에뮬 | BizHawk 2.11.1 (코어 Genesis Plus GX), Lua 로 자동화. 2종째(BlastEm 등)는 도입하지 않음(1종에서 불일치가 없어 판정에 필요하지 않았다) |
| 시작 상태 | 공개 에뮬을 **부팅부터 입력 재생**(mk_state.py·t_play.py 와 같은 규칙: 시작 버튼 연타 → `$E600`=0x14, `$E602`=0)으로 경기 중까지 진행. 그 뒤 메인 루프 대기 진입 시점에 자작 오라클의 시작 RAM(ctrl0 을 대기 경계까지 진행 + setup 적용, 하니스와 동일) 64KB 를 통째로 주입 |
| 주입이 성립하는 근거 | 대기 진입 시 SP 가 양쪽 같음(0xFFFF6C, 전 시나리오 로그 확인). 대기 루프(0x14DC~0x14E8)는 레지스터에 의존하지 않고, 스택·게임 상태는 전부 RAM 에 있다. 세이브스테이트는 형식이 달라 호환되지 않으므로(자작 = 파이썬 pickle) 쓰지 않았다 |
| 프레임 경계 | 하니스와 같은 지점. 공개 에뮬은 실행 훅을 0x14DC(대기 루프 직전 명령, 프레임당 1회)에 걸고, 그 명령(`move.w $E60A,$E608`)의 효과를 비교 때 반영해 자작의 0x14E2 시점과 맞췄다. 자작 에뮬에서 0x14DC 가 매 프레임 정확히 1회 실행됨을 확인 |
| 입력 | 같은 패드 값을 프레임마다 공개 에뮬 패드 포트에 넣음(RAM 직접 쓰기 아님). VBlank 핸들러가 읽어 저장한 `$E64C/$E64D` 가 양쪽 같음으로 입력 정렬 확인 |
| 비교 | 프레임마다 RAM 64KB 전체 바이트 비교 + 하니스 필드 비교(`tools/ext_emu/xcheck/compare.py`) |

부팅부터 입력 재생만으로 프레임을 맞추는 방식은 쓰지 못했다: 같은 입력 규칙으로 경기 화면(`$E600`=0x14)에 닿는 데 공개 에뮬이 연타 69회(2,258프레임), 자작은 저장 상태의 프레임 수(2,263 = 진입 + 60)로 역산해 67회로, 약 54프레임 차이가 난다. 자작 에뮬은 사이클이 아니라 명령 수로 프레임을 끊고 DMA·Z80 대기가 즉시 끝나기 때문이다(부팅·메뉴 구간의 진행 속도는 실기와 다르다. 경기 중 로직 값과는 별개).

## 자작 에뮬에서 확인된 차이와 수정안
| 항목 | 원인 | 영향 | 조치 |
|---|---|---|---|
| `$A11100` 읽기가 항상 0 | `m68k.py` `MD.read()` 가 Z80 버스 요청 상태를 추적하지 않음. 실기·공개 에뮬은 Z80 이 돌고 있으면 bit0=1 | `$E632` 값, VBlank 핸들러 안의 버스 요청 경로(0x1614~, 0x163A) 실행 여부. 게임 상태·감시 필드 영향 없음(2,740프레임 확인) | **수정하지 않음.** 수정안: `write()` 에서 `$A11100` 에 쓴 값의 bit8 을 기억하고 `read()` 에서 bit0 = (요청 안 함 ? 1 : 0) 을 돌려준다. 적용 시 프레임당 명령 수가 조금 늘고 `$E632` 가 FF 가 되지만 하니스 트레이스의 감시 필드는 변하지 않을 것으로 예상(미실행). 필요성 낮음 |
| 버전 레지스터 `$A10001` = 0xA0(해외 NTSC) | `io_read()` 고정값. ROM 은 일본판 | 미확인. RAM 주입 방식이라 부팅 때 읽은 값의 영향은 이번 비교에 드러나지 않는다 | 보고만. 부팅·메뉴 화면을 자작 에뮬로 분석할 때 지역 분기가 의심되면 0x20 으로 바꿔 확인 |

CPU 명령·플래그·타이밍 쪽 오류는 발견되지 않았다.

## 이 확인이 보장하지 않는 것
1. **밟은 명령만 검증됐다.** 추가 구간 330프레임에서 실행된 고유 PC 3,493개, 명령 종류 58개(move, 분기류, add/sub/cmp, and/or/eor/not/neg, 시프트 lsl/lsr/asl/asr, btst/bset/bclr/bchg, mulu, divu, ext, swap, exg, movem, dbra/dbeq, sne, rte 등). **밟지 않은 것: muls, divs, rol/ror/roxl/roxr, addx/subx, abcd/sbcd/nbcd, cmpm, tas, chk, link/unlk, trap, bvs/bvc 등** — 이 명령을 쓰는 경로(필살기·다른 화면 등)는 미확인. divu 는 1개 지점만 밟았다.
2. **경기 중 일반 플레이 경로만.** 필살기·캐치/아웃 판정·교체·점프볼·경기 종료·메뉴·연출은 비교하지 않았다. 새 시나리오를 하니스에 추가할 때 `extra_scenarios.json` 또는 `scenarios.json` 기준으로 같은 절차를 다시 돌리면 된다(약 6분).
3. **랙이 나는 상황은 미확인.** 자작 에뮬은 프레임당 9,600~10,900명령을 쓰는데(상한 14,000) 공개 에뮬에서도 이번 구간은 랙 0 이었다. 화면에 객체가 많아져 실기에서 랙이 나는 장면은 자작 에뮬이 재현하지 못한다(명령 수 기준 타이밍).
4. **공개 에뮬 1종(Genesis Plus GX)과의 일치**다. 실기 대조는 아니다. 다만 서로 독립으로 작성된 두 구현이 2,740프레임 동안 RAM 전체가 같으므로, 같은 오류를 공유할 가능성은 낮다.
5. `give_ball` 등 setup 은 양쪽에 같은 RAM 을 넣는 것이라, setup 자체가 원작의 실제 줍기 경로와 같은지는 이 확인으로 알 수 없다(하니스 README "오라클 신뢰도" 5번 그대로).

## 권고
- **하니스 오라클을 공개 에뮬로 교체하지 않는다.** 근거: (1) 같은 범위에서 값이 완전히 같아 정확도 이득이 없다 (2) 자작 오라클은 파이썬만으로 창 없이 돌고 RAM 조작·임의 PC 훅이 자유롭다. 공개 에뮬은 창이 뜨는 GUI 프로그램이고 경기 진입에 매번 약 2,700프레임 부팅이 필요하다 (3) 라이선스 확인 부담이 없다.
- **대신 보조 검증으로 유지**: 하니스에 새 영역(필살기, 캐치·피격·아웃, 점프볼)을 추가할 때마다 그 시나리오를 이 절차로 한 번 대조한다. 특히 위 1번의 "밟지 않은 명령"이 나오는 경로는 대조 전까지 오라클 값을 확정으로 쓰지 않는다.
- `analysis/22_diff_status.md` 머리말의 "실기·검증된 에뮬과 대조한 적 없음" 문구는 `tools/diff/run.mjs` 가 생성한다. 이번에는 run.mjs 를 건드리지 않았다(문구 갱신은 하니스 담당 판단).
