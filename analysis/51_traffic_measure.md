# 51. 네트워크 트래픽·지연 측정과 절감 후보 (2026-11-20, 박백엔)

측정·분석만 했다. 서버 코드는 한 줄도 바꾸지 않았다(계측 훅도 넣지 않음, 그래서 `_backup/traffic_before/` 사본도 만들 필요가 없었다).
모든 측정은 **2026-11-20 19시 무렵 현재 작업 트리 기준**이다. 이때 다른 에이전트가 래더·채팅·순위표(`server/lobby/lobby.js`, `server/store/*`, `public/js/screens/*`)를 고치는 중이었다. 그래서 래더·로비 수치는 그 뒤 바뀔 수 있다(예: 현재 트리는 손님의 `ladder_join` 을 `ACCOUNT_REQUIRED` 로 거절해서, 래더는 계정 2명으로 쟀다).

측정 환경: Windows 11, Node 25.7, ws 8.23. 임시 서버는 포트 3400에 `DB_PATH=:memory:` 로 띄웠고, `PROGRESS_PATH`·`LEAGUE_PATH`·`RESULTS_DIR`·`RESULTS_PATH`·`JSON_BACKUP_DIR`·`NOTICE_PATH` 는 임시 폴더를 썼다. 한 IP(루프백)에서 많이 붙이려고 측정할 때만 `MAX_CONN_PER_IP`·`MAX_HELLO_PER_MIN`·`MAX_AUTH_PER_MIN` 환경변수를 올렸다. Edge 헤드리스는 임시 프로필로 띄웠고 이 도구가 띄운 것만 종료했다. 운영 DB `data/tongki.db` 는 열지 않았다(sha256 앞 16자리가 측정 전후 모두 `2fb9e76bc8b8bb82`). 루프백·Windows 라 실제 인터넷 경로의 손실·지터는 들어 있지 않다.

**절감량이 큰 후보 3개**(전체 207Mbps 기준, §4.3):
1. **로비 `room_list` 푸시를 바뀐 방만 보내기 + 목록 화면에 있는 사람에게만 보내기**: 약 -93Mbps(**전체의 -45%**). 경기 지연 영향은 없다.
2. **permessage-deflate 레벨 1**: 스냅샷 선 위 -83%로 약 -47Mbps(**전체의 -23%**). room_list 에도 들어서 실제로는 더 클 것이다 [미측정]. 지연은 p95 +2~7ms 다. 다만 CPU +0.3~0.4코어/100좌석, 연결당 약 300KB 메모리가 든다. 레벨 6(ws 기본)은 부하 실측에서 큐 지연 p95 47~470ms 가 나와 쓰면 안 된다.
3. **스냅샷 델타(+좌표 양자화)**: 선 위 -69%(JSON 델타)~-82%(바이너리 델타)로 약 -39~46Mbps(**전체의 -19~22%**). 서버 CPU 는 스냅샷당 +2µs 이하라 지연 영향은 없다.

가장 싸고 위험이 낮은 것은 **정적 파일 압축·캐시·안 쓰는 글꼴 제거**다. -34Mbps(전체의 -16%)이고 첫 화면 4.30MB → 약 1.95MB, 재방문은 0에 가깝다. 지연을 늘리지 않는 순서로 권고하면 정적 → room_list → 델타 → (필요하면) deflate 레벨 1 이다(§4.4). 30Hz 는 -50%(-28Mbps)이지만 체감 지연이 평균 +25ms 늘어서(§5.4) 비권고다.

### 1.5 permessage-deflate
(a) 오프라인 재계산(Node zlib, ws 와 같은 방식: 메시지마다 `Z_SYNC_FLUSH` 하고 끝 4바이트를 뗌, 레벨 6, windowBits 15)

| 방식 | 좌석당 B/s | 압축률 | CPU µs/메시지 |
|---|---|---|---|
| 현행 JSON + deflate(문맥 유지) | 3,511 (pvp 2,813) | **8.3%**(pvp 6.7%) | 44~85 |
| 현행 JSON + deflate(문맥 미유지) | 20,512 | 48% | 30~51 |
| JSON 30Hz + deflate | 1,874 | 8.8% | 70~74 |
| JSON 델타 + deflate | 3,037 | 29% | 46~51 |
| 바이너리 전체 + deflate | 2,442 | 18% | 44~80 |

연속된 snap 이 거의 같아서 문맥을 유지하면 압축률이 7~8%까지 떨어진다. 델타를 한 뒤에는 deflate 를 더해도 이득이 작다(10.6 → 3.0KB/s).

(b) 실제 ws 서버로 재생(`tools/deflate_replay.mjs`): 녹화한 pvp snap 을 60Hz 로 N개 연결에 보냈다. 서버 CPU 는 부모 프로세스에서 쟀고, 클라이언트는 자식 프로세스로 따로 띄웠다. 바이트는 `socket.bytesWritten` 이다. 10초씩 1회만 쟀다.

| 100 | 켬, 레벨 6, threshold 0 | 79% | 2,795 | 0.4 / **47** / **197** |
| 100 | **켬, 레벨 1** | 46% | 3,231 | 0.6 / 2.1 / 5.7 |
| 100 | 켬, 문맥 미유지 | 78% | 19,015 | 1.0 / 221 / 314 |
| 200 | 끔(현행) | 46% | 42,375 | 0.3 / 0.5 / 0.6 |
| 200 | 켬, 레벨 6(ws 기본) | 120% | 2,837 | 0.0 / 5.8 / 10.4 |
| 200 | 켬, 레벨 6, threshold 0 | 125% | 2,795 | 0.8 / **208** / **246** |
| 200 | **켬, 레벨 1** | 85% | 3,168 | 0.0 / 6.6 / 10.3 |
| 200 | 켬, 문맥 미유지 | 135% | 18,461 | 6.2 / 329 / 354 |

- 시계 오차는 프로세스 사이 ±1ms 다(그래서 음수가 나온다).
- 레벨 6은 같은 조건에서도 돌릴 때마다 p95 가 5.8~470ms 로 크게 흔들렸다. zlib 은 libuv 스레드 풀(기본 4개)과 ws 전역 동시 압축 상한(10)에서 큐에 쌓이기 때문이다. **레벨 6은 지연 위험이 크다.**
- 레벨 1은 바이트 -92.5%, p99 10ms 이하였다.
- ws `threshold`(기본 1024B)는 **문맥 미유지(no_context_takeover)를 협상했을 때만** 적용된다(`node_modules/ws/lib/sender.js` 385행). 문맥을 유지하면 700B snap 도 압축된다.
- 메모리 [추정]: 연결마다 deflate 약 256KB(windowBits 15, memLevel 8) + inflate 약 44KB = 약 300KB 다. 접속 1,000명이면 약 300MB 다. `serverMaxWindowBits` 10~12, `memLevel` 4~6 으로 줄이면 압축률이 조금 떨어지는 대신 메모리가 1/4~1/8 이 된다(미측정).
- 현행 서버(`new WebSocketServer({ server, path, maxPayload })`)는 ws 8 기본값인 `perMessageDeflate: false` 다. 브라우저가 압축을 제안해도 서버가 받지 않는다.
- 참고: 압축을 끈 '끔' 행도 200연결에서 CPU 46%다. **지금 서버에서 가장 비싼 일은 압축이 아니라 메시지 수(초당 12,000번 send)다.** 메시지 수를 줄이는 쪽(30Hz·락스텝)은 CPU 에도 듣는다.

### 1.6 메시지당 머리(선 위 오버헤드)
ws 가 `setNoDelay()` 를 켜기 때문에(`node_modules/ws/lib/websocket.js` 269행) snap 1개가 TCP 세그먼트 1개로 바로 나간다. 메시지당 오버헤드는 WS 머리 4B + TLS 1.3 레코드 약 22B + TCP/IPv4 머리 약 52B = **약 78B** 다. 60Hz 면 좌석당 약 4.7KB/s 로, 현행 페이로드의 11% 다. 압축이나 델타를 하면 이 머리가 페이로드보다 커지므로(예: deflate 3.5KB/s 대 머리 4.7KB/s) **그 뒤의 절감은 메시지 수(30Hz·묶음)에서 나온다.** 내려받는 쪽 TCP ACK(지연 ACK, 2세그먼트당 1개 약 52B)는 클라이언트가 보내는 상향 트래픽이라 서버 송신에는 넣지 않았다.

## 2. 로비·대기실·채팅·공지·래더 (`tools/traffic_lobby_measure.mjs`)

실측: 로비 손님 40명, 대기 방 R개(절반은 컴퓨터 대전 방), 초당 2번 방 변화(만들기/나가기 번갈아), 15초.

| 대기 방 수 | 방 밖 1명이 받은 room_list/s | 목록 평균 크기 | **방 밖 1명 B/s** |
|---|---|---|---|
| 0 | 2.0 | 82B | 163 |
| 20 | 2.0 | 2,371B | 4,742 |
| 60 | 2.0 | 6,951B | **13,902** |

- 구조(`server/lobby/lobby.js` `markListDirty`/`roomListMsg`):
  - 방이 생기거나 없어지거나, 인원·상태·규칙이 바뀌면 250ms 로 묶어서 **방에 없는 모든 세션**(`s.conn && !s.roomCode`)에게 **목록 전체**를 보낸다.
  - 이 대상에는 로비 화면만이 아니라 스토리 선택·불꽃 메뉴·래더 대기·리그 메뉴 화면에 있는 사람도 모두 든다.
  - 목록 행 1개는 약 115B 다. 목록에는 일반 방(대기·경기 중, 컴퓨터 대전 포함)이 들고, 스토리·특훈·리그·불꽃·래더 방은 빠진다.
- 모델: 푸시/s ≈ 4 × (1 − e^(−변화율/4)) (250ms 묶음), 바이트 = 푸시/s × 방 밖 인원 × (25 + 115 × 보이는 방 수).
  - 동시 100판이면 경기 시작·종료만으로 초당 약 0.8번 바뀐다(평균 경기 4분 가정). 만들기·들어가기·나가기를 더하면 초당 약 2번이다.
  - 그때 보이는 방이 60개이고 방 밖에 850명이 있으면 **약 11.8MB/s = 94.5Mbps** 다.
  - 보이는 방이 20개면 약 32Mbps 다.
  - 경기가 많을수록 목록이 길어지고 바뀌는 횟수도 늘어서 **제곱에 가깝게 커진다.**
- 래더:
  - `ladder_queue`(134B)는 허용 차나 대기 인원이 바뀔 때만 푸시된다. 실측으로는 혼자 5초 서 있는 동안 1번이었다.
  - 클라이언트는 줄에 서 있는 동안 15초마다 `ladder_status`(716B)를 다시 요청한다(`screens/ladder.js`). 1명당 약 48B/s 다.
  - `ladder_matched` 는 168B 다.
  - `ladder_board`·`pvp_board` 는 빈 DB 에서 276B·102B 였다. 50줄이면 줄당 약 95~105B 로 약 5KB 다 [추정: 필드 구성에서 계산]. 요청할 때만 나간다.
- 채팅 1줄(`{t:'chat', from, text, at}`)은 86B × 두 좌석이다. 빈도 제한(1초 간격, 10초에 5개) 때문에 방 하나에 최대 약 0.2KB/s 라 무시해도 된다.
- 공지 [추정]: `{t:'notice', id, text, at}` 는 약 60~350B × 접속 세션 전원이다. 분당 10개 상한이라 1,000명 × 350B × 10/60 = 최대 약 58KB/s(0.47Mbps)이고 잠깐 생긴다. 관리자 계정은 서버 시작 전에 가입돼 있어야 해서 메모리 DB 로는 실측하지 못했다(코드 형식으로 계산).

## 3. 정적 파일 (`tools/traffic_static.mjs`)

### 3.1 서버가 실제로 보내는 헤더 (임시 서버 응답 그대로)
`server/index.js` 의 정적 처리는 `readFile` 로 파일 전체를 읽어서 `res.end(buf)` 한다. 실측 응답 헤더는 다음뿐이다.
```
content-type: <MIME>   date   connection: keep-alive   keep-alive: timeout=5   transfer-encoding: chunked
```
- `Content-Encoding` 이 없다. `Accept-Encoding: gzip, br` 를 보내도 압축하지 않는다.
- `Cache-Control`·`ETag`·`Last-Modified`·`Content-Length` 가 없다.
- `Range: bytes=0-99` 를 보내도 **200 + 전체 파일**(83.ogg 3.67MB 통째)이 온다.
- `If-Modified-Since`·`If-None-Match` 를 보내도 200 이다(304 가 없다).
- 저장소에는 앞단 nginx 설정이 없다(`*.conf`·문서 검색 결과 없음). 운영(`tongki.oddplay.kr`) 앞단의 압축·캐시 설정은 확인하지 못했다(운영 접속 금지).
- `public/` 전체가 그대로 공개된다. 그 안에 게임이 쓰지 않는 큰 파일이 있다:

| 경로 | 크기 |
|---|---|
| `assets/rom/_cache/*.pkl` | **321MB**(55개, 파이썬 피클 캐시) |
| `bgm_lpf` | 34MB |
| `bgm_cand` | 28MB |
| `bgm_cand_lap` | 2MB |
| `manifest.backup_before_bgm_removal.json` | 71KB |
| `fonts/*.ttf` Galmuri 원본 | 9MB |

  트래픽이 날 일은 아니지만(아무도 요청하지 않는다) 노출·오용(대량 다운로드) 위험이 있어 따로 적는다.

### 3.2 첫 방문 (Edge 헤드리스, CDP Network 로그)
단계 순서: 첫 화면 접속 20초(인트로 재생) → 손님 로그인(로비) 6초 → 컴퓨터 대전 방을 만들고 시작해 25초 → 퇴장 → 새로고침 15초 → 주소로 다시 진입 15초.

| 단계 | 요청 | 받은 바이트 | 그중 큰 것 | gzip/br 이었다면 |
|---|---|---|---|---|
| 첫 화면(boot) | 82 | **4,300KB** | 글꼴 6개 3,297KB · JS 48개 588KB · CSS 2개 160KB · JSON 4개 178KB · 이미지 18개 68KB | gzip 2,376KB / br 2,218KB(-48%) |
| 로그인(로비) | 1 | 0.7KB | | |
| 첫 경기 진입 | 23 | **628KB** | 팀 스프라이트 2장 408KB · anims/teams JSON 116KB · HUD 얼굴 48KB | gzip 468KB(-26%) |

|---|---|---|
| `BlackHanSans-Regular.ttf`(manifest `font.title` = 'DD Title') | 998KB | **어디서도 쓰지 않는다**(`DD Title` 을 참조하는 코드·CSS 없음). 받기만 한다 |

### 3.3 재방문·캐시
- 검증 헤더(`ETag`·`Last-Modified`)도 수명 헤더(`Cache-Control`)도 없다. 그래서 브라우저가 재사용할 수 없고, **방문할 때마다 첫 방문과 같은 4.7MB 를 다시 받는다**(실측: 새로고침·재진입 모두 캐시 적중 0).
- BGM: `public/js/audio.js` 는 경기 곡(`bgm.stage.*`·`bgm.story.*`)을 재생이 끝나면 메모리에서 버리고, 다시 필요하면 새로 받는다(메모리 절약 설계). HTTP 캐시가 없으니 **같은 곡을 경기마다 다시 받는다.**

### 3.4 BGM·음원·큰 파일 지연 로딩
- 정적 에셋은 지연 로딩이다. 경기 스프라이트·배경은 그 경기에 들어갈 때, BGM·효과음은 처음 요청할 때 받는다(`audio.js`, 사용자 입력으로 AudioContext 가 열린 뒤).
- 헤드리스 측정에서는 사용자 입력이 없어서 AudioContext 가 열리지 않았고, **BGM·효과음 요청이 0이었다**(확인 못 함). 그래서 manifest 로 추정했다.

| 곡 | ogg 크기 |
|---|---|
| 타이틀 `8a` | 678KB |
| 메뉴 `8c` | 375KB |
| 대전 `8b` | 851KB |
| 입장 `95` | 81KB |
| 결과 | 74~112KB |
| 경기 곡 | 795KB~3,672KB(평균 약 1.8MB) |

  - 효과음 39개(`rom/sfx`)는 합계 871KB 이고, 처음 울릴 때 하나씩 받는다.
  - [추정] 접속 1회(경기 3판)의 BGM 은 2.0MB(타이틀·메뉴·대전·입장) + 3 × 1.9MB(경기 곡 + 결과) = **약 7.7MB** 다. 캐시가 있으면 서로 다른 곡만 1번씩 받는다.
- 챕터 연출 에셋은 `public/assets/rom/story/` 8개 87KB(컷 4장 24KB, `portraits.png` 21KB, `story_dialogue_ko.json` 25KB(br 5.7KB), `story_cuts.json` 4KB)다. 대사 JSON 은 `assets/data/campaign_dialogue.json` 24KB 이고, 서버 쪽 `server/data/story_dialogue_ko.json` 은 28KB 다. 작아서 영향이 없다.

| G | 양자화만 | -3~5% | -2~3Mbps | 0 | 하 | 하: 단독으로는 가치가 작다(C 와 묶을 때만) |

- **D(deflate)는 A·C 를 한 뒤에는 효과가 줄어든다**(델타 + deflate 3.0KB/s 대 델타 10.6KB/s, 그리고 머리 4.7KB/s 는 그대로).
- A 만 해도 전체의 45% 가 빠진다. A + B + C 를 하면 207 → **약 41Mbps(-80%)** [계산]: 스냅샷 17.4 + 정적 22(대부분 새 방문의 BGM) + 로비 약 1.6 + 기타 0.3.

### 4.4 권고 순서 (「지연을 악화시키지 않는 절감부터」)
1. **B 정적 압축·캐시·안 쓰는 글꼴 제거.** 지연 0, 위험 최하, 첫 화면 로딩도 빨라진다. 함께 `public/` 에서 게임이 쓰지 않는 `_cache`·`bgm_cand*`·`bgm_lpf`·백업 manifest·ttf 원본을 빼거나 서빙을 막는다(노출 차단).
2. **A room_list 델타 푸시.** 지연 0, 전체 절감이 가장 크다. 래더·로비를 고치는 작업과 겹치므로 그 작업이 끝난 뒤에 한다.
3. **C 스냅샷 델타(+1/4px 양자화).** 지연 0. JSON 델타부터 하고, 바이너리는 필요할 때만 한다.
4. **D deflate 레벨 1**: 1~3 뒤의 실측으로 필요할 때만 한다. 운영과 같은 OS 에서 CPU·메모리·p99 를 다시 잰 뒤에 켠다. 레벨 6(ws 기본)은 쓰지 않는다.
5. E 30Hz 는 비권고(지연 +25ms). F 락스텝은 대역폭이 아니라 analysis/50 의 별도 결정 사항이다.

## 5. 지연(입력 → 화면 반영)

### 5.1 현재 경로 분해

| 단계 | 현재 동작(코드) | 지연 |
|---|---|---|
| ① 입력 전송 | `InputSender.update` 가 눌림 상태가 바뀌는 즉시 `flush`. 250ms 재전송은 누르고 있을 때 같은 값을 다시 보내는 것뿐이라 지연과 무관 | 0 + 단방향 RTT/2 |
| ② 서버 수신 | `ws.on('message')` 에서 바로 `setInput` → `latch`(새로 눌린 비트는 1틱 보장) | 약 0 |
| ③ 틱 대기 | `setInterval(lobby.tickGames, 5)` + 60Hz 드리프트 보정. 다음 틱까지 기다린다 | 이론상 0~16.7ms(평균 8.3) + 타이머 해상도. **Windows 실측: 타이머가 약 15.6ms 단위라 snap 간격 p50 15.6 / p95 30.7ms**(빈 서버에서 20ms 넘는 간격 7%, 50~100판이면 24~29%) |
| ④ 엔진 반응 | 이동·점프 모두 **입력이 들어간 다음 틱에 반영**(오프라인 204/204, 81/81 = 1틱) | 그 틱 안 |
| ⑤ 스냅샷 송신 | 같은 루프에서 틱 직후 바로 `broadcastSnap`(stringify 1번, 3~4.5µs), 소켓마다 `send` 약 25~38µs CPU. TCP_NODELAY 켜짐, 압축 꺼짐, 큐 없음(`bufferedAmount > 1MB` 면 버림) | 약 0.1ms(+부하) |
| ⑥ 하향 전송 | | 단방향 RTT/2 |
| ⑦ 클라이언트 보간 | `SnapBuffer`: 최신 snap 보다 `DELAY_TICKS=1` 틱 뒤를 그리고 부드럽게 따라간다(`tick += dt×0.06 + (목표−tick)×0.05`). 최신 틱을 넘지 않게 자른다 | +16.7ms |
| ⑧ 렌더 | `requestAnimationFrame` 다음 프레임 | 평균 8.3ms(최대 16.7, 60Hz 화면) |
| ⑨ 화면 출력 | 합성·스캔아웃 | 약 1프레임 [추정, 미측정, 아래 합계에서 뺐음] |

### 5.2 루프백 실측 ②~⑥ (`tools/latency_measure.mjs`, 시도 300회 × 부하 3단계)
조작 선수가 서 있을 때 방향키를 누르고, 그 선수 x 가 그 방향으로 처음 바뀐 snap 이 도착할 때까지 쟀다. 배경 경기는 컴퓨터 대전이고, 사람 좌석은 입력 없이 snap 을 60Hz 로 받는다.

| 서버 부하 | 평균 | p50 | p95 | p99 | 최대 | snap 간격 p95 / p99 / 최대 |
|---|---|---|---|---|---|---|
| 경기 1판 | 18.2ms | 16.0 | 31.0 | 32.2 | 406(1회, 상태 전환과 겹침) | 30.7 / 31.6 / 32.8 |
| 경기 51판 | 18.2 | 19.3 | 30.2 | 39.3 | 143 | 30.2 / 31.6 / 51.2 |
| 경기 101판 | 22.3 | 20.7 | **39.8** | **58.0** | 136 | 32.8 / 41.9 / 189 |

- 입력 직전 snap 기준 틱 차이는 대부분 2(틱 대기 + 반응 1틱)였다.
- 이 값은 **Windows 타이머 해상도(약 15.6ms)가 지배한다.** 운영이 Linux(pm2)라면 `setInterval(5)` 가 약 1~5ms 단위로 깨어나서 ③은 평균 약 8.3 + 2.5ms, p95 약 21ms 로 줄 것이다 [추정, 미측정].
- 같은 이유로 보간 버퍼 1틱이 모자라는 순간(간격 > 약 17ms)이 Windows 에서 7~29% 생긴다. 이때 화면이 최신 snap 에서 잠깐 멈춘다.

### 5.3 네트워크 RTT 별 체감 지연 모델 (①~⑧, ⑨ 제외)
평균 = RTT + 18(실측 ②~⑥) + 16.7(보간) + 8.3(rAF) = **RTT + 43ms**. p95 ≈ RTT + 31~40 + 16.7 + 16.7 = **RTT + 64~73ms**(실제 인터넷 지터는 더 붙는다).

| RTT | 평균 | p95(1판 ~ 100판) | Linux 서버 추정 평균 |
|---|---|---|---|
| 20ms | **63ms** | 84 ~ 93ms | 약 56ms |
| 50ms | 93ms | 114 ~ 123ms | 약 86ms |
| 100ms | 143ms | 164 ~ 173ms | 약 136ms |

### 5.4 절감 후보별 지연 영향

| 후보 | 지연 변화 | 근거 |
|---|---|---|
| 정적 압축·캐시(B) | 0(로딩만 빨라짐) | 경기 경로 밖 |
| room_list 델타(A) | 0 | 경기 경로 밖(로비 클라이언트의 JSON 파싱도 줄어든다) |
| 델타·양자화(C) | 서버 +1.7~2.3µs/snap, 0에 가깝다. 작은 패킷이 느린 회선 큐를 줄인다(+) | §1.4 인코딩 CPU |
| permessage-deflate 레벨 1(D) | p50 +0.6, p95 +2~7, p99 +6~10ms(100~200연결). 레벨 6은 큐 때문에 p95 47~470ms | §1.5(b) |
| 30Hz(E) | snap 샘플링 +평균 8.3 / 최대 16.7ms, 그리고 보간 버퍼가 2틱이어야 끊김이 없어서(스냅 간격 = 2틱) +16.7ms. 합 **+25ms 평균 / +33ms 최대** | `snaps.js` 보간 규칙 |
| Nagle/TCP | 이미 TCP_NODELAY(ws `setNoDelay()`). Node 클라이언트·브라우저도 지연 없이 보낸다. 앞단 nginx 는 WebSocket 을 그대로 터널링하고 `tcp_nodelay on` 이 기본값이다 [nginx 설정 미확인] | ws 소스 269행 |
| 서버 틱 지터 | Windows p95 +15ms(타이머). 100판이면 p99 snap 간격 42ms, 최대 189ms | §5.2 |
| 입력 락스텝(F) | 내 입력도 상대 입력도 D 틱 뒤에 반영된다. WS 중계면 D ≥ (RTT + 지터)/16.7 이다. RTT 20: D=2 → 33 + 렌더 25 ≈ 58ms(현행 63). RTT 50: D≈4 → 92ms(현행 93). RTT 100: D≈7 → 142ms(현행 143). 지터가 크면 멈칫한다. P2P 같은 도시면 더 좋다(analysis/50 §2.3) | 모델 |
| 입력 예측(내 선수 선반영 + 재조정) | 내 조작은 약 1프레임으로 줄어든다(RTT 와 무관). 상대·공은 현행 그대로. 서버가 다르게 판정하면 되돌리는 '튐'이 생긴다 | analysis/50 §2.1: 엔진이 브라우저에서 같은 결과로 돌아서 기술적으로는 가능 |

### 5.5 지연을 줄이는 후보와 위험

| 후보 | 기대 효과 | 위험·비용 |
|---|---|---|
| 운영 OS 가 Linux 인지 확인. Windows 면 고해상도 대기(짧은 `setImmediate` 루프나 `timeBeginPeriod` 대체) | p95 -10~15ms | 바쁜 대기는 CPU 를 쓴다 |
| TCP_NODELAY·소켓 버퍼 | 이미 켜짐 | 앞단 프록시가 버퍼링하지 않는지만 확인 |
| 스냅샷을 틱 직후 즉시 송신 | 이미 그렇게 한다(같은 루프) | - |
| 입력을 변화 즉시 송신 | 이미 그렇게 한다 | - |
| 보간 버퍼 최소화(1 → 0틱 + 외삽) | -16.7ms | 지터가 있으면 끊기거나 튄다. Windows 서버에서는 지금도 1틱이 모자라는 순간이 7~29% 라 비권고 |
| 서버 위치·경로(국내 리전, 사용자와 같은 망) | RTT 가 그대로 체감에 들어간다. 국내 5~20ms 대 해외 100ms 이상 | 비용 |
| 클라이언트 입력 예측 | 내 조작 -RTT | 상: 엔진 상태 저장·되감기와 연출 이벤트의 튐(analysis/50 의 4단계 롤백과 같은 문제) |

결론: **트래픽 절감 1~3순위(B·A·C)는 모두 경기 지연을 늘리지 않는다.** 지연 쪽의 가장 싼 개선은 서버 OS/타이머 확인이다(코드 변경 전에 운영 환경을 확인할 일). 30Hz 는 지연을 늘려서 비권고다. deflate 는 레벨 1로만, 실측 p99 를 보고 결정한다.
