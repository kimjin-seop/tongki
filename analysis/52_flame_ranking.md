# 52. 순위표에 「불꽃의 계승」 탭 추가 — 데이터 조사·설계 (2026-11-20, 박백엔)

사용자 요구: 순위표에서 불꽃의 계승 전적 순위도 보이면 좋겠다.
이번 단계는 문서만 만들었다. 소스와 DB는 고치지 않았다. 운영 DB `data/tongki.db` 에는 접근하지 않았고, 스키마는 코드(`server/store/db.js`)와 `:memory:` 시험으로만 확인했다.

## 0. 결론 먼저

- **불꽃 전용 순위 데이터·서버 조회는 이미 있다.** 2026-11-19 D27 「도달 순위표」(analysis/39 D27, PROTOCOL §13.13)에서 만들었고, 코드는 `server/flame/ranking.js`, 요청은 `flame_ranking_get` → 응답 `flame_ranking` 이다. 지금은 불꽃의 계승 모드 안의 「순위」 화면(`public/js/screens/flame/rank.js`)에서만 보인다.
- 그래서 이번 요구는 **화면만 바꾸면 된다**: 로비 순위표(`public/js/screens/ranking.js`)에 3번째 탭 「불꽃의 계승」을 붙이고, 기존 `flame_ranking` 응답을 그린다.
- **DB 마이그레이션은 필요 없다**(v3 에 합칠 것도, v4 를 만들 것도 없다). 서버 필수 변경도 없다.
- 지표는 기존 D27 정렬(최고 도달 구간 → 그 도전의 승수 → 먼저 달성)을 그대로 쓰고, **누적(시즌 없음)** 으로 둘 것을 권고한다.

## 1. 모드 구조와 서버에 남는 기록

### 1.1 규칙·진행 구조 요약 (PROTOCOL §13.3·§13.12, `server/flame/run.js`)
- 도전(run) 하나는 컴퓨터를 상대로 지도 노드를 따라 경기를 치른다. 구간마다 7층이고 경기는 일반·일반·강팀·보스 4경기다. 엔드리스가 켜져 있어(기본값) 구간에 상한이 없다. **도전은 1패 또는 포기로 끝난다.** 구간 3 보스를 이기면 「우승」으로 치고(`best.clears++`), 도전은 구간 4 로 이어진다.
- 경기 판정은 서버가 한다. `flameEnd`(handlers.js)가 `game_end` 를 받으면 `Run.applyMatchResult` 가 반영한다. 좌석 0 이 정상 종료(`annihilation`·`timeup`·`sudden_death`)로 이겼을 때만 승리다. `error` 는 재경기, 그 밖은 패배로 도전이 끝난다.
- 키는 소문자 닉네임이다. 손님과 계정 모두 저장된다. 저장 표는 `flame_profiles`(영구 저장 JSON)와 `flame_runs`(도전 JSON)이고, 둘 다 `db.js MIGRATIONS` v2 에 있다.

### 1.2 순위 지표로 쓸 수 있는 값 — 있음/없음

| 지표 | 저장 여부 | 위치 | 비고 |
|---|---|---|---|

| 그 도전의 승수 | **있음** | `best.rank.wins` | 2차 키. 같은 구간 안에서 얼마나 더 갔는지와 같은 뜻이다 |
| 달성 시각 | **있음** | `best.rank.at`(ms, 엔드리스 이전 기록은 0) | 3차 키(먼저 달성한 사람이 위). 주간 필터에도 쓸 수 있다 |

### 1.3 기록 갱신 지점(경기 종료 훅) — 이미 구현됨
- `run.js recordBest` 는 두 군데에서 불린다. ① 구간 보스를 이겼을 때(`applyMatchResult` 의 lastLayer 분기, 진행 중인 도전도 반영) ② 도전 종료 정산 때(`settle`, 경기를 1판 이상 치른 도전만).
- 기록은 **더 멀리 갔거나, 같은 구간에서 승수가 더 많을 때만** 바뀐다. 그래서 패배·포기·재접속으로 줄거나 사라지지 않는다.
- 저장에 성공하면 `handlers.js rankUpdate` 가 메모리 순위표의 그 계정 줄만 고친다. 저장에 실패하면 고치지 않고 `FLAME_SAVE_FAILED` 로 재경기가 된다. 서버를 시작할 때는 `flame_profiles` 전 행에서 순위표를 다시 만든다(`FlameRanking.rebuild`).

### 1.4 모드 구분·손님
- **도전(CPU 상대)** 만 불꽃 순위에 들어간다.
- **불꽃 팀 사람끼리 대전**(`rules.flameTeams`, §13.25): 불꽃 저장에는 아무것도 쓰지 않는다. 승패는 「전체 랭킹」(`pvp_board`)에 일반 사람끼리 경기와 합산된다.
- **손님**: 저장은 되지만 순위에는 계정만 오른다(`isAccount` = `accounts` 표의 키). 손님에게는 `me:null` 이 가고 조회만 된다. 격리 키(`guest-aside:`·`flame-broken:`)는 계정 표에 없어서 빠진다.

## 2. 순위 지표 권고

### 2.1 정렬 — 기존 D27 그대로(권고)
1. 최고 도달 구간 `seg` 내림차순
2. 그 도전의 승수 `wins` 내림차순
3. 먼저 달성 `at` 오름차순. 이 키는 같은 순위 안의 표시 순서만 정한다.
- **구간·승수가 같으면 같은 순위**다(1, 2, 2, 4). 이미 구현·시험되어 있다(`test/flame_endless.test.js` 「순위표: …」).
- 권고 근거: 불꽃의 계승은 1패로 끝나는 로그라이트라서 「어디까지 갔나」 하나가 실력·운영·성장을 함께 담는다. 누적 판수·누적 승은 많이 할수록 오르는 값이라 순위 지표로는 부적합하다. 시간 지표는 엔드리스에서 정의되지 않는다.
- 난이도(일반/고난도) 통합: 표는 하나로 두고 고난도 기록에는 표식을 붙인다(지금과 같다). 고난도를 가중하거나 표를 분리하는 것은 고난도 플레이어가 충분히 모인 뒤로 미룬다.

### 2.2 시즌/누적 — 누적 권고
- 래더는 레이팅 경쟁이라 시즌마다 초기화하는 것이 맞다. 불꽃 기록은 개인 최고 도달(PB) 성격이라 초기화하면 성장 결과를 잃는다. 「전체 랭킹」과 같은 **누적**으로 둔다.
- 주간·시즌 탭을 원하면 2차로 다룬다. 그때는 영구 저장에 주간 최고 칸(예 `best.week{wk, seg, wins, at}`)을 더하면 된다. 이 칸도 JSON 선택 칸이라 DB 변경은 필요 없다.

### 2.3 어뷰징·중복 반영 방지 — 현 구조로 충족
- 서버 판정만 쓴다. 기록은 서버 `game_end` → `applyMatchResult`/`settle` 에서만 바뀌고, 클라이언트는 노드 ID 만 보낸다(§13 원칙).
- 중복 반영이 구조적으로 불가능하다. 기록이 누적 합이 아니라 계정당 최고값 1건이기 때문이다. 같은 경기를 두 번 반영해도 값이 오르지 않는다. 또 `run.match.node`·`run.id` 대조로 오래된 결과(`stale`)는 버린다.
- `flame_new` 를 반복하거나 시작 직후 포기한 도전은 기록하지 않는다(`counted:false`). 연습 경기·키운 팀 대전은 반영하지 않는다.
- 남는 위험: 다계정은 각자 자기 기록만 올리므로 순위를 오염시키지 않는다. 같은 닉네임의 손님으로 오래 기록을 쌓은 뒤 가입해 승계하는 우회(§2.1 한계)는 기존 진행·리그와 같은 수준으로 수용 상태다.

## 3. 서버 변경안

### 3.1 필수 변경 — 없음
- 조회 메시지는 기존 `flame_ranking_get {top?}` → `flame_ranking {top:[{rank, nick, seg, wins, team[≤3], diff, at}], me, total}` 를 그대로 쓴다. 새 메시지 `flame_board` 는 만들지 않는다(같은 내용을 두 이름으로 두지 않는다).
- 빈도: flame 창(`MAX_FLAME_PER_MIN` 300/분)에 든다. 래더·전체 랭킹이 쓰는 캠페인 창(30/분)과 별개라 서로 잠기지 않는다. 로비·방 안 어디서나 된다.
- **DB**: 표·색인·마이그레이션이 필요 없다(영구 저장 JSON 의 `best.rank` 만 읽는다). 그래서 v3(래더, 운영 미실행) 게이트와 무관하고 v4 도 만들지 않는다. v3 운영 실행 여부와 상관없이 배포할 수 있다.
- 조회 비용(측정, 메모리 저장소 2만 계정, 스크래치 스크립트): 서버 시작 때 전 행 다시 만들기 약 416ms, 기록이 바뀐 뒤 첫 조회(정렬) 약 52ms, 그 뒤 조회(캐시) 0.02ms. 응답 크기는 상위 50줄 + 내 줄로 약 4.5KB 다. 지금 유저 수(계정 0~수십)에서는 문제없다. 수만 명을 넘으면 전용 표로 옮긴다(그때 v4, 운영 DDL 승인 필요 — §13.13 규모 한계와 같다).

### 3.2 선택 변경(권고: 이번에는 하지 않음, 원하면 소규모)
- (S1) 줄에 우승 횟수 `clears` 추가: `server/flame/ranking.js rankOfRaw`·`board` 에 칸 하나, 약 5줄이다. 정렬 키는 바꾸지 않는다. DB 변경은 없다. 화면에 「우승」 열이 생긴다. 표가 넓어지므로 1차에서는 뺄 것을 권고한다.
- (L1, 발견한 작은 공백) 손님이 가입해 기록을 승계해도 **다음 불꽃 저장(아무 `flame_*` 쓰기·경기)이나 서버 재시작 전까지는 순위표에 나오지 않는다.** `rankUpdate` 가 저장할 때만 불리고, 가입 경로(`lobby.js` 계정 승격)에서는 순위표를 고치지 않기 때문이다. `flame_get` 은 저장하지 않는다. 고치는 방법은 가입 승계 직후 `this.flameRank?.update(key, nick, this.flame.getProfile(key))` 1줄이다. 다만 `server/lobby/lobby.js` 를 다른 에이전트가 수정 중이라 그 작업이 끝난 뒤에 넣는다. 심각도는 Low 다.

## 4. 화면 변경안 (`public/js/screens/ranking.js`, 읽기만 함 — 현재 다른 에이전트 수정 중)

현재 구조: 탭 버튼 배열 `[['ladder','래더 랭킹'],['pvp','전체 랭킹']]`, `paintLadder`/`paintPvp`, 공통 `table(cols, rows, meRow)`(내 줄 `.rk-me`, 목록 밖이면 `tfoot`), `ask()` 가 두 요청을 보낸다. 갱신 훅은 `onRankingList`·`onPvpBoard`·`onWelcome` 이다. 수신은 `main.js` 의 `net.on('ladder_board'|'pvp_board')` 이다.

변경(윤프론):
1. 탭 배열에 `['flame', '불꽃의 계승']` 을 3번째로 추가한다.
2. `paintFlame(app.flameRank)`: 열은 `순위 · 닉네임 · 구간 · 승 · 핵심`.
   - 닉네임 칸: 닉네임 + `diff > 0` 이면 「고난도」 작은 칩. 이름은 불꽃 catalog 가 있으면 `difficulty[].name`, 없으면 「고난도」.
   - 구간·승: 기록이 없는 내 줄(`seg:0`)은 `-`.
   - 핵심: `team[]` 를 `rankName` 으로 푼다(`'@팀:번호'` → `names.js playerName`). `flame/ui.js` 의 같은 식을 쓰거나 `names.js` 를 직접 쓴다. **텍스트 노드로만** 넣는다(`h()` 문자열 자식, innerHTML 금지).
   - 부제(`sub`): 「가장 멀리 간 도전 기준 · 누적」 한 줄과 `total` 명. 설명 문구는 최소로 한다.
   - 내 줄: 기존 규칙과 같다(`.rk-me` 노랑, 상위 50 안에 없으면 `tfoot`). 손님은 내 줄이 없다.
   - 좁은 폭(≤639px): 핵심 열을 숨기거나 줄바꿈한다(불꽃 화면 `.fl-rk-row` 와 같은 기준).
3. 요청: `ask()` 에 `net.send('flame_ranking_get', {})` 를 추가한다(탭을 열 때만 보내도 된다). 재접속 `onWelcome` 도 같다.
4. `public/js/main.js` 186행 `net.on('flame_ranking')`: 지금은 `app.view === 'flame'` 일 때만 화면에 전달한다 → `app.screen?.onFlameRanking?.(m)` 로 넓히거나 `ranking` 뷰 조건을 더한다(1줄). 「내 순위용 `top:1` 응답은 me 만 갈아 끼운다」는 기존 처리는 그대로 둔다. `app.flameRank` 에 `top` 이 없으면 「불러오는 중…」이다.
5. 불꽃 모드 안의 기존 「순위」 화면(`flame/rank.js`)과 홈의 「내 순위」 줄은 그대로 둔다. 두 화면이 같은 `app.flameRank` 를 공유하므로 데이터가 어긋나지 않는다.

1. 로비 「순위표」에 탭 3개(래더 랭킹·전체 랭킹·불꽃의 계승)가 있고, 불꽃 탭에서 `flame_ranking` 상위 줄이 `순위·닉네임(+고난도)·구간·승·핵심 3명` 으로 보인다. 원작 선수 핵심 이름이 `@3:1` 같은 원문이 아니라 이름으로 보인다.
2. 계정은 내 줄이 강조된다(목록 밖이면 아래 고정 줄, 기록이 없으면 `-`). 손님은 내 줄이 없다. 서버 거절은 토스트로 뜬다.
3. 기존 두 탭과 불꽃 모드 안의 순위 화면·홈 「내 순위」 줄이 종전과 같다. 콘솔 오류 0.

시험 계획(핵심 3개)
1. 서버: 기존 `node --test test/flame_endless.test.js` 「순위표」 2건을 회귀로 확인한다(이번 조사에서 실행, 2/2 통과). 서버를 바꾸지 않으므로 새 시험은 없다. S1·L1 을 하면 그 시험에 단언 1개씩을 더한다.
2. 실화면(강화면, 임시 포트 + 임시 프로필 Edge, `:memory:` 또는 시험용 DB): 계정 2개로 불꽃 기록을 만든 뒤(시험 서버에서 저장값 주입 또는 실제 1경기) 불꽃 탭 표시·내 줄 강조·손님 `me:null`·좁은 폭을 확인한다.
3. 회귀: 탭 전환 3회와 재접속(`welcome`) 뒤 세 탭이 각각 다시 그려지고, 불꽃 모드 홈의 「내 순위」가 그대로인지 확인한다.
