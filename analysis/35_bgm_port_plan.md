## 0. 먼저 읽을 것: 큐 항목의 전제가 지금 상태와 다르다
큐 항목은 "루프 확정 6곡 중 1곡 시범 이식, 활성 플래그는 검증 전 false 유지, 수정 전 사본 `_backup/bgm_before/`"였다. 기록을 읽어 보니 전제 3가지가 이미 바뀌어 있었다.

| 큐 항목의 전제 | 실제 기록(27 문서, HANDOFF §4-4) |
|---|---|
| 루프 확정 곡 = 6곡 | 그 6곡은 **끝나는 곡 6개(루프 없음)** 였다(27 §1). 지금은 24곡 중 **루프·종료 확정 21곡**(루프 15 + 1회 6), 미확정 3곡(0x82, 0x85, 0x98) |
| BGM 은 아직 이식 전 | 2026-11-18 에 이식 완료. **14곡이 켜져 있다**(경기 8, 타이틀, 메뉴, 편성, 입장, 결과 2). 방식 = ROM 드라이버 실행 → 레지스터 열 → 미리 렌더한 파일 재생 |
| 활성 플래그 false 유지 | `public/js/audio.js` `BGM_ENABLED = true`(사용자 결정 "BGM 도 원작 그대로", HANDOFF §4-4). 실제 재생은 곡별 허용 목록(manifest `bgm.*` 의 `verified:true`)으로만 |
| 사본 `_backup/bgm_before/` | 이미 있다(2026-11-18 05:30, 첫 이식 전 사본). 덮어쓰면 그 사본이 사라지므로 **이번 사본은 `_backup/bgm_port_before/`** 에 따로 두었다 |

그래서 이번 작업은 다음처럼 했다.
- 제품 코드(`public/js`, `server`, manifest, 곡 파일)는 **하나도 고치지 않았다.** `BGM_ENABLED` 도 그대로 `true` 다(끄면 사용자 결정으로 켠 14곡이 무음이 되므로 임의로 바꾸지 않았다. §6 결정 1).
- ①은 "남은 이식 작업 계획"으로, ②는 "이미 켜진 루프 곡 1곡(0x8C)을 **공개 에뮬레이터**와 대조"로 수행했다. 지금까지 루프 곡의 근거는 자작 Z80 실행뿐이었고(27 §2 "공개 에뮬레이터 녹음과의 대조는 하지 않았다"), 공개 에뮬 대조는 1회 곡 0x8A 의 소리뿐이었다(27 §11-2).

## 2. 이식 구조(정리)

### 2-1. ROM 안의 위치
| 항목 | 위치 | 근거 |
|---|---|---|
| Z80 드라이버 | ROM 0x7DE0C(0x105C 바이트) → Z80 RAM 0x0000 | 02 §6 [확인] |
| 드라이버 데이터 | ROM 0x7EE68(0x888 바이트) → Z80 0x1100 | 02 §6, `z80snd.py boot()` |
| 초기 파라미터 | ROM 0x15FC(10바이트) → Z80 0x1C00 | 같음 |
| 곡 데이터 | **뱅크 0x0F = ROM 0x78000~0x7FFFF** 를 Z80 0x8000~ 에 매핑. ROM 주소 = 0x78000 + (Z80 주소 − 0x8000) | 이번 실측(곡 0x8C·0x81·0x82 실행 뒤 뱅크 레지스터 값 0x0F) |
| 곡 0x8C 데이터 | 곡 명령 0.5초 뒤 트랙 데이터 포인터 = Z80 0xAAC8·0xAAE4·0xAB1A·0xAB50·0xABA9 → ROM 0x7AAC8~0x7ABA9 부근(그 시점에 읽던 위치이고 트랙 첫 주소는 아니다), 트랙 7개(`$1C40`~`$1D60`) | 이번 실측 |
| 곡 0x81 / 0x82 데이터 | 같은 시점 포인터 최솟값 기준 ROM 0x782A8~ / 0x785BF~, 트랙 10개씩 | 같음 |
| `$1D60` 트랙 | 포인터 0x0A7E = Z80 RAM 안(드라이버 영역). 곡 데이터가 아니라 드라이버 내부 열 | 같음. 용도 미판독 |
| 곡 번호 → 곡 머리 표 | **미판독**(드라이버가 실행으로 찾아 주므로 지금 방식에는 필요 없었다) | - |
| 68k → Z80 | `jsr $16B6`(d0=ID) → 큐 `$E610` → 0x16CE 가 `$A01C0A/B/C` 에 기록 | 02 §6 [확인] |
| 경기 곡 표 | 0x50D2[ROM 스테이지], 0x50F2[스토리 경기 번호] | 27 §4 [코드] |

### 2-2. 재생기 구조(현행)
```
ROM ─ z80snd.py(자작 Z80: 드라이버 그대로 실행) ─ YM2612/PSG 레지스터 쓰기 열(+시각)
     ─ loop_exact.py(곡 진행 상태 반복으로 루프 시작 S·길이 P 확정)
     ─ render.py(VGM → ffmpeg libgme 합성 → 시간축 보정 → ogg/mp3, 루프 지점 기록)
     ─ build_manifest.py(조건 통과 곡만 manifest bgm.* verified:true)
브라우저 ─ audio.js(WebAudio: 버퍼 재생, loopStart/loopEnd, 즉시 교체 = 새 곡 명령, 계단 페이드 = 0xE0, 즉시 정지 = 0xE1)
```
- 효과음(`sfx.*`)과의 통합: 같은 `audio.js` 관리자·같은 manifest 키 간접 참조·같은 렌더 이득(+4.28dB)·같은 출력 단(master → `MIX_TRIM` −4.28dB → 소프트 리미터). 화면 → 곡 표와 경기 이벤트 → 곡 진행은 `public/js/game/sfxmap.js`(`SCREEN_BGM`, `matchBgm`, `playResult`). 새 곡을 켜는 절차는 "루프 확정 → 렌더 → `build_manifest.py` 허용 → `sfxmap.js` 에 장면 연결"이고 `audio.js` 는 고칠 필요가 없다.
- 구조상 재현되지 않는 것: 효과음이 곡의 FM 채널을 잠시 가로채는 동작(27 §9). 미리 렌더한 파일을 섞는 구조의 한계다.

## 4. 시범: 0x8C(모드 메뉴 곡) 공개 에뮬 대조

대상: 0x8C. 고른 이유 = 켜져 있는 루프 곡 중 가장 짧고(루프 768틱 12.169초), **원작이 스스로 거는 장면(모드 메뉴)에 입력 6번으로 닿아** 곡 명령을 손으로 넣지 않아도 된다.

### 4-1. 방법
- 오라클: BizHawk 2.11.1(Genesis Plus GX, `tools/ext_emu/`). 부팅 → 시작 버튼 6회 → 모드 메뉴(프레임 375, `$E600`=0x8C) → 무입력 3300프레임(메뉴 유지 확인: 300프레임마다 `$E600`=0x8C).
- 덤프 2가지를 같은 실행에서 얻었다: ① 매 프레임 끝의 Z80 RAM `$1C00~$1EFF`(3674프레임) ② 소리(부팅부터 3800프레임, 63.4초).
- 대조 1(채널 트레이스, `compare_state.py`): 우리 렌더의 근거인 자작 Z80 실행에서 곡 틱마다 저장한 RAM 과 비교. 비교 대상 = 이 곡 트랙 7개의 **곡 진행 상태**(데이터 포인터·호출 스택 포인터·남은 길이·반복 카운터와 호출 스택·재생 중 비트, 프레임당 91바이트. `loop_exact.py` 와 같은 정의). 공개 에뮬 덤프는 프레임 끝이라 곡 틱 경계와 어긋나므로, 프레임마다 "우리 틱 k 와 같다(exact)" 또는 "모든 바이트가 틱 k 나 k+1 의 값이다(between)"인 k 를 순서대로 찾았다.
- 대조 2(소리, `compare_audio.py`): 웹이 실제로 트는 `8c.ogg` + manifest 루프 지점 대 공개 에뮬 녹음.
- 오디오 레지스터 쓰기 열 자체의 대조는 하지 않았다(**미시도**): 이 에뮬이 내놓는 메모리 도메인 목록(Z80 RAM, MD CART, SRAM, CRAM, VSRAM, VRAM, M68K BUS, 68K RAM)에 Z80 버스·YM2612 포트가 없어 쓰기 훅을 걸 자리를 찾지 못했다. 대신 레지스터 쓰기를 만드는 상태(트랙 구조체)를 비교했다.

## 7. 켜진 곡 12개의 공개 에뮬 대조 (작업 ①)

### 7-1. 방법
- 0x8C 시범(§4)과 같은 비교(곡 진행 상태 + 소리)다. 다른 점 하나: 곡을 원작 화면까지 가서 울리게 하지 않고, **모드 메뉴(프레임 375)에서 60프레임 뒤 Z80 RAM `$1C0A` 에 곡 번호를 직접 썼다**(68k 가 `jsr $16B6` → `$A01C0A` 로 하는 일과 같은 번지). 메뉴 곡 0x8C 가 울리던 중에 새 곡 명령이 들어간 셈이고, 드라이버는 새 곡 명령에서 작업 영역을 전부 지우고 시작한다(Z80 0x0561 → 0x07F2, §10-1).
- 곡마다 EmuHawk 를 새로 띄워 "명령 뒤 S+2P+4초"(1회 곡은 끝+4초)를 돌렸다. 덤프 내내 68k `$E600` = 0x8C(모드 메뉴 유지)임을 600프레임마다 기록했다. 곡 트랙이 아닌 구조체(`$1E20~$1EFF`)가 켜진 프레임은 전 곡 0.
- 우리 쪽 = 자작 Z80 실행(부팅 10프레임 뒤 `$1C0A` 에 곡 번호). 소리 = 웹이 실제로 트는 `public/assets/rom/bgm/XX.ogg` + manifest 루프 지점.
- 정렬 기준: 처음 60프레임 가운데 exact 30 이상이고 exact+between 50 이상(트랙 10개 곡은 틱 처리 도중에 찍히는 프레임이 많아 0x8C 때 쓴 "exact 50 이상"으로는 0x83·0x84·0x86 이 첫 회차에서 맞지 않았다. 기준을 낮춘 뒤 모든 곡이 명령 뒤 6~29프레임에서 정렬됐다).
- 0x8A(타이틀)는 지시대로 제외. 소리만 27 §11-2 에서 대조돼 있고 곡 진행 상태 대조는 하지 않았다.

### 7-4. 판정
켜진 14곡 가운데 0x8C(§4)와 이번 12곡은 **곡 진행·템포·루프 길이·루프 지점이 공개 에뮬 실행과 같다.** 0x8A 는 소리 대조만 있다. 단 (1) 프레임 표본이라 모든 틱을 본 것은 아니고 (2) 곡을 원작 장면이 아니라 직접 명령으로 걸었으며 (3) 음색(합성기)은 §9 의 차이가 남아 있다.

## 8. 미확정 3곡 0x82·0x85·0x98 (작업 ②)

### 8-1. "1틱 끼워 넣기"의 정체 — 드라이버 판독
Z80 드라이버를 디스어셈블해 읽었다(`analysis/scripts/z80dis.py`, 드라이버 0x0000~0x105B).

```
0871: ld hl,$1C14 / ld a,(hl) / or a / ret z      ; 지연 카운터가 0 이면 기능 없음
0877: dec (hl) / ret nz                           ; 곡 틱마다 1 감소
0879: ld a,($1C15) / ld (hl),a                    ; 0 이 되면 N 으로 되돌리고
087D: ld hl,$1C4B / ld de,$0030 / ld b,$0A        ; 곡 트랙 10개($1C40~$1DF0)의
0885: inc (hl) / add hl,de / djnz $0885           ; 남은 길이(+0x0B)를 1 늘린다 = 전 트랙이 1틱 쉰다
```
- `$1C14/$1C15` = 곡 머리의 +5 바이트(곡 시작 0x0576~0x057C). 곡 머리 표 = Z80 0x8004 의 워드(뱅크 0x0F, §2-1 의 "미판독" 해소).
- 즉 **N 틱마다 한 번 모든 트랙이 함께 1틱 쉰다**(템포 미세 조정). 악보 한 바퀴가 M 악보 틱이면 드라이버 틱으로는 M·N/(N−1) 이고, 이 값이 정수가 아니면 쉬는 위치가 바퀴마다 달라져 전체 주기가 (N−1)/gcd(M, N−1) 바퀴가 된다.
- 곡별 N(곡 머리 판독): 0x82=14, 0x83=10, 0x85=12, 0x86=9, 0x87=19, 0x88=3, 0x8B=3, 0x8D=8, 0x8F=3, 0x90=5, 0x91=7, 0x92=7, 0x93=7, 0x95=3, 0x96=7, 0x97=5, 0x98=15, 나머지(0x81 0x84 0x89 0x8A 0x8C 0x8E 0x94)=0. 이미 확정된 루프 곡은 전부 루프 길이 P 가 N 의 배수다(0x83 10240/10, 0x86 4536/9, 0x87 8512/19, 0x88 5616/3, 0x8B 2304/3, 0x96 1792/7 등) = 한 바퀴로 딱 떨어지는 곡들이었다.
- `loop_exact.py` 가 세 곡을 못 잡은 이유 둘: (가) 0x82·0x85 는 주기가 600초 실행 범위 밖 (나) 곡 진행 상태에 **쓰지 않는 트랙의 `+0x0B`** 까지 넣었는데 위 루틴이 쓰지 않는 트랙도 계속 늘린다(0x98 의 PSG 트랙 `$1D9B/$1DCB/$1DFB`). 소리와 무관한 번지다. `loop_exact.py` 는 고치지 않았다(확정된 21곡의 판정 경로를 건드리지 않으려고). 세 곡은 아래 도구로 처리했다.

### 8-3. 0x82 는 한 파일로 루프를 만들 수 없다
- 9트랙(`$1C40 $1C70 $1CA0 $1CD0 $1D00 $1D60 $1D90 $1DC0 $1DF0`) + 지연 카운터만 보면 틱 2488 부터 **48384틱(766.6초 = 13바퀴 = 14 × 3456)** 으로 반복한다(실측, 56418틱 확인). 이전 문서의 계산값 "약 12.8분"은 이것이다.
- 그런데 **FM6 트랙(`$1D30`, 곡 데이터 Z80 0x882D~0x88B4)만 한 바퀴가 3438 악보 틱**이다. 나머지는 3456. 드라이버 틱으로 3702.43 대 3721.85(실측 평균), 13바퀴 합 48132 대 48384(실측, 정확히 14 × 3438 과 14 × 3456). FM6 트랙만 따로 보면 48132틱 주기로 반복한다(실측).
- 공개 에뮬에서도 같다: BizHawk 덤프만으로 잰 한 바퀴 간격이 `$1C70` 3533.76프레임(= 3721.87틱), `$1D30` 3515.32프레임(= 3702.45틱). 자작 Z80 의 오류가 아니라 **원작 곡 데이터가 그렇게 돼 있다**(FM6 파트가 바퀴마다 약 19.4틱 = 0.307초씩 앞으로 당겨진다).
- 전체가 처음 상태로 돌아오려면 lcm(3456, 3438) = 660096 악보 틱(본 트랙 191바퀴 = FM6 192바퀴)에 지연 위상 13배 = 8,581,248 악보 틱 = 9,241,344 드라이버 틱 = **약 40.7시간**(계산값, 실행으로 확인할 수 없는 길이).
- 따라서 "한 바퀴 루프"도 "전체 주기 파일"도 원작과 같지 않다. 한 바퀴 루프는 2바퀴째(약 59초 뒤)부터 FM6 파트의 위치가 원작과 0.3초씩 벌어진다(1틱 흔들림 수준이 아니다).
- 원작과 같게 내는 방법은 둘뿐이다: (가) 드라이버 + YM2612 를 브라우저에서 실시간 합성 (나) 줄기 2개(FM6 / 나머지 9트랙)를 따로 렌더해 각자 주기로 반복 재생. (나)도 줄기당 13바퀴(약 762.6초·766.6초)가 필요해 파일이 크다(계산값 약 13MB × 2). 어느 쪽도 `audio.js` 재생 구조를 바꿔야 한다. → **0x82 는 켜지 않았다.**

## 10. 효과음이 곡 FM 채널을 가로채는 원작 동작 (작업 ④)

판독 = Z80 드라이버 디스어셈블(`analysis/scripts/z80dis.py`) + 68k 0x16B6/0x16CE. 실측 = 자작 Z80 실행(`tools/bgm/sfx_steal_probe.py` → `analysis/data/35_bgm_oracle/sfx_steal_probe.json`). 공개 에뮬에서의 실측은 하지 않았다.

### 10-1. 명령이 들어오는 길
| 단계 | 내용 | 근거 |
|---|---|---|
| 68k 큐 | `jsr $16B6`(d0 = ID) → 큐 `$E610`(8칸, 꽉 차면 버림). VBlank 마다 0x16CE 가 **가장 나중에 넣은 것 1개**를 꺼내 `$A01C0A` → `0B` → `0C` 가운데 비어 있는 첫 칸에 쓴다(셋 다 차 있으면 버림) | 68k 0x16B6~0x1714 |
| Z80 접수 | 메인 루프가 돌 때마다 0x088A: 칸 3개를 차례로 읽고 비운다. bit7 이 선 값이면 우선순위 표(Z80 0x81F9, 인덱스 ID−0x81)와 현재 우선순위 `$1C19` 를 견줘 **현재 값보다 낮으면 버리고, 같거나 높으면** `$1C09`(처리할 명령 1칸)에 넣고 `$1C19` = 표 값 & 0x7F | Z80 0x088A~0x08BD |
| 처리 | 타이머 B 틱(약 128Hz)·타이머 A 틱(곡 틱)마다 0x0511 이 `$1C09` 를 처리. 같은 틱 사이에 통과한 명령이 여럿이면 **마지막에 통과한 것만** 남는다 | Z80 0x0511, 실측 E |
| 범위 | 0x81~0x9F 곡 / 0xA0~0xC5 효과음 / 0xD0~0xDF 특수 효과음(표에 쓸 만한 항목은 0xD0 하나, 0xC4 와 같은 데이터) / 0xE0 페이드 / 0xE1 전부 정지 / 0xE2 PSG 소거 / 0xE3 특수 효과음 정지 | Z80 0x0519~0x0537, 표 0x0538 |
| 우선순위 표 | 곡 0x80(bit7 = 언제나 통과, 저장 값 0), 효과음 0xA0·0xA1 = 0x70, 0xAE·0xC5 = 0x78, 0xC2 = 0x79, 그 밖의 효과음 = 0x75 | Z80 0x81F9~ |
| 음성(`$A01BFF`) | 68k 0x2894 가 직접 쓴다. Z80 0x0FCF: 인터럽트를 막고 **0x07F2(전부 정지: 곡·효과음 상태를 모두 지움)** 뒤 DAC 로 표본을 다 낼 때까지 드라이버가 멈춘다. 끝나도 곡은 되살아나지 않는다 | Z80 0x0070, 0x0FCF~0x104B (판독만, 실측 안 함) |

### 10-2. 채널 배정
- 곡 트랙(0x30 바이트): `$1C40` 리듬 순서(소리 없음, 드럼을 `$1D60`·`$1DF0` 에 건다) / `$1C70` FM1 / `$1CA0` FM2 / `$1CD0` FM4 / `$1D00` **FM5** / `$1D30` **FM6** / `$1D60` FM3(드럼) / `$1D90` PSG1 / `$1DC0` PSG2 / `$1DF0` PSG3(잡음 드럼). 표 0x05EE·0x05FC.
- 효과음 트랙: `$1E80`(FM3) `$1EB0`(FM5) `$1EE0`(FM6) `$1F10`(PSG1) `$1F40`(PSG2) `$1F70`(PSG3), 특수 효과음 트랙 `$1E20` `$1E50`. 표 0x06E7·0x06F7·0x0707.
- **이 게임의 효과음 38개(0xA0~0xC5)는 전부 FM5 하나, 또는 FM5+FM6 둘만 쓴다**(효과음 머리 판독). FM5+FM6: 0xAA 0xAB 0xAE 0xAF 0xB0 0xB1 0xB2 0xB3 0xB5 0xBB 0xBC 0xBE 0xC4. 나머지 25개는 FM5 만. PSG·FM3 를 쓰는 효과음은 없다. 효과음 트랙은 타이머 B(약 128Hz) 박자로 진행한다(곡은 타이머 A).

### 10-3. 가로채기 규칙
1. **시작**(0x060B~0x0691): 효과음의 트랙마다, 그 채널의 곡 트랙 `+0` 의 **bit2 를 켠다**(= 가로채임). 효과음 트랙을 새로 채우고 그 채널을 키 오프, SSG-EG 레지스터를 0 으로. 같은 채널에서 먼저 울리던 효과음이 있으면 그 자리(같은 트랙)를 덮어쓴다 = 앞 효과음은 그 채널에서 끊긴다.
2. **가로채인 동안**: 곡 트랙은 **계속 진행한다**(데이터 포인터가 효과음이 없을 때와 모든 프레임에서 같음 — 실측 A). 다만 그 채널로 가는 쓰기가 전부 막힌다: 음색·음량·주파수 쓰기(`rst $10` → 0x04AB `bit 2,(ix+0)` 이면 버림), 키 온·오프(0x0419·0x0429 `and $06`), 페이드의 음량 갱신(0x07E1). = **그 채널의 곡 소리만 사라지고 박자는 흐른다.**
3. **끝**(효과음 트랙의 끝 명령 0xF2 → 0x0E2C): 현재 우선순위 `$1C19` = 0, 같은 채널에 특수 효과음이 살아 있으면 그쪽에, 아니면 곡 트랙에 채널을 돌려준다 = bit2 를 끄고 **그 트랙의 음색을 다시 써 넣는다**(0x0E8C~0x0E9C: 음색 번호 `+8` → 0x04EC, FM3 이면 특수 모드 레지스터 0x27 도 복구, SSG-EG 가 있으면 복구). **키 온은 하지 않는다** = 곡의 그 채널은 다음 음표가 시작될 때 다시 들린다(울리고 있던 긴 음은 되살아나지 않는다).
4. **우선순위**: 효과음이 울리는 동안 `$1C19` 는 그 효과음의 값. 더 낮은 효과음 명령은 버려진다(실측 B: 0xAA(0x75) 중 0xA0(0x70) → 무시). 같거나 높으면 받아들여 그 효과음이 쓰는 채널을 덮어쓴다(실측 C: 0xAA 중 0xAE(0x78) → 교체, `$1C19` = 0x78). **트랙 하나라도 끝나면 `$1C19` 가 0 이 된다** — FM5+FM6 효과음에서 한쪽이 먼저 끝나면 그때부터 낮은 효과음도 통과한다(판독).
5. **새 곡 명령**: 0x07F2 로 작업 영역을 전부 지우므로 **울리던 효과음도 함께 끊긴다**(실측 D). 0xE1 도 같다(판독).
6. **0xE0 페이드**(0x0783~0x07F1): 시작 순간 `$1C40`(리듬)·`$1D60`(FM3 드럼)·`$1D90`·`$1DC0`·`$1DF0`(PSG 3개) 트랙을 **즉시 끄고 PSG 를 소거**한다(실측: 곡 0x81 에서 명령 2프레임 뒤 다섯 트랙 0, PSG 에 9F BF DF FF). 그 뒤 곡 틱 3개마다 FM 트랙의 음량을 1단계씩 40단계 내리고 끝나면 전부 정지. 가로채인 채널은 음량 갱신을 건너뛴다. → **웹은 지금 곡 전체를 같이 페이드한다(`audio.js` `fade_sec`). PSG·드럼이 바로 끊기는 원작과 다르다(이번에 발견, 미수정).**
7. 실측 A(곡 0x81, 300프레임째 0xAA): 곡 FM5·FM6 트랙 bit2 가 300~311프레임(12프레임) 동안 켜짐, 같은 구간 효과음 트랙 재생, `$1C19` = 0x75, 끝난 뒤 0. 300~420프레임의 FM5 키 온 수 = 효과음 없음 7 / 있음 9(효과음 자신의 3 포함 → 곡 키 온 1개가 막힘).

### 10-4. 지금 구조와의 차이
| 원작 | 웹(미리 렌더한 파일을 섞음) |
|---|---|
| 효과음이 나는 동안 곡의 FM5(와 FM6) 소리가 빠진다 | 곡 전체가 계속 들린다 |
| 낮은 우선순위 효과음은 무시, 같은 채널의 앞 효과음은 끊긴다 | 인트로 효과음만 한 번에 하나(`solo:'intro'`), 경기 효과음은 겹쳐 난다 |
| 페이드 때 PSG·드럼 즉시 끊김 | 전체 페이드 |
| 음성이 나면 곡·효과음 전부 정지 | 따로 처리(곡은 이벤트 표대로 페이드·정지) |

### 10-5. 설계안(구현하지 않음)
- **안 A: 줄기 렌더**. 곡을 3줄기로 따로 렌더한다 — ① FM5 트랙만 ② FM6 트랙만 ③ 나머지(FM1·2·3·4 + PSG). 같은 레지스터 쓰기 열에서 채널별로 걸러 libgme 에 넣으면 된다(`render.py` 에 채널 거르개 추가, 공통 레지스터 0x22·0x27·0x28·0x2B 는 줄기마다 유지). 재생 때 3줄기를 같은 시각에 시작해 같은 루프 지점으로 돌리고, 효과음이 시작되면 그 효과음이 쓰는 채널(§10-2: FM5 또는 FM5+FM6)의 줄기 이득을 0 으로, 효과음 길이가 지나면 **그 줄기의 다음 키 온 시각**(렌더 때 줄기별 키 온 시각 표를 함께 뽑아 둔다)에 이득을 1 로 되돌린다. 우선순위(낮으면 무시·같은 채널 교체)는 `sfxmap.js`/`audio.js` 에 표로 넣는다.
  - 같은 구조로 페이드도 고칠 수 있다(③을 FM 줄기와 PSG+드럼 줄기로 더 나눠 페이드 때 뒤쪽을 즉시 끊음 → 4~5줄기).
  - 비용: 곡 파일과 디코딩 메모리가 줄기 수만큼 는다(크기 미측정). 줄기 합이 한 번에 렌더한 것과 같은지(합성기의 채널 합이 선형인지)는 렌더해서 수치로 확인해야 한다(미확인).
  - 한계: 0x82(§8-3)는 이 안으로도 풀리지 않는다(줄기를 각자 주기로 돌리는 것까지 넣어야 한다).
- **안 B: 실시간 합성**. Z80 드라이버와 YM2612·PSG 합성기를 브라우저(AudioWorklet)에서 돌린다. 가로채기·우선순위·페이드·0x82 의 어긋남·음성 때의 전부 정지가 전부 원작 그대로 나오고 곡 파일이 필요 없어진다. 비용: 합성기 코어 이식(가장 큼, 라이선스 확인 필요), 모바일 CPU, §9 의 음색 차이를 합성기 선택으로 다시 맞춰야 함.
- 권고: 원칙("원작과 완전히 동일")을 끝까지 지키려면 안 B 뿐이다(0x82 포함). 안 A 는 가로채기·페이드까지는 해결하지만 0x82 가 남는다. 둘 다 `audio.js` 재생 구조 변경(윤프론)이라 결정 사항으로 둔다.

## 12. 사용자 판단이 필요한 것 (2차 갱신)
1. **0x85(스토리 10번째 경기·웹 stage 08)**: (가) 한 바퀴 루프 1.13MB 로 켠다 — 권고. 2바퀴째부터 15.8ms 이하 미세 타이밍만 원작과 다름 / (나) 전체 주기 9.91MB(디코딩 약 198MB)로 켠다 — 원작과 같음, 모바일 메모리 미확인 / (다) 무음 유지. 후보 파일 둘 다 준비돼 있고 절차는 §8-6.
2. **0x82(스토리 4~7번째 경기·웹 stage 02~05, 무음 4곳)**: 미리 렌더한 파일 하나로는 원작과 같게 낼 수 없다(§8-3). (가) 무음 유지 / (나) 한 바퀴 루프로 켜되 FM6 파트 위치가 원작과 달라짐을 받아들임(후보 파일은 만들지 않았다) / (다) 실시간 합성 또는 두 줄기 재생으로 구조 변경(§10-5).
3. **고음 필터**: `bgm/` 대 `bgm_lpf/` 를 들어 보고 교체 여부 결정. 교체하면 효과음도 같은 필터로 다시 렌더해야 한다(§9-4).
4. **효과음의 곡 채널 가로채기·페이드 때 PSG·드럼 즉시 끊김**: 안 A(줄기) / 안 B(실시간 합성) / 지금대로(§10-5).
5. 0x98 은 쓰는 장면이 확인되면 바로 연결할 수 있다(루프·렌더 완료).
6. 27 §8 의 청취 확인 항목은 그대로 남아 있다.
