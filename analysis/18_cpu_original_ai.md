# 18. 원작 CPU AI 해독과 웹 반영 (2026-11-17)

표기: [확인]=ROM 판독+에뮬 관측 일치, [관측]=에뮬 실측만, [미해결]. 스크립트는 analysis/scripts/t_cpu_def.py, t_cpu_off.py, t_cpu_idle.py, t_cpu_pick.py (오라클 = m68k.py, 시작 상태 ctrl0.pkl/play0.pkl). 웹 측정은 tools/cpu_catch.mjs, cpu_idle.mjs, cpu_pickup.mjs.

## 1. 확정 규칙
| 항목 | 원작 근거 | 내용 |
|---|---|---|
| 두뇌 구조 | ROM 0xBBEE plan 표(0x00~0x4C) | CPU 팀의 "활성 선수"(타입 0x70)만 plan 상태기계(`$5E`)를 돌린다. 나머지 내야(타입 0x20)는 수동 핸들러 0x8D02. plan 0 = 결정 단계(0xBC42). [확인] |
| 방어 결정 | 0xD5F0, 0xD4F6 (AI 파라미터 b9..b12) | 상대 투구 시작(상대 sub 0xC, 릴리스 약 10f 전)에 8비트 난수 1회를 b9,b10,b11,b12 누적 임계값과 비교해 5택: 0 서있기(plan 0x34), 1 캐치(0x38), 2 웅크리기(0x3C), 3 점프(0x40), 4 옆걸음(0x44). 리그 모드($E697)는 무조건 캐치(0xD612). 25팀 전체 평균 확률 서있기 17%, 캐치 43%, 웅크리기 10%, 점프 16%, 옆걸음 14%. [확인, 에뮬 trace 30회에서 결정 분포·plan 일치] |
| 행동 개시 조건 | 0x6CE8(히트박스 겹침), 히트박스 12 = 64x64, 13 = 160x160 | 결정 후 plan 핸들러는 속도 0 으로 대기하다가 공이 선수 중심 +-32px 상자(점프는 +-80px)에 들어오면 sub 0x14(캐치)/0x18(웅크리기)/점프/sub 8(옆걸음)로 진입(0x77D4/0x77F8/0x770C). 거리·접근시간 계산은 없다. [확인] |
| 캐치 성공 | 0x8CF0 | 캐치 자세 타이머 창(기존 문서 04 와 동일). |
| 수동 내야 | 0x8E82, 0x90A6 | 비활성 내야는 투구 공이 상자에 들어오면 웅크린다. 결정 확률 없음. [확인] |
| 내야 이동속도 | 0x9E2A / 0x9E62 / 0x22DA | 일반 이동 (s2*16+0x140)/256 px/f(s2=10 이면 1.9), 빠른 이동(sub 8) (s2*16+0x300)/256 px/f(3.6). 속도를 즉시 설정(가속 없음). [확인 ROM, 관측 평균 이동속도 내야 2.33 외야 2.16 px/f] |
| 대기 위치 | 0x8F52, 표 0x9E92~0x9F11(좌석0, 좌석1 은 0x9F12~) | 공 구역에 따라 8점 표에서 난수로 1점 선택(팀원과 중복 회피 0x9012), sub 8 로 빠르게 이동, 도착 후 타이머 $18=60f 마다 1/2 확률로 재선택(0x8EDE). 구역 변경 시 즉시 재선택. [확인] |
| 공격 | 0xBD3A plan 4, 0xD6CA/0xD69C | 공을 가진 활성 선수는 발사선(좌석0 x=224, 좌석1 x=288; y 는 자기 y, 0x30~0xD8)으로 이동해 도착하면 상대 조작 선수(`$18(상대 사이드)`)를 목표로 투구 sub 0xC. 투구 종류는 b2..b5(0xD496)로 5택(서서/점프/대시 등), 공격 3택 b0,b1(0xD474). 공 소지 후 릴리스까지 중앙값 103f(투구 14회, 최소 40 최대 143; 내야 94~143, 외야 40~74). 필살기 사용이 투구의 대부분(내야 11/14). [확인 구조, 관측 수치] |
| 정지율 | t_cpu_idle.py, 700f AI 대 AI | 이동 비율 내야 약 37%, 외야 약 11%, 정지 구간 중앙값 44~58f. |

## 2. 웹과의 차이와 원인
| 항목 | 종전 웹 | 원작 | 조치 |
|---|---|---|---|
| 방어표 | b2..b5(공격표)를 방어에 사용 -> 캐치 구간 평균 9%, 웅크리기 50~70% | b9..b12, 캐치 43% | ai.js 가 b9..b12 사용 [원인=파라미터 매핑 오류(버그)] |
| 캐치 시점 | 도달시간 trig(trigShift -6..-2) -> 접촉 후 버튼(성공 26%) | 상자 +-32px 진입 즉시 | 상자 진입 시 입력으로 교체 |
| 방어 대기 | 선수가 배회하며 이동 -> 슛이 빗나감 | 결정 후 제자리 대기 | 방어 결정 선수는 제자리, 상대 차지 중 내야 정지 |
| 이동 속도 | 걷기 0.5~0.75 px/f | 1.9 / 3.6 px/f | `rules.cpu.origSpeed`, 레벨 플래그 `origSpeed` |
| 내야 대기 | 홈 슬롯 +-16px 배회 | 구역별 8점표 + 빠른 이동 | ai.js idlePoint (표 이식) |
| 공격 | 지연 20+b13*4+rand 후 제자리 투구 | 발사선까지 달려가 투구 | 도착 후 지연(발사선 이동 중 타이머 정지) |
| 난이도 | blunder/catch256 등 자작 가공 | 팀·선수별 파라미터만 | L2/L3 blunder=0, catch256=0. L1 만 blunder 60 유지(캠페인 초반 보호, 원작 근거 없음) |

## 3. 전/후 지표 (헤드리스, 웹)
- 사람 슛 vs CPU 좌석1 (tools/cpu_catch.mjs, n=100~150, 차지 8). 전(점프볼 직후 공중 선수 아티팩트가 있는 하네스, 참고용): L2 캐치시도 16% / 성공 4%, L3 22% / 4%. 후(하네스 수정, 같은 코드 경로): L1 34% / 31%, L2 49% / 43%, L3 49% / 43%, 기본 AI 52% / 45%. 에뮬 원작(30회, 대상 team1 선수0, 차지 8): 캐치 13 / 피격 5 / 빗나감(웅크리기·점프 회피) 12 = 43% / 17% / 40%.
- 정지율(tools/cpu_idle.mjs, 3000f x3 시드): 전 내야 40% 외야 30%, 평균 이동속도 0.60 px/f -> 후 내야 50% 외야 24%, 이동속도 내야 2.5 외야 1.6 px/f. 원작 37% / 11%, 2.3 / 2.2 px/f. 외야 이동 비율은 원작보다 높고 속도는 낮다(외야 이동 규칙 미해독 = [미해결]).
- 정지 공 줍기(tools/cpu_pickup.mjs, CPU 대 CPU, 시드 6): 내야 구석 28~31f, 외야 띠 17~18f, 외야 후방 40f, 상대 코트에서 넘어온 공 16f, 실패 0. (원작 비교값은 analysis/15 §7 의 55~90f(정지 타이머 30f 포함)).
- 사람 좌석 시나리오: 사람이 조작 중인 선수는 자동 줍기 안 함(원작 규칙, 문서 11 §3)이라 공 가장 가까운 선수가 조작 선수면 동료는 줍지 않는다 -> 구석 공은 사람이 A 로 줍기 전까지 정지(6/6 실패). 원작도 동일한 구조로 판독되나 동료 CPU 의 개입 여부는 [미해결].

## 4. 미해결(추정으로 채우지 않음)
1. 외야 두뇌(타입 0x24/0x28, ROM 0x9128/0x92A8) 이동·줍기 규칙 미해독. 웹 외야는 기존 outChase 자작 규칙 유지.
2. 투구 종류 선택(b2..b5 의 plan 0x04/0x08/0x0C/0x10/0x14 세부), 패스 선택(b0,b1,b6..b8), 필살기 사용률(원작 AI 투구 14회 중 내야 11회 필살기)은 웹 미반영(specialChance256 기본 0).
3. 웹 자작 규칙 중 원작 근거 없는 것: ctrlSwitch.tickFrames 12, predictRest, stallGuard, autoPickup stillFrames 15, L1 blunder.
4. 사람이 투구할 때 CPU 조준 대상 선택 규칙(`$E21E`), 수동 내야의 정확한 대기 이동은 일부만 확인.
5. 캠페인 승률은 재측정하지 않았다(CPU 방어가 크게 강해졌으므로 하락 예상, 확인 필요).
