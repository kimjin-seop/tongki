## 1. 경기 후 승/패 대사 (서브 9, 0x12672~0x12A0E)

### 1-1. 데이터 상태 [확정: 파일 확인]
- `data/rom_derived/story_dialogue_jp.json` 과 `server/data/story_dialogue_ko.json`(= `public/assets/rom/story/story_dialogue_ko.json`, sha256 같음) 모두 `matches[k].blocks.win`·`blocks.lose` 가 15경기 전부 있다. 선택 표: 승리 0x752C2, 패배 0x752D2 → 블록 4k+2 / 4k+3 → 포인터 표 0x752E2 [판독 0x12422~0x1244A].
- 승/패 판정: `$E68A == 0xE700`(1P 쪽 승리)면 승리 표 [판독 0x12428].
- 이어지는 세그먼트: k=2 승리(팀 그림 장면 1페이지), k=14 승리(엄마 장면 7페이지)가 `segments[1]` 로 들어 있다.
- 지금 화면은 자작 대사(`campaign_dialogue.json` `winPost`/`losePost`)를 쓴다(`story.js showPost()`).

### 1-2. 경기별 화자·초상 슬롯 (원문 화자 id, 16진)
| k | 승리 후(페이지별 화자) | 패배 후 | 오른쪽 초상 |
|---|---|---|---|
| 0 | 1,1,0,1,0,1,0 | 1 | opp_01 |
| 1 | 2,2,0 | 2 | opp_02 |
| 2 | 3,3,0,3,0 → **팀 그림** 13 | 3 | opp_03 → 팀 그림(§3-1) |
| 3~13 | 상대 1페이지(id = k+1) | 상대 1페이지 | opp_{k+1} |
| 14 | F,0,F,0 → **엄마 장면** 10,0,10,F,10,0,0 | F | **taiga_15**(아래) |

- 초상 로드는 경기 전과 같은 0x12450 이다: 오른쪽 = `0x60F72[k+1]`, 입 `0x6381E[k+1]`, 팔레트 `0x74A62[k+1]`, 입 애니 2(k+1) [판독 0x14080]. 따라서 k<14 는 경기 전과 같은 그림.
- **k=14 는 경기 후·맞대면 모두 `taiga_15`**: 0x60F72[15] = 0x60FAE, 0x6381E[15] = 0x6385A, 0x74A62[15] = 0x74A9E, 입 애니 0x1E. 경기 전 대사 둘째 세그먼트에서 바꿔 넣는 그림과 같은 주소다 [판독, 주소 일치].
- 입 슬롯: 0 = 왼쪽(통키), 0x10(엄마) = `$CA80`(엄마 초상의 입), 0x13(みんな) = `$C800`+`$CA80`(팀 그림의 입 둘), 그 밖 = 오른쪽. `story_intro.js slotOf` 는 지금 0x10 을 입 없음으로 둔다 → 엄마 그림이 생겼으므로 바꿔야 한다.
- 타이핑음: 0x10 = 0xA8, 그 밖 경기 후 화자는 0xA7/0xB6(48 §2-2 표, `sfxOf` 그대로).

### 1-3. 화면 흐름 [판독]
| 순서 | 원작 | 근거 |
|---|---|---|
| 진입 | 승리 **0x98** / 패배 **0xE1(즉시 정지)** | 0x1268A, 0x12694 |
| 전환 | 코트 다시 그림(선수 없음) → 32프레임 동안 화면 아래로 32px 스크롤(VSRAM 0 → −32, 1px/f), 위 검은 띠(320x32)가 위에서 1px/f 로 내려오고 아래 검은 띠(320x88)가 3px/f 로 올라옴 → 창 켬(레지스터 0x12=0x91) → 아래 띠 끔 → 초상 켬 | 0x1269C~0x126D8, 0x12906~0x1296E. 띠 = 객체 8개(0x14174), 타일 0x44C = 색 2(검정, 0x10CDA·0x12540) 단색 |
| 대사 | 경기 전과 같은 루틴(0x1205C), 같은 속도·입·타이핑음 | 0x12718 |
| 끝: 패배 | 페이드 없이 바로 서브 10(컨티뉴 창, 같은 화면 위) | 0x12798 |
| 끝: 승리 | k=2 → 팀 그림 장면, k=14 → 엄마 장면(§3). 그 밖: 화면 전체 페이드 아웃 약 32f + **0xE0**(단 k=6 은 0xE0 없이 7번째 승리 이벤트로) | 0x12792~0x127D4, 0x12748 |
| 다음 | k+1 이 3·11 → 세이브 창, 7 → 7번째 승리 이벤트, 14 → 세이브 창, 15 → 엔딩(서브 12), 그 밖 → 제목 카드(k≤6) / 세계 지도(k 7~13) | 0x118C6~0x1191E |

### 1-4. 구현 명세
- `showPost` 를 `introScene` 계열 장면으로 바꾼다: `segments = ko.matches[k].blocks[win ? 'win' : 'lose'].segments`, 오른쪽 초상은 경기 전과 같은 `portraits.json matches[k]`(k=14 는 `taiga_15` 고정).
- 세그먼트 1(이어지는 장면)으로 넘어갈 때 §3 의 그림 교체를 한다. 지금 `runScene.rightName()` 은 `right[seg]` 를 쓰므로, 경기 후용 오른쪽 지정(예: `post: [{seg:0, portrait:'opp_03'}, {seg:1, extra:'team3'}]`)을 화면 코드에서 따로 둔다.
- 머리 `.scene-cap`(경기 N·승리/패배 태그)은 원작에 없다 → 넣지 않는다(48 §7-1 ⑤ 와 같은 이유).
- 버튼(`다음 경기`/`재도전`/`챕터 목록`)은 대사가 끝난 뒤 지금처럼 창 안에. 원작 흐름과의 차이는 §7.
- 진입 전환(32f 스크롤 + 검은 띠)은 선택 사항. 우리 대사 장면이 원작 배치(검은 띠·VSRAM −32)를 그대로 그리지 않으므로(초록 창 사용), 넣는다면 배경 위치를 32px(배율 적용) 내리는 CSS 전환으로 충분하다.

## 2. 맞대면 (서브 7, 0x12592~0x12670)

### 2-1. 화면 구성 [판독]
- 진입(보통 경로): 0x1236E(코트 배경 = 경기 스테이지, 창 레지스터 0x12=0x91, VSRAM −32, 맞대면 표 0x752B2 선택) → 초상 객체 지움 → 0x12450(초상·팔레트) → **8프레임 페이드 인**(0x2562, 막힘형) [0x125A4~0x125C0].
- 이 설정 루틴은 경기 전 대사(서브 3)와 **같다**. 차이는 대사 표(0x752B2)와 페이드 인 길이(경기 전 약 32f, 맞대면 8f)뿐이다. 초상 위치도 같다: 왼쪽 (16,160) 통키, 오른쪽 (264,160) 상대 [판독 0x14080 + 기존 실측 48 §10-3]. 기존 캡처 `st_04_sub7_faceoff.png`(코트 위 얼굴 두 개 + 하단 창)와도 맞다.
- 오른쪽 초상: k<14 는 opp_{k+1}, **k=14 는 taiga_15**(§1-2, 15전 맞대면 화자는 0x0F 다이가).
- 화자: k=0,1,3~13 은 통키 1페이지(「いくぞ、たいが!」 형식), k=2 는 3→0 두 페이지, k=14 는 F→0 [확정: 원문 JSON].
- 앞 화면: 편성 COM(서브 6) 끝 0xA1 + 8f 페이드 아웃(0x14CA2, 0x256C). 15전은 라인업 뒤 편성 2장을 건너뛰고 바로 맞대면(0x147E6 `$E448`) [판독 + 32 문서 확인].
- 재도전(컨티뉴 はい)으로 들어온 15전은 `$E449` 가 서 있어 **설정·페이드 없이** 컨티뉴 창이 있던 화면 위에서 바로 대사를 찍는다(0x12B42 → 0x1259E). 이때 곡은 없다(서브 9 진입 0xE1 뒤).

### 2-2. 끝 전환 [판독 0x125D8~0x12670]
| 시점 | 동작 |
|---|---|
| 블록 끝 버튼 | **0xE0**(BGM 페이드 시작), 초상 객체 5개 끔($C700~$C900), 아래 검은 띠 6개 켬, 창 끔(레지스터 0x12=0x00) |
| 다음 32프레임 | 매 프레임 VSRAM +1(−32 → 0, 화면이 위로 32px), 위 띠 −1px, 아래 띠 +3px(화면 밖으로) = 코트가 경기 화면 위치로 올라가며 검은 띠가 열린다 |
| 32프레임 뒤 | 서브 8(경기 시작). 페이드 아웃 없음 |

### 2-3. 구현 명세
- `introScene(k, m, onDone)` 을 그대로 쓰고 `segments = m.blocks.faceoff.segments` 만 바꾼다. 오른쪽 초상 지정만 k=14 에서 `taiga_15`.
- 흐름: 경기 전 대사 → (규칙 창: §5 결정) → 라인업 → 편성 1P·COM(15전 생략) → **맞대면** → 경기. 지금 `lineup onExit` → `start(rules)` 사이에 맞대면을 넣는다.
- 끝: `app.bgm(null)`(0xE0) → 32f 전환(선택) → `campaign_start`. 경기 화면은 입장 0x95 를 지금처럼 낸다.
- 페이드 인 8f(경기 전보다 짧음). 건너뛰기·Esc 는 경기 전과 같게.

## 4. 챕터 목록 부제

- 원작 스토리에는 챕터 목록 화면이 없다(서브 0 = `はじめから/つづきから` 창, 28 §3-1). 원작 텍스트 중 대응되는 것은 **제목 카드 부제 15개**뿐이다(ROM 그래픽, 맵 0x743FE[k] + 타일 0x6E1EE, 48 §3).
- 번역은 이미 `story_dialogue_ko.json matches[k].title_ko.subtitle` 에 있다(예: 「타이거에게 도전」).
- 명세: `story.js showList()` 의 `titles`(지금 `data.campaign.dialogue` 의 자작 `title`)를 `Intro.loadKo()` 의 `title_ko.subtitle` 로 바꾼다. 상대 팀명 줄은 유지. 미확정 번역 3개(49 §6 #1~#3)는 카드와 목록이 같은 문자열을 쓰므로 한 번만 확정하면 된다.

## 5. 자작 규칙 창 (48 §8 #3)

### 5-1. 원작 사실
- 스토리 서브 표(0x11840) 23개 중 규칙 창은 없다. 경기 전 흐름은 제목 카드(2) → 대사(3) → 라인업(4) → 편성(5·6) → 맞대면(7) → 경기(8) [판독, 32·48 확인].
- 스토리 경기는 시계가 줄어도 끝나지 않는다(`$E680==1` 모드만 시간 종료, 05 문서 [확인], 26 §298). 규칙은 체력제(ノックアウト).
- 규칙 창(ルール/しあいじかん)은 1PvsCOM·1Pvs2P 에만 있다(28 §3).

### 5-2. 권고
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A(권고)** | 스토리 흐름에서 규칙 창을 빼고 `rules:{time:0}`(무제한) 고정 | 원작과 같다(원작 동일 원칙). 0x91 이 끊길 일이 없다 | 28 §8 의 "기본 5분 유지" 결정을 번복. 무제한 캠페인 난이도·경기 길이 미측정(31 P1: k13·k14 aggr75 의 53~55% 가 시간 종료로 갈렸음) |
| B | 규칙 창 유지, 곡만 유지 | 사용자가 시간을 고를 수 있음 | 원작에 없는 화면이 남음 |

- A 를 택하면 서버는 이미 `time:0` 을 받는다(`RULE_TIMES=[0,3,5,8]`). 자작 안전망 30분 무승부 상한은 그대로 둔다(28 §10-1).
- A 전에 임밸런 측정 1회 권장: `LIMIT=0 node tools/campaign_remeasure.mjs 60 aggr50,aggr75 8 14`(31 P1).
- 설명 문구가 필요하다면(시간 제한 없음 안내 등) 원작에 없으므로 넣지 않는다.

### 6-2. verified 승격 판단
- 조건(`tools/bgm/build_manifest.py` 머리): ① 루프 확정 ② 수치 대조 ③ 장면 연결(ROM 호출 지점 [확인]/[코드] + 웹 대응 장면).
- `python -I -B tools/bgm/build_manifest.py --pending`(파일 쓰기 없음) 이번 실행 결과: 0x91·0x98·0x90·0x92 모두 PASS(루프/1회 판정).
- **0x91: ①②③의 ROM 쪽 근거 충족.** 남은 것은 웹 화면(카드 → 대사 → 라인업 → 편성 → 맞대면)이 만들어진 뒤 곡이 끊기지 않고 맞대면 끝에서 페이드되는지 실화면 확인(강화면) 1회. 그 뒤 `PENDING` → `SCENES` 이동 + `build_manifest.py` 실행(박백엔).
- **0x98: ROM 근거 충족, 메모리 결정 필요.** 파일 289.2초(4.88MB ogg)라 디코딩 메모리가 약 102MB(0x85 의 198MB/560초 와 같은 계산). 루프 자체가 273.8초라 한 바퀴 파일로 줄일 수 없다. 0x85 를 크기 때문에 HOLD 한 것과 같은 판단이 필요하다(§10 결정 #3).

### 6-3. 지금 코드 동작 [확정: 소스 읽음]
- `app.go()` 는 화면을 mount 한 **뒤** `screenBgm(view, data)` 를 부른다(`public/js/main.js` 44~53행). 후보가 없으면 `audio.bgm(null)` = 0xE0 페이드.
