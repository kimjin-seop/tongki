## 5. 운영 DB 적용 절차서 — `db.js` 마이그레이션 v2 (flame 표 2개)

**실행은 사용자 승인이 있어야 한다. 이 절은 절차만 적은 것이고, 2026-11-19 현재 운영 DB 에는 적용하지 않았다.**

무엇이 바뀌나: 새 코드로 서버가 뜨는 순간 `server/store/db.js migrate()` 가 운영 DB 에 표 `flame_profiles`·`flame_runs` 를 만들고(`CREATE TABLE` 2개, 한 트랜잭션) `schema_version` 에 `2` 를 넣는다. 기존 표·행은 건드리지 않는다. 따로 돌릴 SQL 은 없다(서버 시작이 곧 적용이다).

아래에서 `<DB>` = 운영 DB 파일(환경변수 `DB_PATH`, 기본 `data/tongki.db`), `<이름>` = 운영 pm2 프로세스 이름, `<시각>` = 작업 시각 표기.

1. **사전 확인**(읽기만): Node 22.5 이상인지, `<DB>` 위치, 디스크 여유(DB 크기의 3배 이상), 현재 버전 `SELECT MAX(version) FROM schema_version` = 1 인지.
2. **정지**: `pm2 stop <이름>`. 프로세스가 내려간 것을 확인한다(WAL 이 마지막으로 반영되고 파일이 더 바뀌지 않게). 접속 중이던 경기는 끊긴다 → 사용자가 없는 시간에 한다.
3. **복사**: `<DB>`, `<DB>-wal`, `<DB>-shm` 세 파일을 **같이** 백업 폴더로 복사한다(있는 것만. 셋 중 하나만 복사하면 복원 때 최근 기록이 빠진다). 복사본 sha256 을 적어 둔다.
4. **리허설(임시 포트·복사본)**: 백업과 별도로 복사본을 하나 더 만들어 `DB_PATH=<리허설 복사본> PORT=<쓰지 않는 임시 포트> node server/index.js` 로 띄운다. 운영 포트·운영 DB 는 건드리지 않는다. 확인할 것:
   - 시작 로그에 오류가 없다.
   - `SELECT MAX(version) FROM schema_version` = 2, `SELECT name FROM sqlite_master WHERE name LIKE 'flame_%'` = 2줄.
   - 기존 표 행 수가 적용 전과 같다: `accounts`·`auth_tokens`·`progress`·`leagues`·`ratings`·`rank_games`·`meta` 각각 `SELECT COUNT(*)`.
   - 임시 포트에 붙어 기존 계정 로그인, `flame_get`(빈 상태), `flame_new` 가 된다.
   - 리허설 서버를 끄고 **같은 복사본으로 한 번 더** 띄워 다시 뜨는지 본다(마이그레이션이 두 번 돌지 않는다).
   리허설에서 하나라도 어긋나면 여기서 멈춘다. 운영 DB 는 아직 그대로다.
5. **적용**: 새 코드를 놓고 `pm2 start <이름>`(또는 `pm2 restart <이름>`).
6. **재시작 확인**: 시작 로그에 오류 없음, 4번의 SQL 확인(버전 2·표 2개·기존 행 수), 기존 계정 로그인·기존 모드 한 판 시작, `flame_get`. 그다음 `pm2 restart <이름>` 을 한 번 더 해서 다시 뜨는지 본다.
7. **되돌리기**(문제가 있을 때). 둘 중 하나:
   - **(가) 통째 복원** — 적용 뒤 쌓인 기록을 버려도 될 때: 서버 정지 → `<DB>`·`-wal`·`-shm` 을 지금 것을 따로 치워 두고 3번의 백업 세 파일로 바꾼다(셋을 같이. 백업에 없던 `-wal`·`-shm` 이 지금 폴더에 남아 있으면 안 된다) → 옛 코드로 시작.
   - **(나) 표만 걷어내기** — 적용 뒤의 계정·진행·랭킹 기록을 살려야 할 때: 서버 정지 → 한 트랜잭션으로 `DROP TABLE flame_runs; DROP TABLE flame_profiles; DELETE FROM schema_version WHERE version = 2;` → 옛 코드로 시작. **세 문장을 반드시 같이 한다.** 표만 지우고 `schema_version` 의 2 를 남기면 다음에 새 코드가 떴을 때 마이그레이션을 건너뛰어 표가 없는 채로 `flame_*` 가 전부 실패한다. 반대로 2 만 지우고 표를 남기면 새 코드가 `CREATE TABLE` 에서 "이미 있음"으로 시작하지 못한다. 이 방법은 그동안 쌓인 flame 저장(코인·도전)을 지운다 → 지우기 전에 두 표를 따로 덤프해 둔다.
   - 표 2개를 그냥 남겨 두고 옛 코드만 되돌리는 것도 된다(옛 코드는 두 표를 읽지 않고, `schema_version` 이 2 로 남아도 동작에 영향이 없다). 가장 손이 덜 간다.
8. **기록**: 실행 시각·백업 위치·해시·확인 결과를 `docs/HANDOFF.md` 에 적는다.

주의
- 운영 DB 에 대한 쓰기·DDL 이므로 최디비의 사전 검토(표 2개 생성의 잠금·소요) 뒤에 한다.
- 저장 형식 v2(§4 B21): 새 코드가 쓴 flame 저장은 v1 코드가 `FLAME_SAVE_NEWER` 로 거절한다. 운영에 flame 이 처음 나가는 것이라 v1 저장은 없다.
- 격리 행: `flame_runs`·`flame_profiles` 의 `flame-broken:%`·`guest-aside:%` 키는 보존용이다. 정리(삭제)는 따로 승인받아 한다.
