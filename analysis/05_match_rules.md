# 05. 매치 규칙 (2단계) - 코드 해독 + 자작 68000 에뮬레이터 실행 검증

표기: [확인]=코드 직접 판독 + (가능하면) 에뮬레이터 실행으로 일치 확인 / [코드]=코드만 읽음, 실행 미검증 / [추정] / [미확인].
도구: `analysis/scripts/m68k.py`(순수 파이썬 68000+VDP 메모리/DMA+패드), `vdprender.py`(화면 렌더), `drv.py`(입력/상태 조작), `state/*.pkl`(저장 상태).
이 ROM 을 에뮬레이터로 실제 구동해 타이틀, 메뉴, 이야기 모드 1경기(상태 0x14)까지 진입, 화면이 정상 렌더됨을 확인했다.
04_rules.md 정정: ① 0x18000 표는 팀 색/몸통 그룹이 아니라 **슬롯별 기본 조준 그룹**(행0/1=사이드0/1: 내야→그룹4 등). ② 0x30744~0x335E6 은 로고가 아니라 **선수 몸통 타일**. ③ 0x4EFFE 의 63타일은 HUD 얼굴 아이콘(VRAM 0x680/0x6C0), 필드 선수 머리는 0x40300 스트림.
메인 메뉴 5모드 이름은 화면 렌더로 확인: 1)倒せ!闘球の強豪たち(스토리) 2)1P vs COM 3)1P vs 2P 4)闘球リーグ 5)炎の猛特訓(특훈). (상태 0x9C/0xA4/0xAC/0xB4/0x94 순)

## 1. 시간/좌표
- 60fps. 시계 $E685=분,$E686=초,$E687=프레임(60). 스토리 1경기 3:00 시작 [확인]. 제한시간 종료 판정은 **$E680==1 이고 $E220==0 일 때만**(0x5618) [코드]; 스토리(E680=0)에서는 시계가 줄어도 종료되지 않음 [확인: 3:00→2:04 진행 중 경기 계속].
- 위치/속도 16.16. 화면 y = obj.y/2 - obj.z + 0xE0, x = obj.x - 카메라 + 0x80. 중력 $E200=0x3000(0.1875/f²) [확인].
- 코트 이동 한계: x 0x10~0x1F0, y 0x10~0xF8 (0x7F8E) [확인]; 팀별 허용영역은 0x6E00 계열 표(구간 $E256..).

## 3. 승패 [확인]
- 사이드 구조체 $E700/$E780 의 +0x57 = **남은 인원**(초기 7; 모드에 따라 1). 선수 1명이 "아웃"될 때마다 -1(0x958A). **한쪽이 0 이 되면 즉시 승패**: 0x528E 가 승자/패자 포인터($E68A/$E68C/$E698/$E69A)를 세팅하고 $E602=0x24. 에뮬레이터에서 잔여를 1/1 로 놓은 AI 대 AI 경기로 `0x00→0x24→0x10→0x30→$E600=0x9C` 전이 실측.
- 시간 종료 승패는 위 표(0x28), 스토리 모드는 시간 종료 없음. 포기(일시정지 메뉴)는 위 0x04.

## 4. 능력치 이름 확정 (에뮬레이션/코드 대조)
| 항목 | 결론 |
|---|---|
| s0 | **HP**. 피격 시 감소, 0 이하면 아웃 [확인] |
| s1 | **방어력**: 데미지 = max(0, 공 위력 - s1) [확인 0x853E] ($E680≠0 이면 데미지 0, 피격=즉시 아웃 규칙) |
| s2 | **이동속도**: 이동 속도 기저 s2<<12, 가속 s2<<7 (0x7FEA), 속도 상한 3.0px/f [확인] |
| s3 | **점프력**: 점프 초기 vz = 0x10000 + (s3<<12), 달리는 중(대시) +0x10000 [확인 0x7E66; 실측 vz=3.75] |
| s4 | **공격력**: 위력 = s4 (+s4/4 점프 중) (+s4/4 대시 중) + 차지(≤15) [확인 0x89AA; 실측 28~48] |
| s5 | **캐치 지속 프레임**: B(무공) 시 캐치 자세 s5 프레임 [확인: 실측 s5=10 → 타이머 9] |
| s6 | 투구 속도(공 +0x74 = s6<<4 (+0x100 점프/ +0x100 대시, +차지<<4)) [코드 0x7D0C] |
| s7 | 패스 속도(s7<<4) [코드 0x72BC] |
팀 레이팅(0x3460)은 표시/난이도용 추정 그대로.

## 5. 입력 매핑 (기본 컨피그 $E692=0, 0x2728 은 A/B/C 순열만 바꿈) [확인: 버튼별 에뮬레이션]
패드 비트: bit4=B, bit5=C, bit6=A. 방향=bit0~3, Start=bit7.
| 상황 | C | B | A | 방향 |
|---|---|---|---|---|
| 공 없음 | **점프** | **캐치 자세**(대형 히트박스 idx11, s5 프레임) | 공이 굴러가는 중이면 **웅크리기(회피)** 30f(히트박스 z높이 24→8, idx3); 공이 정지해 있으면 15f 줍기/잡기 시도 | 이동(8방향, 내야); 같은 방향 **더블탭=대시**($E69… 16f 윈도, 0x780E) |
| 공 보유 | 점프 | **투구**(대상=$E21E) | **패스**(대상=$E214, 같은 편) | 방향 = 조준 그룹 선택(아래) |
| 점프 중 공 보유+B | | 공중 투구(서브 0x24): B 를 누르고 있는 프레임수 = 차지(1프레임씩, 최대 15, 16 이면 자동 발사) | | |
- 외야 선수(타입 0x34/0x38)는 한 축으로만 이동(상·하 라인=가로, 후방=세로) [확인 0x82A4/0x82D6].
- **조준 그룹**(0x8088/0x80A8, 사이드 미러): 방향키 → 상대 슬롯 그룹: 상대 쪽(좌우)=내야 슬롯0~3(그룹0), 위=외야 상단 4~6, 아래=외야 하단 7~9, 반대쪽=후방 10~12. 그룹 내에서는 거리 최근접(0x8752). 방향 없으면 마지막 방향 유지/슬롯 기본값(0x18000 표). 투구 후 공중에서 방향키로 궤적 보정: ↑vy-0x1000/f, ↓+0x1000, →vz+0x1000, ←vz-0x2000 ($E234, 0xA46A) [확인 구조].
- 공을 20초(1200f=$5E>0x4B0) 쥐면 강제 투구 [코드 0x76A4].

## 6. 필살기 [확인: 존재]
- **존재한다.** 공중 투구(C 점프 후 B)에서 차지 카운터가 **13~15 일 때 B 를 떼면**(윈도 = 15-$E69E ~ 15, $E69E 기본 2, 0x8CF0) 공 타입이 일반(0x14)이 아니라 **특수 공 0x90** 이 되고 공 태그($14)=필살기 ID 가 설정된다. 에뮬레이션: 차지 6~12 → 타입 0x14(위력 41~47), 13 → 타입 0x90(태그 22 = 팀0 선수0 의 표 값 22 와 일치) [확인]. 16 이상이면 자동 발사지만 윈도 밖.
- 필살기 ID: ROM 0x18732 (팀*8+선수, 바이트, 25팀; 값 -1(0xFF대)=무작위 32종표 0xB82E) → `analysis/data/special_shots.csv`. 위력 표 0x187FA[ID] (0x32~0x58, 즉 50~88). 일반 투구 위력은 20~50대 [확인].
- 불가 조건(0x8BEE) [코드]: $E680≠0(규칙 모드) 시 일반만, 외야 슬롯(≥4)은 일반만, 리그 모드($E697≠0)는 ID 0x16 고정, $E694≠0 이면 항상 필살. 특수 공 비행 패턴은 핸들러 0xADB8 이하(ID별 0xB89C~ 변형)로 [미해독, ID별 궤적].

## 7. 선수 상태 머신 (타입 = $0(obj)&0x7FFC → 핸들러 0x6D4 표; 서브 = $16(obj) 하위바이트)
타입: 0x10 사람 내야(7040), 0x20 CPU 내야(8D02), 0x24/0x28 CPU 외야 상하/후방(9128/92A8), 0x34/0x38 사람 외야 상하/후방, 0x70/0x74 CPU "활성 선수 두뇌"(내/외), 0x6C 사람 점프볼(7B04), 0x88 CPU 점프볼, 0x30 패스 수신 대기(935C), 0x3C 피격 날아감(946A), 0x40 쓰러짐 60f(94DA), 0x44, 0x48 선 밖/반칙(974C), 0x4C 아웃 이동(986E). 0x821C 가 사람→CPU 형, 0x8228 이 CPU→조작 형(0x4C28 표: 0x10/0x34/0x38 사람, 0x4C42: 0x70/0x74 CPU 활성) 로 바꾼다 [확인: 표 덤프].
**서브(0x7040 계열)**: 0x00 이동/대기 · 0x04 점프(공중, z<0 착지→0x83DA) · 0x08 **대시**(속도 가속 3.0px/f 까지, 방향 떼면 0x28) · 0x0C 투구 실행 · 0x10 패스 실행 · 0x14 캐치 자세(B, s5f; 매프레임 히트박스 idx11 로 공과 충돌시 0x73AC 잡기) · 0x18 웅크림(A, 30f) · 0x1C 줍기/잡기(A, 공 정지시, 15f 후 idx11 충돌 검사) · 0x20 넉백 미끄러짐($68 거리, 마찰 $E22C) · 0x24 공중 투구 차지 · 0x28 제동/착지 후 정지 [확인].
- **점프/회피**: 점프(C)는 z 로 공을 넘김, 웅크림(A)은 히트박스 z범위를 8로 줄임. 충돌 = 0x6C44: x,y AABB(표 0x69D8, idx=$4(obj)) + z 구간(표 0x6A60 [zoff,zlen]) 모두 겹침 [확인].
- **캐치**: 상태 0x14/0x1C 중 공(생존, 상대 편, 위험 플래그 $3 bit6/7)과 충돌 시 0x73AC: 공 방향과 선수 방향 비교(0x8416)가 **서로 정면이면 캐치 성공, 같은 방향(등 보임)이면 피격**(0x84AC). 성공: 공 타입 4(보유), 보유자 지정, 조작 선수 전환(0x8574), 상대 최근접 내야에게 조작 이전 [코드+관측].
- **피격(0x84AC)**: 데미지 d=max(0,공위력-s1) → 내야만 HP-=d(0 클램프), 공은 타입 0x1C(바운스)로 되튕겨 vz=3.0, 피격자는 타입 0x3C(넉백, vz 4.0)→착지 0x40(60f)→0x950C: HP>0 면 일어서서 경기 지속(코트 안이면), **HP==0 이면 아웃(0x9568)**: 외야에서 생존자 중 하나와 슬롯 교환(0x8930; 아웃자는 외야(슬롯4~)로, 외야 선수는 내야로 들어옴, 둘 다 타입 0x4C 로 이동), $57-1 [확인: 관측 obj3(hp0) slot3→slot4 / obj4 slot4→slot3, 약 70f 후 복귀 타입 0x20]. 외야 생존자가 없으면 교환 없이 퇴장 [코드].
- **선 이탈(0x48)**: 착지 후 허용영역 밖(0x6D90)이면 타입 0x48(30f 정지, 공 보유 시 공을 놓음 0x97B4) 후 제자리 복귀(0x9E2A) [코드+관측: 점프볼 때 중앙선 넘으면 발생].
- **공 핸들러**: 0x18(A516)=패스류 비행(위력 3 고정), 0x14(A428)=투구 비행(방향키 보정), 0x1C(A54E)=바운스/굴러감(서브0 바운스: vx,vy>>1, vz=-vz-(vz>>$E22A); 서브4 정지 후 30f 마다 외야 습득 0x85CC; 서브8 0x86A6), 0x4=보유(손 위치 표 0x39F6C), 0x68=티프오프, 0x90=필살기. 투구 비행 중 바닥 닿으면 한 번 튕김(a7CC: vz=2.0) 후 0x1C. 벽(x 0x10/0x1F0, y 0x10/0xF8)에서 반사(속도 반전, 1/4~1/2) [확인].
- **외야→복귀**: 외야에 나간 아웃 선수는 $1F=1(사망)로 표시되어 교환 대상에서 제외; 생존 외야는 공을 받으면 공 습득 상태 0x4C 가 아닌 0x50 역할 오브젝트(0x530A)로 활성. 아웃자가 다시 경기에 복귀하는 규칙은 **없음**으로 보임(잔여 $57 은 증가하지 않음) [코드; 미실행 검증].
- **조작 선수 전환(커서 $C800/$C880, 타입 0x2C, 핸들러 0xDA26)**: 별도 수동 전환 버튼은 **없다**(경기 중 입력은 Start 외에 위 표뿐). 자동 전환: 공이 정지/바운스 종료 시 0x85CC 가 각 사람 사이드에서 (방향키를 누르고 있지 않다면) 공과 가장 가까운 선수로 조작권 이전(0x88B8: $18(사이드)=새 선수, 구/신 선수 타입을 0x821C/0x8262 로 교체); 패스 수신 시 수신자(타입 0x30→캐치), 캐치 시 캐치한 선수가 조작권을 가짐 [코드]. **구역별 전환·A 줍기 실측은 11_ctrl_switch_pickup.md** [확인].

## 8. 에뮬레이터로 검증한 것 / 남은 것

## 9. 스프라이트 조립 [확인: 에뮬레이터 객체 14개×3상태 모두 일치]
`scripts/build_sprites.py` → `gfx/sprites/`: team_00..24.png(+preview_*.png), anims.json, teams.json, palettes.json, manifest.json.
- 몸통: ROM 0x2FE00 → 3 클래스 애니표(0x2FE0C/0x2FF38/0x30064), 선수별 클래스=ROM[0x18008+팀*7+선수]. 애니 레코드 [수][속도]+프레임포인터(수=0이면 단일 프레임). 프레임 [n-1][히트박스 idx]+6B 조각 [y][size][tile.w][x][xflip x]. 반전은 xf 사용+H-flip.
- 몸통 타일: 6개 스트림을 VRAM 타일 0x270,0x2EF,0x341,0x3D9,0x429,0x4DB 에 적재(디코드 결과 VRAM 과 바이트 일치).
- 머리: 팀별 스트림 ROM 0x40300[팀] → VRAM 타일 0x100(사이드0)/0x1B8(사이드1). 머리 프레임 5개/선수 = ROM[0x4D15C+팀*4].l + 선수*0x14; 포즈 = 바이트 0x1E10[애니>>1]/4; 머리 위치 = 0x40000[클래스] 표의 애니·프레임별 (dx,dy); 앞뒤 = 0x1EB8 표 바이트(1=머리가 위).
- 팔레트: ROM 0x2FAEE(팀당 16워드, 사이드0=CRAM라인0, 사이드1=라인1). 색 변환 (v&7)*36 (VDP 3비트).
- 애니 id(byte 오프셋) 이름은 코드 사용처 기반 [추정 일부]: 00/02 걷기, 04 대시, 06/08 투구, 0E/10 서있기, 12/14 점프, 16/18 웅크림, 1A/1C 피격, 1E 쓰러짐, 20/22 캐치, 28/2A 패스, 2C/2E 공중투구, 0A/0C/24/26 미확인. 짝수/홀수 = 앞/뒤(y방향 $3 bit1).

## 바운스 보정 메모 (2026-11, 박백엔)
- ROM 바운스(0xA6C2/0xA77A): `vz = -vz - (-vz >> $E22A)`(산술 시프트, 시프트값은 스테이지표 0x54E8)은 엔진과 같다. **다른 점 2개** [확인: 0x1DEA, 0xA6E4~0xA6F2]: (1) ROM 은 매 프레임 `vz -= g` 를 먼저 하고 `z += vz`(반암시적)인데 엔진은 `z += vz` 후 `vz -= g`; (2) ROM 정지 임계는 `cmp.l $E200(=중력 0x3000), d3` 즉 반발 속도 <= 12288 이면 정지인데 엔진 `ballPhys.settleVz` 는 76000 [추정].
- 엔진의 이산화 때문에 bounceShift 3(스테이지 5,6,12)은 기존 적분(z+=vz 후 vz-=g)에서 반발 속도가 약 137,600 에 수렴해 공이 영원히 튀었다(LOOSE 중앙값 612f, 바운스 23회, 경기가 5분 제한까지 감).
- **적용(2026-11, match.js)**: `bounceShift >= ballPhys.romMinShift(3)` 스테이지의 굴러가는 공(LOOSE)에만 ROM 방식 적용: `vz -= g` 후 `z += vz`, 정지 임계 `ballPhys.romSettleVz=12289`(반발 속도 <= 중력 0x3000 이면 정지). 투구 비행(FLY)·shift 1,2 스테이지는 종전 그대로(settleVz 76000). 이전의 단조 감소 클램프(`ball.bv`)는 제거.
- 선택 근거: 전 스테이지 ROM 방식(순서+임계)을 시도하면 shift 2 스테이지 LOOSE 중앙값 186→134f(-28%), 첫 바운스 높이 20.6→15.4px(-25%)로 일반 거동이 달라져 불채택(대안 a). shift 3 스테이지만 적용하면 LOOSE 중앙값 612→214f, 바운스 23→12회, 정지까지 599→201f(최대 1026→416f). shift 1·2 스테이지(0~4,7~11,13)의 시뮬레이션 해시는 불변, 해시가 바뀌는 스테이지는 5,6,12(캠페인 k6,k7,k13,k14). 측정 도구: `tools/ball_sim.mjs`.
