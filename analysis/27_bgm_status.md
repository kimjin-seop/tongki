# 27. 원작 BGM 이식 상태 (2026-11-18)

사용자 요청: BGM 도 원작 그대로. 이 문서는 곡별로 "원작 루프·길이·템포대로 나오는가"를 수치로 확인한 결과와, 장면별 곡 연결(ROM 판독), 켜 둔 곡·꺼 둔 곡의 근거를 적는다.
**실제 청취는 하지 않았다(§8 사용자 확인 목록).** 백업: `_backup/bgm_before/`.

## 1. 요약
> **2026-11-18 밤 2차 갱신(박백엔, 상세 `analysis/35_bgm_port_plan.md` §7~§12)**: 켜진 14곡 중 13곡(0x8A 제외)이 공개 에뮬(BizHawk)과 곡 진행 상태·소리 대조를 통과. **0x85·0x98 은 루프 확정**(33408틱 529.340초 / 17280틱 273.796초), **0x82 는 FM6 트랙만 한 바퀴가 짧아 한 파일 루프 불가**(전체 주기 약 40.7시간, 계산값). 켠 곡 수는 그대로 14(0x85 는 파일 크기 결정 대기, 0x98 은 장면 미확정). 아래 본문에서 이 세 곡에 대한 옛 서술("루프 추정·미확정", "13바퀴 주기")은 이 갱신이 우선한다.

- 원작 곡 24개(0x81~0x98) 중 **루프·종료 지점 확정 23곡(루프 17 + 1회 6), 루프를 만들 수 없는 곡 1(0x82)**. (2차 갱신 전: 확정 21, 미확정 3)
- 그중 **장면 연결까지 끝나 켠 곡 14개**: 0x81 0x83 0x84 0x86 0x87 0x88 0x89 0x96(경기 곡 8), 0x8A(타이틀), 0x8B(라인업·편성), 0x8C(모드 메뉴·팀 선택), 0x95(입장), 0x8E·0x93(결과).
- 꺼 둔 곡 10개: 0x82(한 파일 루프 불가), 0x85(루프 확정, 파일 크기 결정 대기), 루프는 확정됐지만 웹에 대응 장면이 없거나 원작 장면이 확인되지 않은 8(0x8D 0x8F 0x90 0x91 0x92 0x94 0x97 0x98).
- 결과적으로 **무음인 경기**: 0x82 를 쓰는 스테이지 4곳(웹 stage 02·03·04·05, 스토리 4~7번째 경기), 0x85 를 쓰는 1곳(웹 stage 08, 스토리 10번째 경기). 자작 곡으로 메우지 않았다.
- 이전 상태의 문제 2가지를 바로잡았다.
  1. 이전 문서의 "루프 확정 6곡"은 실제로는 **끝나는 곡 6개(루프 없음)** 였고, 루프 곡 18개는 전부 미확정이었다(`analysis/data/rom_audio.json` 의 `loop_confident`).
  2. 이전 렌더(ffmpeg libgme)는 **시간축이 2049/2048 배(0.0488%) 늘어져 있었고 앞 무음이 잘려** 루프 지점(초)이 파일과 맞지 않았다. 지금 파일은 보정했다(§2-3).

## 2. 오라클과 검증 방법
오라클 = **ROM 의 Z80 사운드 드라이버 자체**(ROM 0x7DE0C)를 자작 Z80 에뮬레이터(`analysis/scripts/z80snd.py`)로 실행해 얻은 YM2612/PSG 레지스터 쓰기 열. 소리 합성만 ffmpeg(libgme)에 맡긴다. 공개 에뮬레이터 녹음과의 대조는 하지 않았다.
(2026-11-18 밤 추가: 0x8C 한 곡은 공개 에뮬(BizHawk)과 곡 진행 상태·소리를 대조했다. 루프 4회 동안 진행 상태·템포·루프 길이 일치, 4kHz 위 대역은 우리 쪽이 셈. `analysis/35_bgm_port_plan.md` §4.)
(2026-11-18 밤 2차 추가: 켜진 나머지 12곡 0x81 83 84 86 87 88 89 8B 8E 93 95 96 도 같은 방법으로 대조했다 — 전 곡 루프 2회 이상(1회 곡은 끝까지) 틱 어긋남 0, 웹 루프 길이 = 원작, 창별 지연 −2~+1ms. 0x8A 는 소리 대조(§11-2)만 있다. 35 문서 §7. 고음 대역 차이의 주된 원인은 기준 에뮬의 출력 저역 통과 필터로 확정, 35 문서 §9.)

### 2-1. 드라이버 구조(이번에 판독·실측)
- 메인 루프(Z80 0x0084~)는 YM2612 상태 포트의 타이머 오버플로 비트를 폴링한다.
  - **타이머 A**(bit0): 0x00C0(재장전, 값 = `$1C04/05`) → 0x00EC. **곡 진행은 이쪽**이다. 타이머 A 값은 곡마다 다르다 = **곡 템포**(아래 표의 "타이머 A"). 1틱 = (1024 − 값) × 144 / 7,670,453 초.
  - **타이머 B**(bit1): 0x00DA(재장전, 값 = `$1C06` = 230 고정, 약 128Hz) → 0x072A/0x0511/0x0116. 변조·음량 변화 같은 고정 주기 처리.
- 트랙 구조체: `$1C40` 부터 0x30 바이트 간격. `+0` bit7 재생 중, `+2` 템포 분주, `+3/+4` 데이터 포인터, `+9` 호출 스택 포인터, `+0x0B` 남은 길이, `+0x0C` 저장 길이, `+0x0D/0E` 주파수, `+0x22~0x27` 변조 상태, `+0x28~0x2F` 반복 카운터·호출 스택. [실측: `$1C70` 필드 덤프]
- 명령(Z80 `$1C0A` 에 기록, 68k 는 `jsr $16B6`): 0x81~0x98 곡, **0xE0 = 페이드 아웃**(곡 틱 3개마다 음량 1단계(0.75dB)씩 40단계 = 30dB, 곡 틱 120개 ≈ 1.7~2.1초 뒤 정지), **0xE1 = 즉시 정지**, 0xE3 = 곡에 영향 없음, **새 곡 명령 = 이전 곡을 즉시 끊고 시작**(겹침 없음). [실측: 0x8C/0x81/0x8B 재생 중 명령을 넣고 레지스터 쓰기 관찰]

### 2-2. 루프 확정(`tools/bgm/loop_exact.py`)
1. 타이머 A 처리 직전(Z80 0x00A9)마다 작업 RAM `$1C00~$1EFF` 를 저장한다.
2. **곡 진행 상태**(타이머 A 경로에서만 바뀌는 번지 전부)가 간격 P 틱으로 **한 주기 이상 그대로 반복**되는 가장 이른 틱 S 를 찾는다 → 루프 시작 S, 길이 P. 드라이버는 결정적이므로 상태가 같으면 이후도 같다(level `full-state`).
3. 끝나는 곡: 상태가 더 변하지 않거나(level `full-state`), 모든 트랙의 재생 중 비트가 꺼진 틱(level `track-flags`).
4. 교차 확인: 1회차 [S, S+P) 와 2회차 [S+P, S+2P) 의 **키 온/오프(YM 0x28) 쓰기 열과 PSG 쓰기 열이 완전히 같은지** 비교. 루프 15곡 모두 일치했고, 타이머 B 쪽 번지까지 포함한 RAM 전체도 모든 틱에서 일치했다(`full_ram_equal_tick_ratio` 1.0).

주의: 여기서 S 는 "상태가 처음으로 주기적이 되는 틱"이다. 0x88 처럼 악보상 되돌이 지점(약 14.6초)보다 늦게(70.0초) 잡히는 곡이 있다. 길이 P 는 같고, 늦은 쪽을 쓰면 틀릴 일이 없으므로 그대로 썼다(파일이 길어지는 대가).

### 2-3. 오디오 대조(`tools/bgm/render.py`)
- libgme 시간축 보정(합성 클릭 41개·200초로 실측, FM·PSG 공통, 잔차 0.06ms 이하): ① 앞 무음을 잘라 내므로 로그 시각 0 에 PSG 표식음을 넣어 기준점으로 삼고 곡은 0.5초 뒤에 둔다 ② 출력이 2049/2048 배 늘어지므로 2048/2049 로 리샘플한다.
- 곡을 2회차 끝까지 렌더해 1회차와 2회차를 비교한다.
  - **스펙트로그램 상관**(10ms 간격, 위상 무시): 0.93~0.97. 대조군(2회차를 0.5초 어긋나게 놓음): 0.43~0.67.
  - **루프 길이 오차**(음 변화량 열의 교차상관이 최대인 지연, 1ms 단위): **15곡 모두 0ms**. (시간축 보정 전에는 6~19ms 어긋났다.)
  - 이음매 앞뒤 0.5초 스펙트로그램 상관: 0.93~0.97.
  - 파형 그대로의 상관은 0.49~0.93 으로 낮다. 타이머 A(곡 틱)와 타이머 B(변조)의 어긋남 때문에 FM 위상이 회차마다 달라서이며 원작 실기도 같다.
- 파일 구성: 0 ~ S+P+2.25초. 재생 루프 구간 = [S+2, S+P+2]. 2초 민 이유는 되돌아갈 때 인트로 꼬리음이 아니라 루프 끝 음의 잔향이 이어지게 하기 위해서다. 구간 길이는 P 그대로다.
- ogg 디코딩 길이·파형이 원본 wav 와 일치(상관 0.987 이상), 클리핑 0.

### 미확정 3곡의 사실
> 2차 갱신(35 문서 §8): 아래 "드라이버가 가끔 1틱을 더 끼워 넣는다"의 정체는 **곡 머리 +5 의 값 N 틱마다 전 트랙이 1틱 쉬는 템포 지연(Z80 0x0871)** 이다(0x82 N=14, 0x85 N=12, 0x98 N=15). 0x85 는 11바퀴 = 33408틱, 0x98 은 17280틱으로 정확히 반복한다(실행 확인). **0x82 의 "13바퀴(48,384틱)"는 9트랙에만 맞고, FM6 트랙은 한 바퀴가 18악보 틱 짧아 전체는 반복하지 않는다** — 아래 0x82 서술의 "한 바퀴를 잘라 반복하면 음표는 같다"는 0x82 에는 틀리다(FM6 파트 위치가 바퀴마다 0.3초씩 달라진다). 0x98 이 600초에도 안 잡힌 것은 쓰지 않는 PSG 트랙의 카운터 때문이었다.

- 600초(약 3만 8천 틱)를 돌려도 곡 진행 상태(트랙별 포인터·길이·반복 카운터·호출 스택)가 반복되지 않았다.
- 트랙별로 보면(300초 실행, `tools/bgm/track_periods.py`):
  - **0x82**: 리듬 쪽 트랙 2개(`$1C40`, `$1D60`)는 2016틱(31.94초) 주기로 9회 이상 반복. 나머지 선율 트랙 8개는 300초 안에 주기가 없다. 이전 문서의 "루프 0.02~31.97초"는 리듬 트랙만 본 값이었다.
  - **0x85**: `$1D60` 트랙만 2304틱(36.5초) 주기, 선율 트랙 9개는 300초 안에 주기 없음.
  - **0x98**: 리듬 트랙 360틱(5.70초), 선율 트랙 17280틱(273.8초 = 리듬의 48배)로 보이나 한 주기 남짓만 확인됐다.
- 데이터 포인터가 뒤로 되돌아가는 틱을 420초 동안 추적한 결과(트랙별 되돌이 시점, 실측):
  - **0x82**: 선율 트랙(`$1C70` 등)의 전체 되돌이(`8614>85BF`)가 틱 3723, …, 26054 에 7번 = **한 바퀴 평균 3721.83틱(58.97초)** 이고 바퀴마다 길이가 1틱씩 다르다. 리듬 트랙(`$1C40`)은 155틱 패턴을 돌되 평균 155.08틱(13패턴마다 1틱 추가 = 2016틱). 선율 한 바퀴 = 리듬 24패턴이다.
    → 곡은 처음부터(인트로 없이) 약 58.97초 단위로 되풀이되지만, **드라이버가 가끔 1틱(15.8ms)을 더 끼워 넣는 위치가 바퀴마다 달라** 상태가 정확히 같아지려면 13바퀴(48,384틱 = 766.6초)가 필요하다 [13바퀴 주기는 계산값, 미실행].
  - **0x85**: `$1D30` 트랙의 전체 되돌이(`9319>92B8`)가 틱 839, 3876, …, 25136 = 한 바퀴 평균 3037.1틱(48.1초), 역시 바퀴마다 길이가 다르다.
- 정리: 세 곡은 "한 바퀴를 잘라 반복"하면 음표는 같지만 1틱 흔들림의 위치가 원작과 달라진다. 원작과 완전히 같게 하려면 전체 주기(0x82 는 약 12.8분) 파일이나 실시간 합성이 필요하다. 어느 쪽으로 할지는 결정 사항이라 켜지 않았다(§8-6, §9).

## 5. 음량·효과음과의 믹스
- 원작에는 "BGM 음량 대 효과음 음량" 표가 따로 없다. 곡·효과음 데이터 안의 음량(TL·PSG 감쇠)이 그대로 칩에서 합쳐진다.
- 그래서 **BGM 과 효과음을 같은 이득으로 렌더**했다: 효과음 렌더의 공통 이득(+4.28dB, `rom_audio.json` 의 `sfx_gain_db`)을 BGM 전곡에 똑같이 적용. 이전에는 BGM 이 +2.72dB 로 따로 정규화돼 있어 효과음보다 1.56dB 작았다.
- manifest 의 gain: BGM 1.0, **ROM 렌더 효과음 전부 1.0**(이전 0.7~0.9 는 근거 없는 조정값이라 되돌렸다. 이전 값은 항목의 `gain_before_mix_fix` 에 남김). 합성 효과음은 건드리지 않았다.
- BGM 최대 피크 −1.32dBFS(0x88), 클리핑 0.

- **합산 피크(2026-11-18 실측, 브라우저 디코딩 뒤 최대 진폭 × manifest gain, `_verify/round32_bgm_review/result.json`)**: 곡 최대 0.894(−0.97dBFS, 0x88. ogg 디코딩 뒤 값이라 렌더 원본 −1.32dBFS 보다 조금 높다), 그 밖의 곡 0.26~0.81. 경기 중 효과음 최대 0.562(−5.0dBFS, FIGHT 음성 0x82), 캐치 0.536, 리시브 0.513, 투구 0.494. 인트로 효과음 최대 0.699.
  - 최악 합산(피크가 같은 순간에 겹친다고 가정): 경기 곡 + 효과음 1개 = 1.456(+3.3dBFS), 곡 + 효과음 3개 = 2.506(+8.0dBFS). 즉 **곡과 효과음이 겹치면 출력단에서 잘릴 수 있다**(실제 겹침 빈도·들리는 정도는 미측정).
  - 조치 보류: 마스터 앞 압축기·리미터나 일괄 감쇠는 원작 음량 균형을 바꾸므로 청취 없이 넣지 않았다. §8 의 8번으로 사용자 확인 대기.
  - **2026-11-18 갱신**: 사용자 청취 신고(인트로 소리 깨짐)로 출력 단에 이득 −4.28dB + 소프트 리미터를 넣었다. 위 수치는 그 전 값이다. 측정·근거·되돌리는 법은 §11.

## 6. 웹 적용
- **곡별 허용 목록 = `public/assets/manifest.json` 의 `bgm.*` 항목 중 `verified:true`**(25키, 14곡). `tools/bgm/build_manifest.py` 가 조건(루프 확정 + 수치 대조 통과 + 장면 연결)을 만족한 곡에만 키를 만든다. 키가 없거나 verified 가 아니면 `audio.js` 의 `bgmAllowed()` 가 막아 무음이다.
- `public/js/audio.js`: `BGM_ENABLED = true`, 새 곡 = 즉시 교체(이전의 0.6초 교차 페이드 제거), `bgm(null)` = 0xE0 페이드(항목 `fade_sec` = 곡 틱 120개, 30dB 계단 감소 뒤 끊김), `bgmStop()` = 0xE1.
- `public/js/game/sfxmap.js`: 화면 → 곡 표(`SCREEN_BGM`), 경기 곡 진행(`matchBgm`), 결과 곡(`playResult`). 대체 곡 연결(없으면 다른 곡)은 없앴다.
- `public/js/screens/game.js`, `main.js`, `intro.js`: 위 연결 호출.
- 파일: `public/assets/rom/bgm/XX.ogg|mp3`(gitignore). 0x82·0x85·0x98 파일은 이전 렌더 그대로이며 키가 없어 재생되지 않는다.
- 용량: 켠 곡 ogg 합계 약 17.5MB. 가장 긴 0x83 은 205초(디코딩 시 약 72MB 메모리).

- **리뷰 지적 반영(2026-11-18, 정검수 → 윤프론)**
  - 탭 숨김(컨텍스트 suspended) 중 받은 곡 명령: 숨김 중에는 `wantBgm` 만 바뀌므로, 복귀(`statechange`·`resume()`) 때 `syncBgm()` 이 "재생 중인 곡 키 ≠ wantBgm" 이면 `startBgm(wantBgm)` 을 부른다(정지 명령이면 0xE0 페이드). 1회 곡이 끝났을 때 다른 곡 명령이 남아 있으면 그 곡을 시작한다(로딩이 1회 곡보다 길었던 경우 포함). 이전에는 경기 곡이 결과 화면에서 계속 돌거나, 입장 곡 중 숨겼다 돌아오면 그 경기 내내 무음이었다.
  - 디코딩 버퍼 해제: 경기 곡(`bgm.stage.*`/`bgm.story.*`)은 재생이 끝나면(교체·페이드 종료·즉시 정지) `release()` 로 버퍼·파일 캐시를 버리고 다시 요청되면 새로 받는다. 타이틀·메뉴·편성·입장·결과 곡과 효과음은 유지. 같은 파일을 쓰는 다른 키가 재생·예약 중이면 파일 캐시는 남긴다.
  - 미리 받기: `matchBgm()` 생성(경기 화면 진입) 때 `audio.preload([경기 곡, 'bgm.enter'])`. manifest 의 `preload` 필드는 여전히 읽지 않는다(표시용). 미리 받고 쓰지 않은 경기 곡은 다음 `preload` 때 버린다.

## 8. 사용자 확인이 필요한 항목(실제 청취)
1. 켠 14곡이 기억하는 원작 곡과 같은가(음색 포함). 음색은 libgme 의 YM2612 합성에 달려 있고 대조할 기준 녹음이 없다.
2. 루프 이음매에서 끊김·튐이 들리는가(특히 0x8C 메뉴, 0x8B 편성, 0x96 마지막 경기).
3. BGM 과 효과음의 크기 균형. 효과음이 이전보다 커졌다(0.7~0.9 → 1.0).
4. 온라인 사람 대 사람 경기에서 진 쪽에도 승리 곡(0x8E)이 나온다. 원작(한 화면 2인) 규칙 그대로인데, 각자 화면인 온라인에서는 어색할 수 있다.
5. 경기 곡이 FIGHT 뒤 약 0.9초에 시작하는 타이밍, 입장 곡(0x95)과 그 사이 무음.
6. 0x82·0x85 스테이지 5곳을 무음으로 둘지, 한 바퀴 루프(음표는 같고 1틱 흔들림 위치만 다름)로 켤지. 스토리 화면 무음 유지 여부. → 2차 갱신: 0x85 는 한 바퀴 루프(1.13MB) / 전체 주기(9.91MB) 후보 파일이 준비돼 있다. 0x82 는 한 바퀴 루프가 원작과 다르다(FM6 파트). 선택지는 35 문서 §12.
7. 모바일(iOS 사파리·카톡 인앱) 실기기 재생, 긴 곡(0x83 205초) 로딩 시간·메모리.
8. 곡과 효과음이 겹칠 때 소리가 찌그러지는가(§5 합산 피크: 최악 +3.3dBFS~+8.0dBFS). 찌그러지면 마스터 앞 리미터를 넣을지, 전체를 일괄로 낮출지 결정.

## 11. 인트로 소리 깨짐 신고 조사와 출력 단 수정 (2026-11-18, 윤프론)
사용자 신고(실제 청취): "처음 인트로에 온갖 소리가 다 나오면서 다 소리가 깨진다". **청취는 하지 못했다. 아래는 전부 수치다.** 백업 `_backup/intro_audio_before/`, 자료 `_verify/round34_intro_audio/`.

### 11-1. 측정(headless Edge, 임시 포트 3395, 수정 전)
방법: 출력(destination)으로 들어가는 모든 연결을 측정 노드에도 걸어 최종 출력 합의 피크와 1.0 초과 샘플 수를 세고, 소리가 시작된 시각·인트로 프레임을 기록했다.

| 시나리오 | 시작된 소리(인트로 프레임) | 출력 피크 | 1.0 초과 샘플 |
|---|---|---|---|
| A 인트로 시작 직후 소리만 풀림(F9) → 끝까지 | 0xB1 f378, 0xB2 f431, 0xB5 f510, 0xB4 f574, 0x8A f650, 0xB3 f742 (0xB0 f342 는 풀리기 전이라 버려짐) | 0.831 (−1.6dBFS, f743 곡+플래시) | 0 / 415만 |
| B 잠긴 채 f1500 에서 소리만 풀림 | 0x8A 1개가 **처음부터** 시작(f1512) | 0.608 | 0 |
| C 잠긴 채 f1500 에서 건너뛰기(첫 입력) | 없음 | 0 | 0 |
| D 풀린 뒤 f760 에서 건너뛰기 | A 와 같고 곡은 즉시 정지 | 0.831 | 0 |
| E 로비 → 편성 → 경기 시작 25초(0x95 → GO → FIGHT → 0x88 + 경기 효과음 43개) | - | 0.951 (−0.4dBFS) | 0 / 340만 |

확인된 사실:
- **인트로 구간 출력은 잘리지 않는다**(피크 0.83, 1.0 초과 0). 신고 원인을 "곡+효과음 합산 클리핑"으로 본 가정은 인트로에서는 틀렸다. 경기 중은 25초 표본에서 0.95 까지 올라가 여유가 0.4dB 뿐이었다(§5 최악 합산 1.456 은 여전히 가능).
- **원작에 없는 소리는 없다.** 인트로에서 나는 소리는 원작 큐 7개(10 문서 §4)뿐이고 프레임도 같다. 프레임마다 반복되는 중복 발화 0(요청 6, 재생 5, 잠금 1), 같은 효과음 여러 개 동시 재생 0, 풀릴 때 밀린 효과음이 한꺼번에 나오는 일 0(잠긴 동안의 효과음은 버린다).
- 인트로는 일반 입력(키·클릭·터치)이 곧 건너뛰기라서, **소리가 들리는 경우는 건너뛰지 않는 입력(F1~F12, Ctrl/Alt 조합 키 = 전체 화면 F11 등)으로 소리가 풀렸을 때뿐**이다. Ctrl 단독은 브라우저가 사용자 입력으로 치지 않아 풀리지 않는다[실측].
- 원작과 달랐던 점 3가지:
  1. 잠긴 채 지나간 타이틀 곡(0x8A)이 풀리는 순간 **처음부터** 시작했다(B). 원작이라면 곡이 이미 그만큼 흘러 있다.
  2. 불덩이 0xB0(0.97초)이 착탄 0xB1(0.6초 뒤)과 0.37초 겹쳤다. 기준 녹음에서는 0xB1 이 시작되면 0xB0 이 끊긴다(§11-2).
  3. 전체 음량이 기준 녹음보다 컸다(§11-2).

### 11-2. 기준 에뮬레이터 녹음과 대조
기준 = `tools/ext_emu/bizhawk`(Genesis Plus GX)로 ROM 을 무입력 2950프레임 돌린 소리 덤프(`EmuHawk.exe --dump-type=wave --dump-name=<wav> --dump-length=2950 --dump-close rom/danpei.gen`, 49.2초). 공개 에뮬레이터 녹음과 대조한 것은 이번이 처음이다(§2 는 자작 드라이버 실행 + libgme).

| 소리 | 로그 스펙트로그램 상관 | 우리 RMS / 기준 RMS | 차이(dB) | 스펙트럼 중심(우리/기준 Hz) |
|---|---|---|---|---|
| 0xB0 불덩이 | 0.63 | 0.127 / 0.069 | +5.3 | 4844 / 4479 |
| 0xB1 착탄 | 0.68 | 0.113 / 0.059 | +5.7 | 4134 / 4022 |
| 0xB2 불꽃 | 0.81 | 0.123 / 0.069 | +5.0 | 843 / 735 |
| 0xB5 소로고 | 0.69 | 0.142 / 0.074 | +5.6 | 2917 / 3439 |
| 0xB4 와이프 | 0.68 | 0.118 / 0.056 | +6.5 | 3836 / 4669 |
| 0xB3 플래시(기준은 곡 포함) | 0.64 | 0.185 / 0.110 | +4.5 | 2578 / 2865 |
| 0x8A 타이틀 곡(2초 창 9개, 4~34초) | 0.90~0.93 | 0.088~0.102 / 0.053~0.063 | +4.2~4.3 | 1310 / 1405 |

- 곡은 기준 녹음과 같은 곡이다(상관 0.90~0.93 = §2-3 의 1·2회차 상관과 같은 수준). 효과음은 50ms 단위 음량 변화 모양이 기준과 같다(잡음형 소리라 스펙트로그램 상관은 낮게 나온다).
- **우리 출력은 기준 녹음보다 곡 +4.3dB, 효과음 +5.0~6.5dB 컸다.** 곡의 차이는 렌더 때 더한 공통 이득 +4.28dB 와 같다. 효과음은 곡 대비 0.7~2.2dB 더 크다(22050Hz 모노 렌더·기준 쪽 저역 통과 필터 차이로 추정, 미확인).
- 기준 녹음의 인트로 전체 피크는 0.446(−7.0dBFS), 1.0 근처 샘플 0. 파일 자체(8a.ogg, b0~b5.wav)에도 잘린 샘플은 없다(피크 0.36~0.75).
- 인트로 효과음은 원래 잡음형 FM 소리(스펙트럼 중심 3~5kHz)다. "깨진다"가 이 음색 자체를 가리킬 가능성이 있다[추정, 청취 필요].

- 신고 증상의 직접 원인은 확정하지 못했다. 수치로 배제한 것: 출력 클리핑, 원작에 없는 소리, 중복 발화, 밀린 효과음 일괄 재생. 남은 후보: 기준보다 4~6dB 큰 음량(수정함), 잡음형 효과음 음색, 재생 기기·OS 쪽 왜곡(측정 불가).
- 효과음이 곡 대비 0.7~2.2dB 큰 차이는 그대로 뒀다. 경기 효과음·음성은 기준 녹음과 대조하지 않았다.
- 리미터가 실제로 누르는 구간(합 0.9 초과)의 음질은 수치로만 확인했다(출력 1.0 이하).
- 탭을 숨긴 채 소리가 잠겨 있던 동안에는 인트로 프레임은 멈추고 시계는 흐르므로, 그 뒤 풀리면 타이틀 곡 위치가 화면보다 앞선다(드문 경우, 미수정).
- 효과음 한 번에 하나(solo)는 인트로에만 적용했다. 경기 효과음의 원작 채널 배정은 판독하지 않았다.
